# valiant

## A. FACTUALLY WRONG

1. **The alleged hard-coded ordering of pattern and custom variants is wrong.** The record says: “**background variants → PAM/protospacer protection edits → mutator functions on r1/r2/r3 → custom VCF variants**” (lines 94–97). Background and PAM changes do form the shared base sequence, but `Targeton.process()` registers **custom variants first and pattern variants second**, and the two are independent one-event oligo branches rather than sequential transformations of one another. [`targeton.py`, lines 204–312](https://github.com/cancerit/VaLiAnT/blob/8796cc112dafd4919fec59913f58cd2be87c45eb/src/valiant/targeton.py#L204-L312)

2. **Built-in mutators do generate multi-base variants.** The record says: “**multi-base and combinatorial variants can only enter via a hand-authored VCF**” (lines 189–193). The combinatorial part is correct, but the multi-base part is false: arbitrary-span deletion mutators, `inframe`, `ala`, `stop`, `aa`, and `snvre` can all generate multi-nucleotide deletion or replacement events without a VCF. [README deletion and codon mutators, lines 272–463](https://github.com/cancerit/VaLiAnT/blob/8796cc112dafd4919fec59913f58cd2be87c45eb/README.md#L272-L463)

3. **`--include-no-op-oligo` is not a general WT-inclusion switch.** The record calls it “**WT ('no-op') inclusion**” and says it adds a single sequence (lines 192–193). It emits a no-variable-change oligo only when at least one background or annotated PAM edit applies, and that oligo carries the fixed altered background/PAM sequence—so it need not be wild type. With no applicable fixed edit, the flag adds nothing. [`sge_cli.py`, lines 41–44](https://github.com/cancerit/VaLiAnT/blob/8796cc112dafd4919fec59913f58cd2be87c45eb/src/valiant/sge_cli.py#L41-L44); [`meta_table.py`, lines 414–457](https://github.com/cancerit/VaLiAnT/blob/8796cc112dafd4919fec59913f58cd2be87c45eb/src/valiant/meta_table.py#L414-L457)

4. **Not every execution writes `config.json`.** The record twice says “**each execution**”/“**per execution**” writes the configuration (lines 242–243 and 621–622). A normal library-generation run does, but `--sequences-only` writes `ref_sequences.csv` and calls `sys.exit(0)` before the common `finalise()` function writes the configuration. [`sge_proc.py`, lines 527–568](https://github.com/cancerit/VaLiAnT/blob/8796cc112dafd4919fec59913f58cd2be87c45eb/src/valiant/sge_proc.py#L527-L568); [`common_cli.py`, lines 94–115](https://github.com/cancerit/VaLiAnT/blob/8796cc112dafd4919fec59913f58cd2be87c45eb/src/valiant/common_cli.py#L94-L115)

5. **Current v4 does not consume GTF/GFF stop-feature rows.** The record says “**only CDS, UTR and stop features are taken into consideration**” (lines 320–322). The current loader recognizes only literal `CDS` and `UTR` feature types and ignores all others; it obtains stop context by extending the terminal CDS by three bases. This is a paper-era/current-software distinction that the record does not flag. [README, lines 104–108](https://github.com/cancerit/VaLiAnT/blob/8796cc112dafd4919fec59913f58cd2be87c45eb/README.md#L104-L108); [`loaders/gtf.py`, lines 51–54 and 107–160](https://github.com/cancerit/VaLiAnT/blob/8796cc112dafd4919fec59913f58cd2be87c45eb/src/valiant/loaders/gtf.py#L51-L160)

6. **The record overstates enforcement of “one transcript per execution.”** It says “**the code confirms the wiki**” and concludes “**one transcript per run**” (lines 319–330, repeated at 632–635). That is the documented recommendation, but the current loader validates one gene/transcript pair only within the selected contig/strand group. `run_sge` loops over contigs, clears per-contig state, and merely warns—not errors—when annotation accompanies multiple contigs. Thus separate transcripts on separate contigs can proceed in one invocation; the implementation restriction is not globally “one per execution.” [`loaders/gtf.py`, lines 131–155](https://github.com/cancerit/VaLiAnT/blob/8796cc112dafd4919fec59913f58cd2be87c45eb/src/valiant/loaders/gtf.py#L131-L155); [`sge_proc.py`, lines 409–451 and 548–563](https://github.com/cancerit/VaLiAnT/blob/8796cc112dafd4919fec59913f58cd2be87c45eb/src/valiant/sge_proc.py#L409-L451)

7. **The SNVRE codon-ranking rule is misstated.** The record says `snvre` “**swaps a missense codon for the next most frequent triplet**” (lines 421–423). Current behavior is: use the top-ranked synonymous codon for the SNV’s amino-acid result, and use the second-ranked one only if the triggering SNV codon is already the top-ranked codon; nonsense changes follow the analogous stop-codon rule. [README, lines 383–463](https://github.com/cancerit/VaLiAnT/blob/8796cc112dafd4919fec59913f58cd2be87c45eb/README.md#L383-L463); [`mutators/snv_re.py`](https://github.com/cancerit/VaLiAnT/blob/8796cc112dafd4919fec59913f58cd2be87c45eb/src/valiant/mutators/snv_re.py)

8. **Background-overlap filtering is narrower than the record claims.** It says “**Mutations that overlap background variants are discarded**” (lines 586–590 and 652). In the current implementation, pattern/custom variants are discarded by this overlap test for **coordinate-shifting background variants** (indels); the masks used by `ref_var_overlaps_var`/`alt_var_overlaps_var` are populated only where `alt_ref_delta != 0`. A mutation coincident with a background SNV is not discarded by that mechanism. [`genomic_position_offsets.py`, lines 108–146 and 246–277](https://github.com/cancerit/VaLiAnT/blob/8796cc112dafd4919fec59913f58cd2be87c45eb/src/valiant/genomic_position_offsets.py#L108-L146); [`targeton.py`, lines 204–227 and 278–290](https://github.com/cancerit/VaLiAnT/blob/8796cc112dafd4919fec59913f58cd2be87c45eb/src/valiant/targeton.py#L204-L290)

9. **SNVs are not the only generic variants that can affect partial/liminal codon bases.** The limitation says “**only SNVs reach them**” (line 640). Codon-specific replacement/deletion mutators do ignore partial codons, but the generic parametric deletion mutator and an imported custom variant can also affect those bases. [README mutator scope, lines 257–274](https://github.com/cancerit/VaLiAnT/blob/8796cc112dafd4919fec59913f58cd2be87c45eb/README.md#L257-L274); [`mutators/deletion.py`, lines 32–48](https://github.com/cancerit/VaLiAnT/blob/8796cc112dafd4919fec59913f58cd2be87c45eb/src/valiant/mutators/deletion.py#L32-L48); [README custom variants, lines 465–476](https://github.com/cancerit/VaLiAnT/blob/8796cc112dafd4919fec59913f58cd2be87c45eb/README.md#L465-L476)

10. **PAM protection edits are not restricted to synonymous or noncoding substitutions.** The record describes them as “**user-defined synonymous or non-coding SNVs**” (lines 573–577). That is the intended design pattern in the paper, not an input restriction in v4: the current parser requires a one-base REF/ALT and `SGRNA`, but accepts missense and nonsense edits too, which is why output supports `pam_mut_annot = syn|mis|non|ncd`. [`pam_variant.py`, lines 32–57](https://github.com/cancerit/VaLiAnT/blob/8796cc112dafd4919fec59913f58cd2be87c45eb/src/valiant/pam_variant.py#L32-L57); [README metadata, lines 774–775](https://github.com/cancerit/VaLiAnT/blob/8796cc112dafd4919fec59913f58cd2be87c45eb/README.md#L774-L775)

11. **The two custom-provenance INFO tags are not carried by every output VCF record.** The record says the two output VCFs are “**each carrying `SGE_OLIGO`, `SGE_SRC`, `SGE_VCF_ALIAS`, `SGE_VCF_VAR_ID`**” (lines 591–593; similarly 368–370). `SGE_OLIGO` and `SGE_SRC` are general; `SGE_VCF_ALIAS` and `SGE_VCF_VAR_ID` are optional and apply only to imported custom variants, not ordinary mutator-generated records. [README, lines 789–803](https://github.com/cancerit/VaLiAnT/blob/8796cc112dafd4919fec59913f58cd2be87c45eb/README.md#L789-L803); [`vcf_writer.py`](https://github.com/cancerit/VaLiAnT/blob/8796cc112dafd4919fec59913f58cd2be87c45eb/src/valiant/vcf_writer.py)

## B. INCOMPLETE

1. **Core `snv` semantics.** The record names `snv` but never plainly says that it emits all three non-reference bases at every eligible nucleotide, one event per oligo, in coding and noncoding regions. [README, lines 294–309](https://github.com/cancerit/VaLiAnT/blob/8796cc112dafd4919fec59913f58cd2be87c45eb/README.md#L294-L309) This is material because it defines the basic nucleotide-saturation coverage and library-size scaling.

2. **`inframe`, `ala`, and `stop` semantics and no-op behavior.** `inframe` deletes each complete reading-frame triplet; `ala` and `stop` replace each complete codon with the table’s top alanine/stop codon, skipping a codon already identical to that selected replacement. [README, lines 311–350](https://github.com/cancerit/VaLiAnT/blob/8796cc112dafd4919fec59913f58cd2be87c45eb/README.md#L311-L350); [`mutators/codon.py`, lines 41–88](https://github.com/cancerit/VaLiAnT/blob/8796cc112dafd4919fec59913f58cd2be87c45eb/src/valiant/mutators/codon.py#L41-L88) These are core library designs, and the skip rule changes exact counts.

3. **Full SNVRE behavior.** The record mentions the dependency and a missense use but omits synonymous expansion, nonsense handling, exclusion of reference/triggering/duplicate codons, and the fact that amino acids with no additional synonymous codon produce no extra design. [README, lines 383–463](https://github.com/cancerit/VaLiAnT/blob/8796cc112dafd4919fec59913f58cd2be87c45eb/README.md#L383-L463) This is material because SNVRE is a distinctive representation-expansion capability, not merely another codon substitution.

4. **Custom-VCF ingestion restrictions.** The record does not disclose that v4 reads only `r.alts[0]` from a multiallelic record, skips monomorphic records, and requires unambiguous A/C/G/T alleles; symbolic or ambiguous ALTs fail. [`custom_variant.py`, lines 78–129](https://github.com/cancerit/VaLiAnT/blob/8796cc112dafd4919fec59913f58cd2be87c45eb/src/valiant/custom_variant.py#L78-L129); [`DnaStr`, lines 25–30](https://github.com/cancerit/VaLiAnT/blob/8796cc112dafd4919fec59913f58cd2be87c45eb/src/valiant/strings/dna_str.py#L25-L30) This is material because a catalog VCF can silently lose additional ALT alleles or records.

5. **Background masking and validation edge cases.** `--bg-mask BED` positionally excludes background records, yet the record merely names the input and notes that one example does not use it; it also omits that `--force-bg-indels` requires `--force-bg-ns`, that noncoding background indels warn, and that a PAM/background overlap in the same coding codon is fatal. [README, lines 114–120](https://github.com/cancerit/VaLiAnT/blob/8796cc112dafd4919fec59913f58cd2be87c45eb/README.md#L114-L120); [`sge_config.py`, lines 63–69](https://github.com/cancerit/VaLiAnT/blob/8796cc112dafd4919fec59913f58cd2be87c45eb/src/valiant/sge_config.py#L63-L69); [`sge_proc.py`, lines 109–128 and 306–320](https://github.com/cancerit/VaLiAnT/blob/8796cc112dafd4919fec59913f58cd2be87c45eb/src/valiant/sge_proc.py#L109-L128) These rules determine which background-aware designs run, fail, or change composition.

6. **PAM-edit conflict rules.** The record omits that duplicate-position protection edits and multiple edits in one coding codon are rejected, while a linked edit outside the targeton is warned and not applied there. [`sge_proc.py`, lines 214–260](https://github.com/cancerit/VaLiAnT/blob/8796cc112dafd4919fec59913f58cd2be87c45eb/src/valiant/sge_proc.py#L214-L260) This is material to whether a user-specified protected repair-template design is representable.

7. **cDNA mode’s full boundary.** The record says custom VCF and VCF output are unavailable, but does not clearly state that cDNA also lacks PAM edits, background/mask variants, `--revcomp-minus-strand`, and `--sequences-only`; moreover, a mutable `r2` that overlaps an annotated CDS must be wholly within that CDS. [`cdna_cli.py`, lines 26–75](https://github.com/cancerit/VaLiAnT/blob/8796cc112dafd4919fec59913f58cd2be87c45eb/src/valiant/cdna_cli.py#L26-L75); [`cdna_proc.py`, lines 78–107](https://github.com/cancerit/VaLiAnT/blob/8796cc112dafd4919fec59913f58cd2be87c45eb/src/valiant/cdna_proc.py#L78-L107) This is material because otherwise a reader may assume fixed-edit and strand features described for SGE transfer to cDNA.

8. **Mutable-region exon geometry.** The record gives the coding/noncoding-mixing rule but omits that an individual mutable `r1`, `r2`, or `r3` is also rejected if it overlaps multiple CDS exons. [`targeton.py`, lines 92–103](https://github.com/cancerit/VaLiAnT/blob/8796cc112dafd4919fec59913f58cd2be87c45eb/src/valiant/targeton.py#L92-L103) This is material because it limits how targetons spanning splice junctions must be partitioned.

9. **Operational input contract.** The output directory must already exist; SGE needs a local FASTA and matching `.fai`; contig names must match the FASTA and annotation; and `SPECIES`/`ASSEMBLY` are metadata strings rather than remote reference selectors. [README, lines 65–110 and 211–217](https://github.com/cancerit/VaLiAnT/blob/8796cc112dafd4919fec59913f58cd2be87c45eb/README.md#L65-L110); [`common_cli.py`, lines 32–46](https://github.com/cancerit/VaLiAnT/blob/8796cc112dafd4919fec59913f58cd2be87c45eb/src/valiant/common_cli.py#L32-L46) This is material to what “species/genome-build agnostic” actually means in use.

10. **Exact sequence-construction/filtering interactions.** The record does not state that adaptors count toward `--min-length`/`--max-length`, are appended after any targeton reverse complement (so the adaptors themselves are not reverse-complemented), and that below-minimum as well as above-maximum oligos go to excluded metadata. [`common_cli.py`, lines 56–65 and 79–91](https://github.com/cancerit/VaLiAnT/blob/8796cc112dafd4919fec59913f58cd2be87c45eb/src/valiant/common_cli.py#L56-L91); [`meta_table.py`, lines 404–407 and 451–465](https://github.com/cancerit/VaLiAnT/blob/8796cc112dafd4919fec59913f58cd2be87c45eb/src/valiant/meta_table.py#L404-L465) This is material because it determines the actual synthesis sequence and whether it survives filtering.

11. **Small action-vector and replay restrictions.** Duplicate mutator labels and whitespace are ignored; a replayed configuration with a different application version produces a warning rather than a compatibility guarantee. [README, lines 630–636](https://github.com/cancerit/VaLiAnT/blob/8796cc112dafd4919fec59913f58cd2be87c45eb/README.md#L630-L636), [519–536](https://github.com/cancerit/VaLiAnT/blob/8796cc112dafd4919fec59913f58cd2be87c45eb/README.md#L519-L536) These are minor but material to exact parser behavior and reproducibility claims.

## C. BALANCE

The record is **mostly fair, with a capability rather than limitation emphasis**. It gives generous, proportionate space to VaLiAnT’s real strengths—mixed region-specific mutagenesis, two design modes, background-aware design, prime-editing use, parametric deletions, rich provenance, two VCFs, deduplication, and examples—and devotes substantially more total space to capabilities/examples than to its compact limitations section. It is therefore not unfairly limitation-heavy. The main imbalance is inside the capability coverage: several absence claims and implementation details receive exhaustive treatment while the ordinary `snv`, `inframe`, `ala`, `stop`, and full `snvre` design semantics are largely name-only; the factual errors and omitted edge restrictions above also make the positive account somewhat more expansive than exact.

# mpranator

### A. FACTUALLY WRONG

1. **“the four live forms submit a JS-generated `ordering` field”** — Only the Motif and SNP oligo-assembly forms have the draggable component list and synthesize an `ordering` field. Transmutation and PWM Seq-Gen have neither that field nor that JavaScript, and their result views do not read it. Evidence: the four official forms ([Motif](https://www.genomegeek.com/MPRA/Motifs/), [SNP](https://www.genomegeek.com/MPRA/SNPs/), [Transmutation](https://www.genomegeek.com/MPRA/Transmutation/), [PWM](https://www.genomegeek.com/MPRA/PWM/)); repository [`part1.html` lines 81–118](https://github.com/hemberg-lab/MPRAnator/blob/master/iliasApp/templates/iliasApp/part1.html#L81-L118), [`mpraSnp.html` lines 80–112](https://github.com/hemberg-lab/MPRAnator/blob/master/iliasApp/templates/iliasApp/mpraSnp.html#L80-L112), and [`views.py` lines 34–44, 151–215, 325–342](https://github.com/hemberg-lab/MPRAnator/blob/master/iliasApp/views.py).

2. **“Headers are generated entirely by the tool; the user never supplies them.”** — MPRAnator generates descriptors, but it also preserves user-supplied names: Motif output embeds the background FASTA header, Transmutation prefixes the input FASTA name, SNP output begins with the supplied coordinate header, and PWM output uses the supplied PWM name. Evidence: [`oligo.py` lines 71–76](https://github.com/hemberg-lab/MPRAnator/blob/master/oligo.py#L71-L76), [`views.py` lines 210–211](https://github.com/hemberg-lab/MPRAnator/blob/master/iliasApp/views.py#L210-L211), and the official documentation’s Transmutation and PWM header examples ([documentation](https://www.genomegeek.com/MPRA/documentation/)).

3. **“`Part3Form` lacks the reverse/complement options the live site and Supplementary describe.”** — The public repository's `Part3Form` explicitly declares both `reverse` and `complement`, and its result view applies them. PWM code is absent from the snapshot, but reverse/complement Transmutation is not. Evidence: [`forms.py` lines 340–349](https://github.com/hemberg-lab/MPRAnator/blob/master/iliasApp/forms.py#L340-L349) and [`views.py` lines 164–194](https://github.com/hemberg-lab/MPRAnator/blob/master/iliasApp/views.py#L164-L194).

4. **“SNP module doubles as a plain assembly tool” and “can accept a set of FASTA sequences without a list of associated SNPs.”** — This is the paper-era/Supplementary statement quoted by the record, not a capability of the public software now available: the repository form explicitly raises `Enter SNPs!` when the SNP text is empty, and the current live form also rejects an empty SNP list. The record presents the older statement as an unqualified current capability instead of flagging the paper/software disagreement. Evidence: [`forms.py` lines 534–545](https://github.com/hemberg-lab/MPRAnator/blob/master/iliasApp/forms.py#L534-L545) and the [current SNP form](https://www.genomegeek.com/MPRA/SNPs/).

5. **“both [shipped REST scripts] 500 as distributed.”** — The exact currently served scripts do not receive an HTTP 500 when run as written. They POST to `http://www.genomegeek.com/...`; on 2026-08-14 that request followed a 301 to HTTPS, was converted to GET, then redirected to the input form and ended at HTTP 200. Under Python 3 the next line fails locally because `result.content` (bytes) is written to a text-mode file. Equivalent payloads posted directly to the HTTPS result URLs did return 500, so the underlying generators were failing, but the stated behavior and failure mechanism of the distributed clients are wrong. Evidence: the official homepage’s two API-script downloads ([homepage](https://www.genomegeek.com/)), the form endpoints, and the repository clients’ same text-mode write pattern ([Motif client lines 68–74](https://github.com/hemberg-lab/MPRAnator/blob/master/downloadables/MpraMotifs_script.py#L68-L74), [SNP client lines 58–64](https://github.com/hemberg-lab/MPRAnator/blob/master/downloadables/MpraSnps_script.py#L58-L64)).

Live checks on 2026-08-14 confirmed a 9-nt difference works while a 10-nt difference does not. Evidence: repository root ([GitHub](https://github.com/hemberg-lab/MPRAnator)), [`mycustom.py` lines 16–73 and 124–195](https://github.com/hemberg-lab/MPRAnator/blob/master/mycustom.py), and [`part1.py`](https://github.com/hemberg-lab/MPRAnator/blob/master/part1.py).

### B. INCOMPLETE

1. **Repository Motif truncation.** The public result view silently uses only the first 20 background records and only the first 800 nt of each (`sequenceO[:20]`, `i.sequence[:800]`). The record discusses declared form caps but omits this much tighter implementation-only truncation; it is material because a seemingly accepted input can produce a library from only a subset of the supplied designs. Evidence: [`views.py` lines 81–84](https://github.com/hemberg-lab/MPRAnator/blob/master/iliasApp/views.py#L81-L84).

2. **Transmutation realization and reproducibility semantics.** The module emits one randomly shuffled/mutated realization per input sequence, provides neither a seed nor a replicate-count control, uses a simple mononucleotide shuffle, and applies combined operations in the fixed order scramble → reverse → complement → point mutation. The record names the four operations but does not convey these restrictions; they are material for determining whether negative-control libraries are reproducible or compositionally controlled. Evidence: [`part3.py` lines 5–48](https://github.com/hemberg-lab/MPRAnator/blob/master/part3.py#L5-L48) and [`views.py` lines 164–205](https://github.com/hemberg-lab/MPRAnator/blob/master/iliasApp/views.py#L164-L205).

3. **PWM input and run bounds.** The current PWM form constrains threshold to 0–1 and simulations to 1–1000, expects a `>` name followed by four whitespace-separated numeric rows, requires dot decimals, and exposes duplicate removal. The record explains the two modes and duplicate removal but omits the numeric bounds and complete accepted matrix syntax; these define the actual size and format of PWM-derived libraries. Evidence: [current PWM form](https://www.genomegeek.com/MPRA/PWM/) and [official PWM documentation](https://www.genomegeek.com/MPRA/documentation/).

4. **Example API clients do not expose all documented modes.** The downloadable Motif client omits `reverseComplement`, and the SNP client omits `makeSnpCombinations`; users must discover and add those form fields themselves. The record says programmatic access covers two modules but not that even those clients cover only a subset of their UI capabilities, which is material to the advertised programmatic interface. Evidence: [`MpraMotifs_script.py` data dictionary](https://github.com/hemberg-lab/MPRAnator/blob/master/downloadables/MpraMotifs_script.py#L45-L64), [`MpraSnps_script.py` data dictionary](https://github.com/hemberg-lab/MPRAnator/blob/master/downloadables/MpraSnps_script.py#L41-L55), and the [Motif](https://www.genomegeek.com/MPRA/Motifs/) and [SNP](https://www.genomegeek.com/MPRA/SNPs/) forms.

5. **Barcode filter/distance details.** The advertised edit-distance condition is not reliably enforced: the repository code counts *matching* positions, compares that number to `diffs`, retains the accumulated comparison list across candidates, and after a failed comparison regenerates without rechecking distance to existing barcodes. Its initial and fallback GC-bound predicates also differ, and barcoding is silently disabled unless the length, both GC bounds, and replicate count are all present. The record notes only that the distance test is “Hamming-style”; the omitted logic is material because neither the requested minimum separation nor consistent filtering is guaranteed by this snapshot. Evidence: [`part1.py` lines 52–88](https://github.com/hemberg-lab/MPRAnator/blob/master/part1.py#L52-L88) and [`getBarCodes` lines 295–319](https://github.com/hemberg-lab/MPRAnator/blob/master/part1.py#L295-L319).

6. **SNP parser and matching restrictions.** “VCF format” here means at least five whitespace-separated fields with no VCF-header handling, chromosomes limited to bare `1`–`22`/`X`/`Y`, and comma-separated ALT alleles; the supplied REF allele is not checked against the background. ### C. BALANCE

Ignoring its comparisons and evaluative rhetoric, the record gives Oligopool Calculator's strengths substantial and generally proportionate space: it inventories all 22 current modules, separates current software from example-only mutant generation in several places, and devotes a long section to capabilities beyond the survey matrix. 3. **Important design-objective modes and restrictions are scattered or absent.** `greedy_substitution` and `beam_substitution` support raw-response maximization with `y=None`, arbitrary per-candidate losses, `output_mask`, and single-character design with `motifs=None`; both are fixed-length substitution searches from one template, while only beam returns multiple distinct winners. [`greedy_substitution` signature and contract](https://github.com/jmschrei/tangermeme/blob/8d732b8c08764057b7ae5faa644d48664f36b44b/tangermeme/design/greedy_substitution.py#L24-L147); [`beam_substitution` signature and contract](https://github.com/jmschrei/tangermeme/blob/8d732b8c08764057b7ae5faa644d48664f36b44b/tangermeme/design/beam_substitution.py#L25-L174). **Why material:** these controls determine whether the package can express a user's actual design objective and whether the result is one sequence or a ranked variant set.

4. **The true insertion and deletion sequence generators are relegated to a tutorial list.** `ersatz.insert` retains the whole template and returns a longer batch; `ersatz.delete` excises a half-open interval and returns a shorter batch. Insert currently rejects starts greater than `sequence_length - motif_length`, even though output length grows; both use one coordinate across the batch. [`insert`](https://github.com/jmschrei/tangermeme/blob/8d732b8c08764057b7ae5faa644d48664f36b44b/tangermeme/ersatz.py#L20-L94); [`delete`](https://github.com/jmschrei/tangermeme/blob/8d732b8c08764057b7ae5faa644d48664f36b44b/tangermeme/ersatz.py#L300-L340). **Why material:** readers otherwise miss that core tangermeme can materialize variable-length indel collections even though its oracle-guided designers cannot search indels.

5. **Masked/paired substitution semantics are omitted.** `ersatz.substitute` can broadcast one motif or pair one motif with each input, and all-zero motif columns/default string `N` preserve the original character; `multisubstitute` centers and applies a multi-motif arrangement with explicit gaps. [`substitute`](https://github.com/jmschrei/tangermeme/blob/8d732b8c08764057b7ae5faa644d48664f36b44b/tangermeme/ersatz.py#L97-L195); [`multisubstitute`](https://github.com/jmschrei/tangermeme/blob/8d732b8c08764057b7ae5faa644d48664f36b44b/tangermeme/ersatz.py#L198-L297). **Why material:** these are useful batch-library construction modes, especially for degenerate constructs and per-member motif assignments, not just generic “motif implantation.”

6. **Control-library independence and diversity restrictions are missing.** `shuffle` applies the same positional permutation to every sequence in a batch for a given replicate; `dinucleotide_shuffle` fixes the selected region's first and last characters and can warn or fail when low diversity prevents the requested distinct shuffles. [`shuffle` documented behavior](https://github.com/jmschrei/tangermeme/blob/8d732b8c08764057b7ae5faa644d48664f36b44b/tangermeme/ersatz.py#L425-L498); [`dinucleotide_shuffle`](https://github.com/jmschrei/tangermeme/blob/8d732b8c08764057b7ae5faa644d48664f36b44b/tangermeme/ersatz.py#L529-L688). **Why material:** these details affect whether generated controls are statistically independent and how much library diversity they really contain.

7. **`predict` as a candidate-library scoring engine is underdescribed.** It batches collections that do not fit GPU memory, can retain the source as int8 and upcast batches, forwards aligned auxiliary inputs, post-processes outputs, supports tensor/list outputs, and restores model device/training state; however, auxiliary integer and Boolean inputs are cast to the model dtype unless wrapped. [`predict`](https://github.com/jmschrei/tangermeme/blob/8d732b8c08764057b7ae5faa644d48664f36b44b/tangermeme/predict.py#L17-L165). **Why material:** scalable oracle scoring is the bridge from a generated variant collection to ranking and selection.

8. **Variant-effect indel normalization is not explained.** `deletion_effect` expects an input padded by the maximum deletion count and trims the reference for equal model length; `insertion_effect` lengthens then trims a flank selected by `left`. The functions return before/after outputs, not edited sequences. [`variant_effect.py`](https://github.com/jmschrei/tangermeme/blob/8d732b8c08764057b7ae5faa644d48664f36b44b/tangermeme/variant_effect.py#L124-L404). **Why material:** without this restriction, “deletion/insertion effects” sounds like arbitrary variable-length-model support when it is actually fixed-model-length scoring.

9. **The paired-versus-product distinction is not made explicit.** `apply_product` evaluates every independent combination of `X` and auxiliary axes, while `apply_pairwise` crosses each sequence with index-zipped auxiliary contexts; the latter is public and documented in source/bundled guidance but omitted from the rendered Sphinx member list. [`product.py`](https://github.com/jmschrei/tangermeme/blob/8d732b8c08764057b7ae5faa644d48664f36b44b/tangermeme/product.py#L30-L349); [rendered member list source](https://github.com/jmschrei/tangermeme/blob/8d732b8c08764057b7ae5faa644d48664f36b44b/docs/api/product.rst). **Why material:** choosing the wrong interface changes the biological context set being evaluated and can multiply a library into invalid combinations.

10. **`utils.chunk` / `unchunk` are absent.** They tile variable-length sequence collections into overlapping fixed model windows and reconstruct base-resolution outputs; incomplete terminal windows are discarded, and current `unchunk` requires original lengths despite a `None` default. [`utils.py`, lines 649–786](https://github.com/jmschrei/tangermeme/blob/8d732b8c08764057b7ae5faa644d48664f36b44b/tangermeme/utils.py#L649-L786). **Why material:** this is the package's built-in way to score long or variable-length collections with fixed-window models.

11. **FASTA export's ambiguity restriction is omitted.** `io.one_hot_to_fasta` is a public, tested source function omitted from the rendered I/O member list, and it calls `characters` without exposing `force`/`allow_N`; ambiguous, tied, or all-zero columns can therefore fail—including all-zero positions that may occur in a construct returned by `greedy_marginalize`. [`one_hot_to_fasta`](https://github.com/jmschrei/tangermeme/blob/8d732b8c08764057b7ae5faa644d48664f36b44b/tangermeme/io.py#L540-L587); [`characters`](https://github.com/jmschrei/tangermeme/blob/8d732b8c08764057b7ae5faa644d48664f36b44b/tangermeme/utils.py#L338-L410). **Why material:** this determines whether a designed tensor can actually be exported without custom decoding.

12. **Motif-library ingestion and hard-consensus conversion are barely mentioned.** `io.read_meme` loads named PWMs, `utils.pwm_consensus` converts each to an argmax one-hot motif, and `characters` supplies the string accepted by design calls; ties choose the earliest channel and all-zero columns remain zero. [`read_meme`](https://github.com/jmschrei/tangermeme/blob/8d732b8c08764057b7ae5faa644d48664f36b44b/tangermeme/io.py#L590-L619); [`pwm_consensus`](https://github.com/jmschrei/tangermeme/blob/8d732b8c08764057b7ae5faa644d48664f36b44b/tangermeme/utils.py#L789-L822). **Why material:** it is the supported path from a motif database to the discrete motif vocabulary used in sequence design, and it makes clear that design does not optimize or sample PWMs directly.

13. **Reproducibility and sequence diagnostics are incomplete.** `gc_content` excludes all-zero positions, `entropy` and `information_content` operate per position on PWMs/one-hot batches, and unmentioned `set_seed` seeds Python, NumPy, Torch, and CUDA; none is enforced as a design constraint, and explicit `random_state` arguments take precedence. [`utils.py`, lines 874–1016](https://github.com/jmschrei/tangermeme/blob/8d732b8c08764057b7ae5faa644d48664f36b44b/tangermeme/utils.py#L874-L1016). **Why material:** these are the only built-in composition/diversity diagnostics and global reproducibility helper for generated collections.

14. **Seqlet-discovery restrictions are incomplete.** Both callers require projected 2-D attribution tracks; `recursive_seqlets` calls only positive seqlets, assumes equal-length examples, and prevents core overlap, while `tfmodisco_seqlets` is only the seqlet-calling stage rather than the full external TF-MoDISco workflow. [`seqlet.py`](https://github.com/jmschrei/tangermeme/blob/8d732b8c08764057b7ae5faa644d48664f36b44b/tangermeme/seqlet.py#L211-L577). **Why material:** these restrictions shape which candidate motifs/parts can be discovered and subsequently supplied to the design APIs.

15. **Matched-background output semantics are incomplete.** `match.extract_matching_loci` returns sorted coordinates rather than sequences and does not preserve one-to-one pairing with input loci; GC matching is binned, scarce bins spill to neighbors, and high-N query loci can be dropped. [`extract_matching_loci`](https://github.com/jmschrei/tangermeme/blob/8d732b8c08764057b7ae5faa644d48664f36b44b/tangermeme/match.py#L372-L621). **Why material:** these backgrounds drive marginal-effect estimates and construct design, so treating them as paired controls would change the analysis.

16. **The paper/current-software boundary is not stated.** The supplied August 2025 paper reports tangermeme **0.5.1** for its benchmark, whereas the surveyed software is 1.4.0 and now includes later design APIs, most visibly `beam_substitution`; conversely, former FIMO/Tomtom CLIs have moved out. [paper, Methods/software versions, pp. 6 and 9](/mnt/c/Users/zhliu/Desktop/KinneyLab/25_poolparty_private/revision/tool_survey/papers/Schreiber2025_tangermeme_all.pdf); [current 1.4 history](https://github.com/jmschrei/tangermeme/blob/8d732b8c08764057b7ae5faa644d48664f36b44b/docs/whats_new.rst#L9-L22); [current README migration warning](https://github.com/jmschrei/tangermeme/blob/8d732b8c08764057b7ae5faa644d48664f36b44b/README.md#L65-L78). **Why material:** without the version boundary, paper-wide statements can be mistaken for verified properties of the current implementation, as happened with universal multi-output support.

17. **Installation commands are absent.** Current primary instructions are `pip install tangermeme` or `uv add tangermeme`; Python >=3.10 and PyTorch >=2.0 are required. [README installation section](https://github.com/jmschrei/tangermeme/blob/8d732b8c08764057b7ae5faa644d48664f36b44b/README.md#L18-L47); [`pyproject.toml`](https://github.com/jmschrei/tangermeme/blob/8d732b8c08764057b7ae5faa644d48664f36b44b/pyproject.toml#L5-L35). **Why material:** version, license, and maintenance are recorded, but a reader still cannot tell from the record how the current package is obtained.

## C. BALANCE

The record is **not fully balanced**. It is unusually conscientious about several real strengths—motif placement, spacing sweeps, control generation, beam/screen top-*n* outputs, composable perturbation/model operations, interpretation tools, and active maintenance—and it corrects some prior understatements. Even so, it documents absent pooled-library abstractions and wet-lab features at much greater depth than it explains the four current design algorithms, especially de novo `screen` and background-averaged `greedy_marginalize`; its concluding absolute claim that tangermeme returns only controls, DeepLIFT references, and design winners erases the core sequence-returning Ersatz transformations. Capabilities are therefore substantial but not given proportionate, consistently accurate space relative to limitations.

# biopython

### A. FACTUALLY WRONG

1. **Wrong introduction version for undefined sequences.** The record says, **“Since 1.78 it also supports undefined and partially-defined sequences.”** Undefined `Seq(None, length=...)` support was introduced in **1.79**, not 1.78; the 1.79 release notes explicitly call it new. The current capability is real, but its version history is wrong. [1.88 `NEWS.rst`, 1.79 section](https://github.com/biopython/biopython/blob/biopython-188/NEWS.rst); [`Bio.Seq` API](https://biopython.org/docs/latest/api/Bio.Seq.html).

2. **`Alignment` and `SeqIO.to_dict()` are mischaracterized.** The record calls `Alignment`/`Alignments`/`MultipleSeqAlignment` **“alignments, i.e. equal-length gapped rows”** and groups **“`SeqIO.to_dict()` / `index()` / `index_db()` [as] views over a file.”** Only the legacy `MultipleSeqAlignment` directly stores equal-length gapped `SeqRecord` rows; modern `Alignment` stores original sequences (which can differ in length) plus a coordinate array, and `Alignments` is a container of such objects. Separately, `to_dict()` eagerly consumes any record iterable into an ordinary in-memory dictionary; only `index()` and `index_db()` are file-backed random-access objects. [`Bio.Align.Alignment` / `Alignments` source](https://github.com/biopython/biopython/blob/biopython-188/Bio/Align/__init__.py); [`Bio.SeqIO.to_dict`, `index`, and `index_db`](https://biopython.org/docs/latest/api/Bio.SeqIO.html).

3. **Insertion does not preserve every feature.** The record says, **“Insertion is `rec[:i] + insert + rec[i:]` with features maintained.”** `SeqRecord` slicing retains and shifts only features fully contained in each slice; a feature that crosses `i` is omitted from both slices and therefore lost after concatenation. Most general annotations and `dbxrefs` are also discarded by each slice. [`SeqRecord.__getitem__` and `__add__`](https://github.com/biopython/biopython/blob/biopython-188/Bio/SeqRecord.py); [`Bio.SeqRecord` API](https://biopython.org/docs/latest/api/Bio.SeqRecord.html).

4. **Arbitrary record metadata do not all round-trip through GenBank.** The record says the `annotations`, `features`, and `letter_annotations` containers **“all round-trip to GenBank.”** GenBank writing maps only supported INSDC record fields and features/qualifiers; arbitrary `annotations` keys and general `letter_annotations` (for example per-letter quality or custom arrays) are not serialized and therefore cannot generally round-trip. [`Bio.SeqIO.InsdcIO` GenBank writer](https://github.com/biopython/biopython/blob/biopython-188/Bio/SeqIO/InsdcIO.py); [`SeqRecord.letter_annotations`](https://biopython.org/docs/latest/api/Bio.SeqRecord.html#Bio.SeqRecord.SeqRecord.letter_annotations).

5. **The current statistical-learning inventory is obsolete.** The record says, **“Biopython's only ML/statistical content is the legacy `Bio.HMM`, `Bio.Cluster`, and `Bio.PopGen`.”** Current 1.88 has no substantive HMM implementation: `Bio.HMM.DynamicProgramming`, `Trainer`, `MarkovModel`, and `Utilities`, along with `Bio.kNN`, `Bio.LogisticRegression`, `Bio.NaiveBayes`, and `Bio.MaxEntropy`, were removed in 1.86; only an empty `Bio.HMM` package initializer remains. `Bio.Cluster` remains, while current `Bio.PopGen` contains GenePop parsing/manipulation rather than the 2009 simulation/outlier suite. [1.88 `DEPRECATED.rst`, statistical modules](https://github.com/biopython/biopython/blob/biopython-188/DEPRECATED.rst); [`Bio.HMM` source](https://github.com/biopython/biopython/tree/biopython-188/Bio/HMM); [`Bio.PopGen` source](https://github.com/biopython/biopython/tree/biopython-188/Bio/PopGen).

6. **Two 2009-to-current removals are left unflagged and the package-directory list obscures them.** The record reproduces a current package list containing **“Alphabet … HMM … PopGen”** and later lists **“population genetics (`Bio.PopGen`)”** without explaining that `Bio.Alphabet` is now only an import-failing compatibility stub, or that the paper's `Bio.PopGen.FDist` and `Bio.PopGen.SimCoal` functionality was removed in 1.70. The correct current picture is no Alphabet object and only GenePop under `Bio.PopGen`; the paper's Alphabet, coalescent simulation, and FST-outlier claims are historical. [`Bio.Alphabet` stub](https://github.com/biopython/biopython/blob/biopython-188/Bio/Alphabet/__init__.py); [1.88 `DEPRECATED.rst`](https://github.com/biopython/biopython/blob/biopython-188/DEPRECATED.rst); [Cock et al. 2009, pp. 1422–1423](../papers/Cock2009_biopython.pdf).

7. **The transcript-format claim conflates formats with different fields.** The record says **“BED12/bigBed/PSL/bigPsl exon-block transcript models with `thickStart`/`thickEnd` CDS bounds are read and written”** and later that **“The same exon-block model is read and written for `psl`, `bigpsl`, `bigbed`, `bigmaf`.”** BED12/bigBed and bigPsl carry BED `thickStart`/`thickEnd`; ordinary PSL has block coordinates but no `thickStart`/`thickEnd` fields, while bigMaf is BED3 plus a MAF block and is a multiple-alignment container, not that BED12 transcript/CDS model. [`Bio.Align.bed`](https://github.com/biopython/biopython/blob/biopython-188/Bio/Align/bed.py); [`Bio.Align.psl`](https://github.com/biopython/biopython/blob/biopython-188/Bio/Align/psl.py); [`Bio.Align.bigpsl` declaration](https://github.com/biopython/biopython/blob/biopython-188/Bio/Align/bigpsl.py); [`Bio.Align.bigmaf` BED3+MAF declaration](https://github.com/biopython/biopython/blob/biopython-188/Bio/Align/bigmaf.py).

8. **`CodonAligner` is misattributed split-codon functionality.** The record calls BED/PSL plus `Bio.Align.CodonAligner` **“A second route to the same arithmetic”** as extracting and translating a CDS whose codon spans exons. `CodonAligner` aligns a protein to a nucleotide sequence while allowing frameshifts; it does not interpret BED/PSL exon models, remove introns, or map an edit across an exon-spanning codon. Joined feature extraction is supplied by `SeqFeature`/`CompoundLocation`; codon-aware protein–nucleotide alignment is a separate capability. [`CodonAligner` API](https://biopython.org/docs/latest/api/Bio.Align.html#Bio.Align.CodonAligner); [`SeqFeature.extract` / `translate`](https://biopython.org/docs/latest/api/Bio.SeqFeature.html).

9. **Not every `Bio.Align.formats` entry is writable.** The record claims **“Modern `Bio.Align` genomic file I/O — read *and write* for the full `formats` tuple”** and lists all 20 formats. In 1.88, `emboss`, `hhr`, `msf`, and `tabular` expose readers but no `AlignmentWriter`; passing them to `Bio.Align.write` is not supported. [`Bio.Align` format dispatch](https://github.com/biopython/biopython/blob/biopython-188/Bio/Align/__init__.py); [`emboss`](https://github.com/biopython/biopython/blob/biopython-188/Bio/Align/emboss.py), [`hhr`](https://github.com/biopython/biopython/blob/biopython-188/Bio/Align/hhr.py), [`msf`](https://github.com/biopython/biopython/blob/biopython-188/Bio/Align/msf.py), and [`tabular`](https://github.com/biopython/biopython/blob/biopython-188/Bio/Align/tabular.py) implementations.

10. **The `Bio.SeqIO` read/write list includes read-only formats.** The record says **“~30 `Bio.SeqIO` formats read/write (… SnapGene, GCK, … GFA1/2, `twobit`, …).”** SnapGene, GCK, GFA1/GFA2, and twoBit are read-only in `SeqIO` 1.88 (as are several other registered inputs); the reader and writer registries are deliberately asymmetric. [`Bio.SeqIO` format table and registries](https://github.com/biopython/biopython/blob/biopython-188/Bio/SeqIO/__init__.py).

11. **The linked “latest” documentation was not 1.88 at the audit date.** The sources table labels `https://biopython.org/docs/latest/Tutorial/index.html` **“Tutorial & Cookbook, 1.88,”** but the project's documentation landing page still identified the published latest documentation as **1.87** on 2026-08-14, consistent with the record's later admission that the website lagged the release. The package itself is 1.88; this is a documentation-version error, not a package-version error. [Biopython documentation landing page](https://biopython.org/wiki/Documentation); [PyPI 1.88 release metadata](https://pypi.org/project/biopython/).

### B. INCOMPLETE

1. **Complete sequence-editing and transformation primitives.** The record reduces `MutableSeq` largely to per-position assignment and `SeqRecord` arithmetic, omitting slice assignment/deletion, `insert`, `append`, `extend`, `pop`, `remove`, `replace`, `join`, repetition, RNA complements, back-transcription, and in-place complement/reverse-complement modes. It also omits the important restriction that current `Seq` has no molecule/alphabet validation and will accept biologically nonsensical DNA/protein combinations. [`Bio.Seq` API](https://biopython.org/docs/latest/api/Bio.Seq.html); [sequence-object Tutorial](https://biopython.org/docs/latest/Tutorial/chapter_seq_objects.html). This is material because these are the actual building blocks from which a user can construct variant sets, and the lack of type checking is a correctness hazard.

2. **CDS validation and genetic-code/back-table APIs.** `Seq.translate(..., cds=True)` validates a start, complete codons, one terminal stop, and no internal stops; translation accepts named/numbered/custom NCBI tables, and `SeqFeature.translate` honors `codon_start`/`transl_table`. `Bio.Data.CodonTable` also exposes DNA/RNA/ambiguous alternative codes and a deliberately naive one-codon `back_table`/`make_back_table`. [`Bio.Seq.translate`](https://biopython.org/docs/latest/api/Bio.Seq.html#Bio.Seq.translate); [`Bio.SeqFeature.translate`](https://biopython.org/docs/latest/api/Bio.SeqFeature.html#Bio.SeqFeature.SeqFeature.translate); [`Bio.Data.CodonTable`](https://biopython.org/docs/latest/api/Bio.Data.CodonTable.html). This is material because it separates coding-sequence validation and basic reverse translation from the CAI optimizer the record does discuss.

3. **Multi-pattern and ambiguity-aware motif screening.** `Seq.search` searches many exact subsequences in one pass, while `Bio.SeqUtils.nt_search` interprets IUPAC ambiguity in the query (forward strand only). [`Seq.search`](https://biopython.org/docs/latest/api/Bio.Seq.html#Bio.Seq.Seq.search); [`nt_search`](https://biopython.org/docs/latest/api/Bio.SeqUtils.html#Bio.SeqUtils.nt_search). This is material because forbidden/required motif screening is a direct library-filtering primitive, and its strand/ambiguity limits affect correct use.

4. **Sequence-quality and read-collection modes.** The record names FASTQ cookbook recipes but does not document per-letter qualities or the ABI, `abi-trim` (Mott trimming), PHD, ACE, SFF, FASTQ, and QUAL interfaces in `Bio.SeqIO`/`Bio.Sequencing`. [`Bio.SeqIO` format table](https://biopython.org/docs/latest/api/Bio.SeqIO.html); [`Bio.Sequencing` API](https://biopython.org/docs/latest/api/Bio.Sequencing.html). This is material for validating or processing physically synthesized/assayed sequence collections.

5. **Alignment-collection manipulation beyond coordinate liftover.** The record gives extensive space to file formats and liftover but omits `Alignment` row/column slicing, concatenation, sorting, reverse complement, frequencies, substitution counts/matrices, coordinate indices/inverse indices, counts, and `Alignment.from_alignments_with_same_reference`. [`Bio.Align` API](https://biopython.org/docs/latest/api/Bio.Align.html). These are material operations for comparing, consolidating, and quality-checking variant collections.

6. **Experimental codon-alignment builder and its stability restriction.** `Bio.codonalign.build` constructs a codon alignment from a protein MSA and corresponding nucleotide records, but the whole module raises `BiopythonExperimentalWarning` and may change. [`Bio.codonalign` source/API](https://github.com/biopython/biopython/blob/biopython-188/Bio/codonalign/__init__.py); [experimental-code policy](https://pypi.org/project/biopython/). This is material because it is a collection-construction mode distinct from `CodonAligner`, and its experimental status affects reliance on it.

7. **CAPS variant discrimination.** The record only parenthetically calls `Bio.CAPS` “restriction-site polymorphism detection.” `CAPSMap(alignment, enzymes).dcuts` reports each differential site's position, enzyme, sequences cut, and sequences blocked, requires equal-length aligned variants, and does not design the primers implied by a CAPS assay. [`Bio.CAPS` API](https://biopython.org/docs/latest/api/Bio.CAPS.html). This is material because it directly discriminates members of a sequence-variant set using restriction enzymes.

8. **Current GenePop collection operations.** Beyond a generic `Bio.PopGen` name, current 1.88 can parse and reconstruct GenePop allele collections, stream very large files, split records by population or locus, and remove populations/loci; population names are documented as unreliable and streaming is one-pass. [`Bio.PopGen.GenePop` source](https://github.com/biopython/biopython/tree/biopython-188/Bio/PopGen/GenePop). This is material because it is the actual current variant/genotype collection support left after the paper's FDist/SimCoal modules disappeared.

9. **Bootstrap collection generation.** `Bio.Phylo.Consensus.bootstrap`, `bootstrap_trees`, `bootstrap_consensus`, and `Bio.Nexus.Nexus.bootstrap` generate column-resampled alignment/tree collections; `Bio.Phylo.Consensus.bootstrap` is marked obsolete. [`Bio.Phylo.Consensus`](https://github.com/biopython/biopython/blob/biopython-188/Bio/Phylo/Consensus.py); [`Bio.Nexus.Nexus`](https://github.com/biopython/biopython/blob/biopython-188/Bio/Nexus/Nexus.py). It also does not state that instances must be equal-length, PSSM calculation is DNA-specific, substitution-matrix consensus is unimplemented, and `degenerate_consensus` returns one IUPAC-compressed sequence rather than enumerating it. [motif Tutorial](https://biopython.org/docs/latest/Tutorial/chapter_motifs.html); [`Bio.motifs.matrix`](https://biopython.org/docs/latest/api/Bio.motifs.matrix.html). This is material because these controls determine how candidate libraries can be screened and clarify that a degenerate consensus is not a generated library.

11. **Restriction digest, topology, and cloning-screen modes.** The record mentions site analysis and a few filters but omits enzyme/Batch `.search(linear=True|False)`, `.catalyse`/`.catalyze`, circular-boundary cuts, 5′/3′/blunt overhang classification, compatible ends, iso/equi/neoschizomers, suppliers, and `Analysis` filters by site count and region. It also omits that the bundled database is REBASE release 404 (2024), enzymes with unknown cut positions cannot be digested, and the model does not perform ligation/assembly design or infer sample methylation. ### C. BALANCE

The record correctly and repeatedly establishes that Biopython has no dedicated library-design layer, and it gives exceptional space to modern genomic-coordinate and alignment-format strengths. Overall, however, it is **not balanced for the requested design/library scope**: limitations and absent domain-specific workflows are documented far more deeply and repetitively than the package's many usable construction, screening, collection, and validation primitives. Core editing modes, CDS validation, motif thresholds, restriction digests, CAPS, GenePop, thermodynamic models, protein/DNA descriptors, experimental codon-alignment construction, bootstrap generation, and PIC protein-coordinate construction are missing or compressed into name-only lists. The result fairly rejects Biopython as a turnkey library designer but materially understates what current Biopython can do as infrastructure for building and checking sequence collections.
