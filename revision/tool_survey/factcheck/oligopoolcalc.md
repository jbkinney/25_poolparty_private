“Documented API” below means a current, package-level Python entry point documented in `docs/api.md`; unless noted, the same operation is also a CLI subcommand. “Example-only” means code shipped under `examples/`, not an exported `oligopool` entry point.

#### Degenerate Mode

| Capability | What it does / interface | Surface | Stated restrictions and edge cases | Primary-source evidence |
|---|---|---|---|---|
| Lossless IUPAC compression | `op.compress(...)` groups similar concrete DNA variants into fewer IUPAC-degenerate oligos. It returns a variant-to-degenerate `mapping_df`, an orderable `synthesis_df` with sequence/degeneracy/length, and stats including compression ratio. | Barcode-free selection-library workflow and back-mapping | The mapping table lets a user synthesize fewer degenerate oligos, run a selection, sequence surviving concrete sequences, and map them back to original variant IDs without a designed barcode readout. | Documented workflow/recipe, powered by `compress`. | Best when mutations are localized and selection (not per-variant quantitative barcoding) identifies survivors. Highly dispersed diversity compresses poorly. | [Degenerate Mode workflow](https://github.com/ayaanhossain/oligopool/blob/b88fa394ca67ed4c48ec41127b5707694ee7cf0a/docs/docs.md#L889-L903); [selection recipe](https://github.com/ayaanhossain/oligopool/blob/b88fa394ca67ed4c48ec41127b5707694ee7cf0a/docs/docs.md#L2369-L2388) |
| Expand degenerate sequences | `op.expand(...)` enumerates every concrete A/T/G/C sequence represented by IUPAC input, optionally using the `compress` mapping to retain/restore mapping identifiers. Without the mapping table, it cannot infer original variant IDs. | [expand API lines 834–874](https://github.com/ayaanhossain/oligopool/blob/b88fa394ca67ed4c48ec41127b5707694ee7cf0a/docs/api.md#L834-L874) |

| Capability | What it does / interface | Surface | Stated restrictions and edge cases | Primary-source evidence |
|---|---|---|---|---|

### Paper-era versus current-software boundary

The 2024 paper presents Design Mode (`barcode`, `primer`, motifs/spacers, `split`, `pad`) and Analysis Mode (index, pack, association/combinatorial count, Scry), with large-scale benchmarks. It does **not** describe the later Degenerate Mode, `join`, the current expanded QC/inspection behavior, cross-set/per-group/patch workflows as presently documented, or YAML/DAG CLI orchestration. Git history/changelog dates `compress`/`expand` to 2026-01-26, YAML pipelines to 2026-01-31, `inspect` to 2026-02-09, and `join` to 2026-02-14/15. Conversely, two paper descriptions are broader/different than current contracts: paper primer matching gives an example difference below 0.3 °C while current paired-primer matching is within 1 °C; and the paper describes callbacks that tally arbitrary properties, while the current callback contract is Boolean filtering only. These distinctions are part of the frozen yardstick, not yet judgments about the survey record.

Evidence: [paper pp. 4219–4230 (PDF pp. 2–13)](../papers/Hossain2024_OligopoolCalculator.pdf); [current API table of contents](https://github.com/ayaanhossain/oligopool/blob/b88fa394ca67ed4c48ec41127b5707694ee7cf0a/docs/api.md#L14-L56); [2026 changelog](https://github.com/ayaanhossain/oligopool/blob/b88fa394ca67ed4c48ec41127b5707694ee7cf0a/CHANGELOG.md#L69-L79).

## Phase 2 — comparison with the survey record

### A. FACTUALLY WRONG

1. **Wrong paper title.** The record cites *“Automated Design of Thousands of Nonrepetitive Parts for Engineering Stable Genetic Systems”* as the Oligopool Calculator paper (line 6). The actual article is *“Automated Design of Oligopools and Rapid Analysis of Massively Parallel Barcoded Measurements.”* The quoted title belongs to a different Salis-lab article. [Paper first page](../papers/Hossain2024_OligopoolCalculator.pdf); [publisher metadata in the repository README](https://github.com/ayaanhossain/oligopool/blob/b88fa394ca67ed4c48ec41127b5707694ee7cf0a/README.md#L311-L318).

2. **Rows are not always preserved.** The record says, *“An Oligopool Calculator library is therefore always exactly the rows the user supplied”* (line 66). `join` and the ordinary column-wise design operations preserve the ID set, but `compress` creates a new `synthesis_df` with one row per compressed degenerate oligo and `expand` creates one row per concrete expansion; either can change the row count. The narrower claim that there is no general row-union operator is supported, but the stated conclusion is false. [`compress` return contract](https://github.com/ayaanhossain/oligopool/blob/b88fa394ca67ed4c48ec41127b5707694ee7cf0a/docs/api.md#L782-L820); [`expand` return contract](https://github.com/ayaanhossain/oligopool/blob/b88fa394ca67ed4c48ec41127b5707694ee7cf0a/docs/api.md#L825-L874).

3. **Not all 22 modules return DataFrames/CSVs.** The record says, *“All 22 modules return materialized DataFrames/CSVs”* (line 106). `background`, `lenstat`, `index`, and `pack` return statistics rather than a design DataFrame; `inspect` returns an inspection result/stats; `vectorDB` and `Scry` expose stateful objects. This does not make the design pipeline lazy, but it falsifies the evidence used for that conclusion. [API table of contents and return contracts](https://github.com/ayaanhossain/oligopool/blob/b88fa394ca67ed4c48ec41127b5707694ee7cf0a/docs/api.md#L14-L56); [`vectorDB` and `Scry`](https://github.com/ayaanhossain/oligopool/blob/b88fa394ca67ed4c48ec41127b5707694ee7cf0a/docs/api.md#L1517-L1607).

4. **`ID` is not a required user input to every module.** The record says, *“The `ID` column is a required user input on every module”* (line 133). It is central to tabular library-design inputs, but not to every module: for example, `background` accepts sequence collections/FASTA, `pack` accepts FASTQ reads, `inspect` accepts an artifact target, and the advanced constructors are not DataFrame modules at all. [Background input contract](https://github.com/ayaanhossain/oligopool/blob/b88fa394ca67ed4c48ec41127b5707694ee7cf0a/docs/api.md#L360-L399); [`pack` inputs](https://github.com/ayaanhossain/oligopool/blob/b88fa394ca67ed4c48ec41127b5707694ee7cf0a/docs/api.md#L969-L1041); [`inspect`](https://github.com/ayaanhossain/oligopool/blob/b88fa394ca67ed4c48ec41127b5707694ee7cf0a/docs/api.md#L1464-L1512).

5. **The synthesis-limit and assembly descriptions are overbroad/wrong.** The record states, *“`oligo_length_limit` is a required parameter on every design module”* and describes `pad` as providing *“Type IIS pads for scarless Golden Gate”* (lines 183 and 242). `oligo_length_limit` is required by generative design calls such as `barcode`, `primer`, `motif`, and `spacer`, but not by all nine Design Mode operations (`background`, `merge`, `revcomp`, and `final` do not take it). More importantly, the documentation explicitly says the Type IIS enzyme is used to **remove primer pads**, not to ligate fragments to one another; fragments are assembled through the overlaps designed by `split`. [Design-mode signatures](https://github.com/ayaanhossain/oligopool/blob/b88fa394ca67ed4c48ec41127b5707694ee7cf0a/docs/api.md#L58-L616); [pad-removal versus assembly clarification](https://github.com/ayaanhossain/oligopool/blob/b88fa394ca67ed4c48ec41127b5707694ee7cf0a/docs/docs.md#L872-L878).

6. **The 6.8-second benchmark is misidentified.** The record says, *“Verify/design step for 93,180 oligos took 6.8 s”* (line 213). Table S1 reports 6.8 seconds specifically for **designing the spacer regions** of the 93,180-member promoter library, not for verifying or designing the complete oligos. [Paper Table S1 and surrounding text, PDF pp. 6 and 14](../papers/Hossain2024_OligopoolCalculator.pdf).

7. **Current Analysis Mode is credited with outputs it does not expose.** The unqualified summary claims *“index-hopping detection and mismatch-distribution reporting”* (line 239). Those are discussed in the paper-era application, but the current `xcount` API reports observed barcode combinations (including partial tuples marked `'-'`) and does not classify or remove index-hopped combinations. The current `acount`/`xcount` output and stats schemas likewise contain counts and failure diagnostics, not a barcode edit-distance/mismatch distribution. A user could perform such analyses downstream, but they are not current documented built-ins. [`xcount` behavior and partial combinations](https://github.com/ayaanhossain/oligopool/blob/b88fa394ca67ed4c48ec41127b5707694ee7cf0a/docs/docs.md#L1134-L1151); [`acount` output schema](https://github.com/ayaanhossain/oligopool/blob/b88fa394ca67ed4c48ec41127b5707694ee7cf0a/docs/api.md#L1094-L1124); [`xcount` output schema](https://github.com/ayaanhossain/oligopool/blob/b88fa394ca67ed4c48ec41127b5707694ee7cf0a/docs/api.md#L1218-L1247); [paper Analysis Mode, PDF pp. 3 and 9–10](../papers/Hossain2024_OligopoolCalculator.pdf).

8. **Three paper/current-software disagreements are presented without being flagged.** The record treats paper and current behavior as one account, but:

   - The paper's paired-primer example uses a melting-temperature difference below 0.3 °C, whereas the current API guarantees matching within 1 °C.
   - The paper states primer lengths are 15–22 nt (`14 < L < 23`); the current implementation enforces a 15-nt minimum but no 22-nt maximum.
   - The paper describes callbacks as capable of tallying arbitrary properties/dictionaries; the current `acount`/`xcount` callback contract is only a Boolean accept/reject filter (`True` or `False`).

   These are not merely omitted enhancements: the paper and current release differ, and the record does not qualify the differences. [Current paired-primer contract](https://github.com/ayaanhossain/oligopool/blob/b88fa394ca67ed4c48ec41127b5707694ee7cf0a/docs/api.md#L156-L207); [current minimum-length validation](https://github.com/ayaanhossain/oligopool/blob/b88fa394ca67ed4c48ec41127b5707694ee7cf0a/oligopool/primer.py#L153-L174); [current callback contract](https://github.com/ayaanhossain/oligopool/blob/b88fa394ca67ed4c48ec41127b5707694ee7cf0a/docs/api.md#L1147-L1165); [paper Design/Analysis descriptions, PDF pp. 6 and 9](../papers/Hossain2024_OligopoolCalculator.pdf).

9. **The example parser does not perform a general topological sort.** The record twice says `get_primer_order()` *“topologically resolves the paired-primer dependency graph”* (lines 220 and 246). This is example-only code implementing a short deque insertion heuristic: it has no graph construction, topological-sort algorithm, or cycle detection. It can order the example's primer dependencies, but the stronger implementation claim is false. [`get_primer_order` source](https://github.com/ayaanhossain/oligopool/blob/b88fa394ca67ed4c48ec41127b5707694ee7cf0a/examples/design-assembly-parser/design_assembly_parser.py#L217-L236).

10. **Minor source-tree inventory details are wrong.** The claim that there are *“All 40 `oligopool/**/*.py` files”* (line 140) is off by one at the cited release: the package tree contains 41 Python files. The same passage cites `oligopool/core_lenstat.py`, but the file is actually `oligopool/base/core_lenstat.py`. [Pinned package tree](https://github.com/ayaanhossain/oligopool/tree/b88fa394ca67ed4c48ec41127b5707694ee7cf0a/oligopool); [`core_lenstat.py`](https://github.com/ayaanhossain/oligopool/blob/b88fa394ca67ed4c48ec41127b5707694ee7cf0a/oligopool/base/core_lenstat.py).

[API](https://github.com/ayaanhossain/oligopool/blob/b88fa394ca67ed4c48ec41127b5707694ee7cf0a/docs/api.md#L762-L820). ### C. BALANCE

Ignoring its comparisons and evaluative rhetoric, the record gives Oligopool Calculator's strengths substantial and generally proportionate space: it inventories all 22 current modules, separates current software from example-only mutant generation in several places, and devotes a long section to capabilities beyond the survey matrix. It also documents limitations in depth, but not more deeply than capabilities overall. The representation is therefore broadly balanced rather than systematically understating the tool; its principal problems are discrete factual overclaims, a few paper/current-release conflations, and missing lower-level modes and restrictions.
