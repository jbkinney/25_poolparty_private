# Ledidi fact-check

## Phase 1 inventory (frozen before opening the survey record)

Snapshot date: 2026-08-14. I treated the PyPI artifact as the current released software and separately marked functionality present only on the repository's default branch. This distinction matters: the newest PyPI release is 2.1.0, while the repository's release notes call the additional default-branch work “Version 2.2.0 (unreleased).” The public Read the Docs banner still says v2.0.0 and is also stale. This inventory was saved before the Phase 2 record was opened and was not subsequently revised.

### Identity, availability, installation, and maintenance

- **Current released version and date:** **2.1.0, released 2025-04-24**. PyPI labels it the latest release and gives that date; the package's `__version__` is also 2.1.0. Evidence: [PyPI project page, lines 23–31 and 91–101](https://pypi.org/project/ledidi/); [release commit, `ledidi/__init__.py`](https://github.com/jmschrei/ledidi/blob/7adfcd6/ledidi/__init__.py); [current default-branch `__init__.py`, line 4](https://github.com/jmschrei/ledidi/blob/adbca708d45340fb7f375e4d0e2438d3cfa7c852/ledidi/__init__.py#L4). The default branch contains later work described as **2.2.0 (unreleased)**, not a newer installable release: [release history, lines 9–37](https://github.com/jmschrei/ledidi/blob/adbca708d45340fb7f375e4d0e2438d3cfa7c852/docs/whats_new.rst#L9-L37).
- **License:** the repository and the license file embedded in the 2.1.0 wheel are **Apache License 2.0**. Evidence: [repository `LICENSE`](https://github.com/jmschrei/ledidi/blob/adbca708d45340fb7f375e4d0e2438d3cfa7c852/LICENSE) and [README, lines 289–291](https://github.com/jmschrei/ledidi/blob/adbca708d45340fb7f375e4d0e2438d3cfa7c852/README.md#L289-L291). PyPI's unverified metadata says “MIT License,” but the same wheel contains the Apache-2.0 license text; therefore the PyPI metadata label is stale/wrong, not a second license. Evidence for the conflicting label: [PyPI, lines 47–57 and 79–90](https://pypi.org/project/ledidi/).
- **Installation:** released installation is `pip install ledidi`. Development installation is `git clone …`, then `uv pip install -e ".[dev]"`; tests run with `python -m pytest tests/`. Evidence: [README, lines 29–42](https://github.com/jmschrei/ledidi/blob/adbca708d45340fb7f375e4d0e2438d3cfa7c852/README.md#L29-L42). The released 2.1.0 wheel declares PyTorch >=1.9 and matplotlib; current unreleased source raises the floor to Python >=3.10 and PyTorch >=2.0 and adds NumPy and tangermeme >=1.3.0. Evidence: [current `pyproject.toml`, lines 5–28](https://github.com/jmschrei/ledidi/blob/adbca708d45340fb7f375e4d0e2438d3cfa7c852/pyproject.toml#L5-L28) and [unreleased release notes, lines 24–37](https://github.com/jmschrei/ledidi/blob/adbca708d45340fb7f375e4d0e2438d3cfa7c852/docs/whats_new.rst#L24-L37).
- **Maintenance:** **actively maintained.** The repository explicitly calls itself research software under active development, and its latest commit at the snapshot was 2026-06-23, with multiple documentation, validation, CI, test, and plotting changes in June 2026. Evidence: [README roadmap, lines 250–270](https://github.com/jmschrei/ledidi/blob/adbca708d45340fb7f375e4d0e2438d3cfa7c852/README.md#L250-L270); [2026-06-23 commit](https://github.com/jmschrei/ledidi/commit/adbca708d45340fb7f375e4d0e2438d3cfa7c852). The gap since the last PyPI upload does not mean the repository is dormant.
- **Interface/packaging:** it is a Python/PyTorch library, not a standalone web application or command-line designer. The installed top-level package exports `ledidi` and `Ledidi`; `losses`, `wrappers`, `pruning`, and `plot` are importable submodules. A command-line pipeline is only a roadmap item. Evidence: [package exports](https://github.com/jmschrei/ledidi/blob/adbca708d45340fb7f375e4d0e2438d3cfa7c852/ledidi/__init__.py#L4-L7), [README, lines 188–219](https://github.com/jmschrei/ledidi/blob/adbca708d45340fb7f375e4d0e2438d3cfa7c852/README.md#L188-L219), and [roadmap, lines 258–268](https://github.com/jmschrei/ledidi/blob/adbca708d45340fb7f375e4d0e2438d3cfa7c852/README.md#L258-L268).

### Important negative boundaries

- **No insertions/deletions or variable-length design:** current representation produces substitutions in a fixed-length tensor; indels are a roadmap item. [README, lines 262–264](https://github.com/jmschrei/ledidi/blob/adbca708d45340fb7f375e4d0e2438d3cfa7c852/README.md#L262-L264)
- **No first-class global biological-constraint system:** GC content, restriction sites, codon usage, and absence of off-target effects are listed as future multi-objective/constraint work. A user may sometimes approximate them with masks, `initial_weights`, an oracle, or a custom differentiable loss, but there is no packaged constraint language or solver. [README, lines 260–266](https://github.com/jmschrei/ledidi/blob/adbca708d45340fb7f375e4d0e2438d3cfa7c852/README.md#L260-L266)
- **No bundled end-to-end library pipeline:** Ledidi returns tensors. FASTA/locus handling, encoding/decoding, attributions, motif scans, experimental-feasibility logic, oligo construction, and variant/sequence-file export are user or third-party responsibilities. [README, lines 80–104 and 256–268](https://github.com/jmschrei/ledidi/blob/adbca708d45340fb7f375e4d0e2438d3cfa7c852/README.md#L80-L104)
- **No guarantee that one sampled batch is diverse:** members of a batch share one fitted weight matrix and are correlated. `n_samples` gives a large pool around that solution; `n_repeats` or separately seeded fits are needed for distinct solution families. [README, lines 146–150](https://github.com/jmschrei/ledidi/blob/adbca708d45340fb7f375e4d0e2438d3cfa7c852/README.md#L146-L150)
- **No built-in trust guarantee:** an oracle can be exploited, and the method can generate out-of-distribution or biologically meaningless designs. Independent validation is recommended, not enforced. [README, lines 252–258](https://github.com/jmschrei/ledidi/blob/adbca708d45340fb7f375e4d0e2438d3cfa7c852/README.md#L252-L258); [paper, pp. 29–30](/mnt/c/Users/zhliu/Desktop/KinneyLab/25_poolparty_private/revision/tool_survey/papers/Schreiber2025_ledidi.pdf)

## A. FACTUALLY WRONG

1. **“No codon-aware or amino-acid-level mutagenesis”** is too broad. Ledidi has no codon-aware DMS enumerator, reading-frame logic, or documented protein example, but its released core explicitly edits categorical sequences “comprised of nucleotides or amino acids,” and the README says it applies out of the box to protein models. With a compatible differentiable protein oracle, it therefore can make oracle-guided amino-acid substitutions. Evidence: [released `Ledidi` documentation, lines 182–208](https://github.com/jmschrei/ledidi/blob/7adfcd6453a6851e2145bec328d5063bd19f4c4f/ledidi/ledidi.py#L182-L208); [README, line 27](https://github.com/jmschrei/ledidi/blob/adbca708d45340fb7f375e4d0e2438d3cfa7c852/README.md#L27).

2. **“It renders one design run at a time”** is false of `plot_edits`. The function has no run identity or one-run check: `X_attrs` can be an arbitrary `(n, 4, length)` tensor or a list, and lists are concatenated before all sequences are drawn as stacked tracks. Its real restrictions are a common reference/length, user-supplied attributions, and—on release 2.1.0—a hard-coded DNA alphabet. Evidence: [released `plot_edits`, lines 44–105](https://github.com/jmschrei/ledidi/blob/7adfcd6453a6851e2145bec328d5063bd19f4c4f/ledidi/plot.py#L44-L105).

3. **“Documented design-validation recipe as a capability, not just an example”** misattributes tutorial workflow to Ledidi. Tutorial 7 is an example/recommendation built from user/external attribution, motif-scanning, and held-out-oracle code; Ledidi exposes no validation API. The project explicitly lists first-class evaluation as future work. Evidence: [validation tutorial](https://github.com/jmschrei/ledidi/blob/adbca708d45340fb7f375e4d0e2438d3cfa7c852/docs/tutorials/Tutorial_7_-_Validating_Your_Designs.ipynb); [README roadmap, lines 252–258](https://github.com/jmschrei/ledidi/blob/adbca708d45340fb7f375e4d0e2438d3cfa7c852/README.md#L252-L258).

## B. INCOMPLETE

1. **Custom input-loss hook.** The record names `input_loss` only in a signature and then treats the input term as fixed edit counting. Released `Ledidi` lets callers replace the L1 input-space loss as well as the output loss. This is material because users can redefine which sequence changes are costly rather than only tuning the scalar `l`. Evidence: [released API, lines 215–224 and 276–280](https://github.com/jmschrei/ledidi/blob/7adfcd6453a6851e2145bec328d5063bd19f4c4f/ledidi/ledidi.py#L215-L224).

2. **Oracle-adapter recipes and receptive-field hazard.** Tutorial 4 shows user-written wrappers that select/reduce outputs, add fixed inputs, permute channels, and crop a common long sequence for models with different input widths; `DesignWrapper` itself only concatenates outputs that match in every dimension except the last. This is material because a cropped oracle cannot see or constrain flanking edits, allowing the optimizer to hide unwanted features there unless those regions are masked. Evidence: [current `DesignWrapper`, lines 23–33](https://github.com/jmschrei/ledidi/blob/adbca708d45340fb7f375e4d0e2438d3cfa7c852/ledidi/wrappers.py#L23-L33); [Multiple Models tutorial, adapter and receptive-field examples](https://github.com/jmschrei/ledidi/blob/adbca708d45340fb7f375e4d0e2438d3cfa7c852/docs/tutorials/Tutorial_4_-_Multiple_Models.ipynb).

3. **Soft-prior non-persistence.** The record notes graded `initial_weights` but omits the tutorial's warning that optimization can undo even a large finite prior. This is material because a prior is an initialization bias, not a guaranteed library constraint. Evidence: [Constraints and Priors tutorial, “Priors” section](https://github.com/jmschrei/ledidi/blob/adbca708d45340fb7f375e4d0e2438d3cfa7c852/docs/tutorials/Tutorial_2_-_Constraints_and_Priors.ipynb); [input/output documentation, lines 59–65](https://github.com/jmschrei/ledidi/blob/adbca708d45340fb7f375e4d0e2438d3cfa7c852/docs/input_output.rst#L59-L65).

4. **In-painting is preferential, not exclusive.** The record says zeroed spans are free but omits that Ledidi may still edit outside them unless those positions are masked, and that every all-zero/`N` column is a fillable position that will not be preserved. This is material when a requested library must confine variation to a declared window. Evidence: [input/output documentation, lines 14–18](https://github.com/jmschrei/ledidi/blob/adbca708d45340fb7f375e4d0e2438d3cfa7c852/docs/input_output.rst#L14-L18); [released loss masking, lines 386–414](https://github.com/jmschrei/ledidi/blob/7adfcd6453a6851e2145bec328d5063bd19f4c4f/ledidi/ledidi.py#L386-L414).

5. **`MinGap` semantics and failure modes.** The record names `MinGap` but does not explain that it ignores `y_bar`, optimizes only relative separation between the weakest on-target and strongest off-target output, requires comparable output scales, and can stall if one on-target is unoptimizable or an off-target is correlated. This is material because the loss does not guarantee high absolute activity and can behave very differently from target matching. Evidence: [current `MinGap`, lines 23–94](https://github.com/jmschrei/ledidi/blob/adbca708d45340fb7f375e4d0e2438d3cfa7c852/ledidi/losses.py#L23-L94); [Custom Loss Functions tutorial](https://github.com/jmschrei/ledidi/blob/adbca708d45340fb7f375e4d0e2438d3cfa7c852/docs/tutorials/Tutorial_6_-_Custom_Loss_Functions.ipynb).

This is material for library-scale use and for interpreting a pruning threshold. Evidence: [released pruning API and implementation, lines 7–18 and 54–96](https://github.com/jmschrei/ledidi/blob/7adfcd6453a6851e2145bec328d5063bd19f4c4f/ledidi/pruning.py#L7-L18).

This is material because the core designer's protein/RNA alphabet generality does not extend to that released visualization helper. Evidence: [released plotting source, lines 57–64 and 81–105](https://github.com/jmschrei/ledidi/blob/7adfcd6453a6851e2145bec328d5063bd19f4c4f/ledidi/plot.py#L57-L64).

## C. BALANCE

Yes—overall, the record is balanced. Its row-oriented middle is necessarily limitation-heavy, but it gives substantial, proportionate space to Ledidi's central strengths: oracle-in-the-loop minimal editing, many samples and repeated fits, affinity catalogs, masks and edit-type constraints, forced/relocated motifs, in-painting, custom objectives, multi-model design, pruning, and the paper's case studies. The factual understatements above (especially amino-acid editing and existing edit constraints) and the omitted operational restrictions matter, but they do not make the record as a whole systematically capability-heavy or limitation-heavy.
