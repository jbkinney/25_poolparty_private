# pydna fact-check

## Phase 1 inventory (frozen before the survey record was opened)

**Freeze point:** 2026-08-14. This inventory was completed and saved before reading the survey record. It is not revised below; Phase 2 findings are appended after it.

### Source/version baseline

- The version baseline for current released behavior is the official `v5.5.16` tag (commit [`7b718ac`](https://github.com/pydna-group/pydna/commit/7b718accc7439f75fa2372bdef41464fb5ef79a8)). PyPI identifies **5.5.16** as the latest stable release and dates its uploaded wheel and source archive **2026-06-09** ([PyPI project metadata and release files](https://pypi.org/project/pydna/)).
- The repository's `master` branch is ahead of that release: at the freeze point its head was commit [`4e02f81`](https://github.com/pydna-group/pydna/commit/4e02f81dfd39629c68d2a93dfbb434bfe7d56120), dated **2026-08-01**, and its project version was the prerelease `6.0.0-a.24.post.17+b7b559bd66` ([`pyproject.toml`, lines 29–41](https://github.com/pydna-group/pydna/blob/4e02f81dfd39629c68d2a93dfbb434bfe7d56120/pyproject.toml#L29-L41)). The official documentation site is built from this development line, so its displayed 6.0.0 alpha version is not the latest stable PyPI release.
- The project is **actively maintained**: it had a stable release on 2026-06-09 and a repository commit on 2026-08-01, with many other 2025–2026 releases visible in PyPI's release history. This is stronger evidence than an undated activity badge.
- The current package metadata says **BSD** and the bundled license is the three-clause BSD form: redistribution in source/binary form is allowed, modification is allowed, and the third clause prohibits endorsement using the organizations' or contributors' names ([`LICENSE.txt`, lines 1–31](https://github.com/pydna-group/pydna/blob/v5.5.16/LICENSE.txt#L1-L31); [`pyproject.toml`, lines 6–18 and 29–40](https://github.com/pydna-group/pydna/blob/v5.5.16/pyproject.toml#L6-L40)). There is no non-academic-use restriction.
- Current installation is from PyPI. The repository instructs `pip install --pre --upgrade pydna` (the `--pre` deliberately permits prereleases), or `poetry add pydna`; extras can be requested in brackets ([README, lines 288–384](https://github.com/pydna-group/pydna/blob/v5.5.16/README.md#L288-L384)). The stable package requires Python `>=3.10,<4.0` and defines the optional extras `clipboard`, `download`, `express`, `gel`, and `primer_screen` ([`pyproject.toml`, lines 42–74](https://github.com/pydna-group/pydna/blob/v5.5.16/pyproject.toml#L42-L74)). The README's all-extras example omits `primer_screen`, although the package metadata exposes it.
- The 2015 paper is historical evidence, not the current API contract. It describes a Python 2.7-era release, the historical `assembly_primers` and `Assembly.linear_products`/`circular_products` interfaces, and calls the license “FreeBSD” (Pereira et al. 2015, pp. 3–4 and 8–9). Current releases require Python 3.10+, use `assembly_fragments` and the `assembly2` interfaces below, and label the license BSD.

### Capability inventory

The status label in every item distinguishes first-party documented API from capabilities that only appear in example code. “Generated API” means a public module/function included by the official documentation build's `sphinx-apidoc`; it is still documented first-party API even when it lacks a tutorial.

1. **Represent annotated, linear or circular double-stranded DNA and its physical ends.** `pydna.dseq.Dseq` models Watson/Crick strands, offsets, blunt/sticky/single-stranded ends and topology; `pydna.dseqrecord.Dseqrecord` adds names, annotations and Biopython `SeqFeature`s. Sequence slicing, reverse complementing, origin shifting, concatenating/repeating, circularizing and linearizing produce sequence records and generally transform retained features with them. **Status:** central documented API with introductory notebooks, not example-only. **Restrictions:** circular molecules cannot simply be multiplied or ligated as linear records, ligation/circularization checks end compatibility, and some origin-spanning feature edge cases are explicitly called out in source. **Evidence:** [README, lines 43–53 and 264–285](https://github.com/pydna-group/pydna/blob/v5.5.16/README.md#L43-L53); [`Dseq` implementation](https://github.com/pydna-group/pydna/blob/v5.5.16/src/pydna/dseq.py#L190); [`Dseqrecord` implementation](https://github.com/pydna-group/pydna/blob/v5.5.16/src/pydna/dseqrecord.py#L56).

2. **Import a collection of DNA/primer records and export designed products.** `pydna.parsers.parse` accepts path-like inputs, raw text or iterables, extracts all records from FASTA, GenBank and EMBL (including mixed text), and returns a list; `parse_primers` makes `Primer` objects, `read`/`read_primer` demand one record, and `parse_snapgene` reads SnapGene `.dna`. `Dseqrecord.format`/`write` exports through Biopython formats, and optional clipboard methods copy FASTA/GenBank. **Status:** documented API and Importing Sequences tutorial. **Restrictions:** `parse` handles DNA, not protein records; automatic path/format guessing can make malformed inputs surprising; SnapGene uses a separate parser; clipboard support needs the `clipboard` extra. **Evidence:** [`parse`, `parse_primers`, `parse_snapgene`](https://github.com/pydna-group/pydna/blob/v5.5.16/src/pydna/parsers.py#L190-L327); [Importing Sequences notebook](https://github.com/pydna-group/pydna/blob/v5.5.16/docs/notebooks/Importing_Seqs.ipynb); [README optional dependencies, lines 301–326](https://github.com/pydna-group/pydna/blob/v5.5.16/README.md#L301-L326).

3. **Retrieve or identify sequence records through NCBI.** `pydna.genbank.Genbank.nucleotide`/`pydna.genbank.genbank` downloads an accession, optionally an interval and strand, into a `Dseqrecord`; `pydna.sequence_picker.genbank_accession` sends an arbitrary DNA query to NCBI BLASTN/megablast and returns the top subject region as a record. **Status:** both are generated documented APIs; direct GenBank download is also in the README/paper, while BLAST-based picking has no tutorial. **Restrictions:** both are network-dependent; NCBI download requires a valid e-mail; the picker returns a top match, not a library search or sequence design. **Evidence:** [`genbank.py`, lines 27–200](https://github.com/pydna-group/pydna/blob/v5.5.16/src/pydna/genbank.py#L27-L200); [`sequence_picker.py`, lines 19–68](https://github.com/pydna-group/pydna/blob/v5.5.16/src/pydna/sequence_picker.py#L19-L68); [README example, lines 266–285](https://github.com/pydna-group/pydna/blob/v5.5.16/README.md#L266-L285).

4. **Create, preserve, extract and translate annotated features.** `Dseqrecord.add_feature`, record slicing/extraction and cut/assembly operations retain compatible features; a CDS feature can be extracted and translated to `ProteinSeq`/`ProteinSeqRecord`, including compound/spliced locations. `orfs` and `orfs_to_features` find ORFs and turn them into annotations. **Status:** documented API and Dseq Features tutorial. **Restrictions:** feature preservation is a sequence-coordinate operation; it does not biologically infer arbitrary new feature annotations. **Evidence:** [Dseq Features notebook](https://github.com/pydna-group/pydna/blob/v5.5.16/docs/notebooks/Dseq_Features.ipynb); [`Dseqrecord.add_feature` and ORF methods](https://github.com/pydna-group/pydna/blob/v5.5.16/src/pydna/dseqrecord.py#L56); Pereira et al. (2015), pp. 2–3.

5. **Generate synthetic random DNA, RNA, ORFs and proteins.** `pydna.utils.randomDNA`, `randomRNA`, `randomORF`, and `randomprot` generate individual random sequences; giving `maxlength` causes a triangularly selected length, and `randomORF` creates an ATG-started, non-stop internal coding region with a random stop codon. These functions can be called repeatedly from Python to make collections. **Status:** generated documented API, not merely example code, but not highlighted in the main capability list. **Restrictions:** there is no built-in library design objective, diversity constraint or per-call seed; these are random generators, not codon optimization or reverse translation. **Evidence:** [`utils.py`, lines 445–544](https://github.com/pydna-group/pydna/blob/v5.5.16/src/pydna/utils.py#L445-L544).

6. **Translate DNA and inspect protein/coding-sequence properties.** `pydna.seq.Seq.translate` returns `ProteinSeq`; `ProteinSeq`/`ProteinSeqRecord` support ordinary Biopython protein sequences and protein analyses, while DNA methods report GC, ORFs, rare codons, start/stop quality and an `express` table (CAI, GC, terminal residue and rare-codon counts). **Status:** generated documented API; translation is demonstrated in the feature tutorial. **Restrictions:** the only bundled organism tables are limited (not a general host-design database); CAI needs the `express` extra; the standalone `pydna.utils.express` is explicitly `NotImplemented`; there is no current core reverse translation, codon optimization, amino-acid substitution library design or protein fitness scoring. **Evidence:** [`seq.py`, lines 125–221](https://github.com/pydna-group/pydna/blob/v5.5.16/src/pydna/seq.py#L125-L221); [`proteinseq.py`](https://github.com/pydna-group/pydna/blob/v5.5.16/src/pydna/proteinseq.py); [`utils.py`, lines 226–275](https://github.com/pydna-group/pydna/blob/v5.5.16/src/pydna/utils.py#L226-L275); [`express` extra](https://github.com/pydna-group/pydna/blob/v5.5.16/pyproject.toml#L69-L74).

7. **Compare, canonicalize and deduplicate collections of sequence designs.** `pydna.utils.eq` compares multiple DNA sequences while optionally treating reverse complements and circular rotations as equal; `deduplicate` removes repeated items; sequence records expose SEGUID/related checksums suitable for stable identity. **Status:** generated documented utility/record API, with no dedicated tutorial. **Restrictions:** equality/deduplication is structural sequence identity, not functional-equivalence or diversity analysis. **Evidence:** [`utils.eq` and `deduplicate`](https://github.com/pydna-group/pydna/blob/v5.5.16/src/pydna/utils.py#L546-L614); [`utils.py`, lines 991–1012](https://github.com/pydna-group/pydna/blob/v5.5.16/src/pydna/utils.py#L991-L1012); [`Dseqrecord` checksum methods](https://github.com/pydna-group/pydna/blob/v5.5.16/src/pydna/dseqrecord.py).

8. **Design PCR primers for a target sequence.** `pydna.design.primer_design(template, fp=None, rp=None, limit=13, target_tm=55, tm_func=..., estimate_function=...)` designs both primers or the missing mate to a supplied primer, targeting melting temperature and returning an `Amplicon` carrying primers and template. Custom Tm/length-estimation functions are accepted. **Status:** prominent documented API, README example and primer/PCR tutorials. **Restrictions:** supplying both primers is rejected (use `pcr` to simulate them); sequence design is endpoint primer design, not a multiplex/library optimizer; it warns when the designed annealing sequence is non-unique. **Evidence:** [`design.primer_design`, lines 74–247](https://github.com/pydna-group/pydna/blob/v5.5.16/src/pydna/design.py#L74-L247); [README example, lines 85–118](https://github.com/pydna-group/pydna/blob/v5.5.16/README.md#L85-L118); [primer-design notebook](https://github.com/pydna-group/pydna/blob/v5.5.16/docs/notebooks/primer_design.ipynb).

9. **Screen a large existing primer collection against one or several sequence variants.** The optional `pydna.primer_screen` module builds/reuses an Aho–Corasick automaton and exposes `forward_primers`, `reverse_primers`, `primer_pairs`, `flanking_primer_pairs`, `diff_primer_pairs`, and `diff_primer_triplets`. It reports binding sites, valid amplicon-size pairs, primers flanking a target, and pairs/triplets whose band sizes distinguish sequence variants; extended IUPAC DNA symbols (and U) are expanded. **Status:** documented first-party example notebook plus generated API, not a third-party example. **Restrictions:** it emits a warning that the module is experimental, not extensively tested and may change; it requires the `primer_screen`/`pyahocorasick` extra; pair routines use primers with unique binding sites; the default diagnostic rule requires a roughly 20% band-size separation; automata index a 3′ suffix (default 16), and highly degenerate IUPAC primers can expand combinatorially. **Evidence:** [primer-screen notebook, introduction and API](https://github.com/pydna-group/pydna/blob/v5.5.16/docs/notebooks/Example_primer_screen.ipynb); [`primer_screen.py`, lines 141–855](https://github.com/pydna-group/pydna/blob/v5.5.16/src/pydna/primer_screen.py#L141-L855); [`primer_screen` extra](https://github.com/pydna-group/pydna/blob/v5.5.16/pyproject.toml#L69-L74).

10. **Simulate PCR, including tailed primers and inverse PCR.** `pydna.amplify.Anneal` locates all forward/reverse primer sites and enumerates products; `pydna.amplify.pcr` is the convenience interface and returns one `Amplicon`. An `Amplicon` records primer/template provenance, Tm/GC information, ASCII binding figures and suggested polymerase-specific PCR programs. Fully contained GenBank features are retained. **Status:** prominent documented API and PCR tutorial; also central in the paper. **Restrictions:** annealing requires a perfectly matching 3′ suffix of at least `limit` bases (arbitrary 5′ tails are allowed); `pcr` raises unless exactly one product is found, whereas `Anneal.products` exposes multiple possibilities; this is sequence-level simulation, not kinetic yield prediction. **Evidence:** [`amplify.py`, lines 34–498](https://github.com/pydna-group/pydna/blob/v5.5.16/src/pydna/amplify.py#L34-L498); [PCR notebook](https://github.com/pydna-group/pydna/blob/v5.5.16/docs/notebooks/PCR.ipynb); Pereira et al. (2015), p. 3.

11. **Design overlapping/tailed primers for ordered assemblies.** `pydna.design.assembly_fragments(fragments, overlap=35, maxlink=40, circular=False)` adds homologous tails to PCR amplicon primers for fusion PCR, Gibson-like and in-vivo homologous-recombination assembly; short linker sequences can be synthesized into neighboring primer tails. `circular_assembly_fragments` is a deprecated alias. **Status:** documented API and primer-design tutorial; it replaces the paper's old `assembly_primers` name. **Restrictions:** fragment order and `circular` are supplied by the user; linkers longer than `maxlink` are treated as ordinary fragments; at least every second non-link fragment must be an `Amplicon`, because tails can only be added through primers. **Evidence:** [`design.assembly_fragments`, lines 249–790](https://github.com/pydna-group/pydna/blob/v5.5.16/src/pydna/design.py#L249-L790); [primer-design notebook](https://github.com/pydna-group/pydna/blob/v5.5.16/docs/notebooks/primer_design.ipynb); Pereira et al. (2015), p. 3 (historical API).

12. **Design USER-cloning primer tails.** Experimental `pydna.design.user_assembly_design` selects short overlaps and adds uracils to primer tails for ordered USER assembly. **Status:** generated public API, not merely third-party code, but not part of the getting-started tutorials. **Restrictions:** it raises a `FutureWarning` that the function is experimental; overlap/tail bounds default to 4–15 and 50 bases; it inherits the need for PCR-amplifiable fragments. **Evidence:** [`design.user_assembly_design`, lines 792–1011](https://github.com/pydna-group/pydna/blob/v5.5.16/src/pydna/design.py#L792-L1011).

13. **Digest DNA and enumerate/classify restriction sites and fragments.** `Dseq`/`Dseqrecord.cut` accepts Biopython restriction enzymes and returns every resulting fragment, with sticky/blunt termini and transferable features; cutter-query methods identify no-cutters, unique/once, twice or N-cutters, and `linearize` opens a circular record at a single cutter. **Status:** central documented API and restriction-ligation tutorials. **Restrictions:** this is exact sequence/site simulation using Biopython enzyme definitions; ordinary `cut` represents the specified digest, not empirical methylation/activity/yield. **Evidence:** [`Dseq` cut/cutter API](https://github.com/pydna-group/pydna/blob/v5.5.16/src/pydna/dseq.py); [`Dseqrecord.cut` and `linearize`](https://github.com/pydna-group/pydna/blob/v5.5.16/src/pydna/dseqrecord.py); [restriction-ligation notebook](https://github.com/pydna-group/pydna/blob/v5.5.16/docs/notebooks/Restrict_Ligate_Cloning.ipynb); Pereira et al. (2015), pp. 5–6.

14. **Engineer physical DNA ends beyond restriction digestion.** `Dseq.fill_in`/`klenow`, `nibble_to_blunt`/`mung`, `T4`/`t4`, strand-specific `nibble_*`, `terminal_transferase`, `user`, `melt`, `melt_ss_dna`, and `shed_ss_dna` model fill-in, exonucleolytic resection, selected-nucleotide T4 polymerase treatment, terminal tailing, USER uracil cleavage, strand melting and release of short/gapped single strands. **Status:** generated `Dseq` API; largely absent from the main capability list and tutorials. **Restrictions:** operations are deterministic transformations of the supplied sequence/ends; they do not model reaction efficiency or competing chemistry. **Evidence:** [`dseq.py` end-modification methods](https://github.com/pydna-group/pydna/blob/v5.5.16/src/pydna/dseq.py).

15. **Simulate compatible-end ligation and circularization.** `Dseq`/`Dseqrecord.__add__`, `.join`, and `.looped` ligate compatible blunt/sticky ends and construct exact linear or circular products; the higher-level `pydna.assembly2.ligation_assembly` enumerates possible products and orientations from pre-cut fragments. **Status:** central documented API/tutorial; high-level enumeration is generated API. **Restrictions:** incompatible termini fail; high-level ligation defaults to disallowing blunt-end and partial sticky-overlap joins unless enabled; it predicts sequence-compatible products, not relative abundance. **Evidence:** [README example, lines 196–264](https://github.com/pydna-group/pydna/blob/v5.5.16/README.md#L196-L264); [`ligation_assembly`, lines 2537–2601](https://github.com/pydna-group/pydna/blob/v5.5.16/src/pydna/assembly2.py#L2537-L2601); Pereira et al. (2015), pp. 5–6.

16. **Enumerate alternative assemblies through a graph, not just one user-specified construct.** `pydna.assembly2.Assembly` represents fragments in both orientations, finds overlap edges, and exposes linear, circular, insertion, splicing/inversion and single-fragment products; convenience functions return lists of valid products and remove subassemblies. `assembly2str` renders plans. **Status:** documented API plus `new_assemblies` notebook; it supersedes the paper's legacy `pydna.assembly.Assembly.linear_products`/`circular_products`. **Restrictions:** by default `use_fragment_order=True` constrains paths from first to last (the docstring advises `False` for all arrangements); `use_all_fragments` can require every input; each fragment is used at most once; path enumeration is capped at 10,000 and assembly results at 50 by default. The legacy `assembly` module also has a configurable computation timeout. No abundance ranking is claimed. **Evidence:** [`assembly2.Assembly`, lines 1164–2190](https://github.com/pydna-group/pydna/blob/v5.5.16/src/pydna/assembly2.py#L1164-L2190); [new-assemblies notebook](https://github.com/pydna-group/pydna/blob/v5.5.16/docs/notebooks/new_assemblies.ipynb); Pereira et al. (2015), pp. 3–4.

17. **Simulate homology/overlap-based assembly modes.** `gibson_assembly`, `in_fusion_assembly`, `fusion_pcr_assembly`, and `in_vivo_assembly` enumerate all accepted linear/circular products from collections of fragments using method-specific overlap functions; one-fragment inputs can also circularize or yield rearrangements. A legacy `pydna.fusionpcr.fuse_by_pcr` recursively constructs overlap-extension products. **Status:** current convenience functions are documented API, with Gibson tutorials; `fuse_by_pcr` is generated legacy API without a current tutorial. **Restrictions:** these are sequence-overlap rules (default Gibson/In-Fusion/fusion-PCR limit 25), not thermodynamic/process simulation; `in_fusion_assembly` currently shares Gibson-like behavior under a distinct provenance type; the legacy helper is much more primitive. **Evidence:** [`assembly2.py`, lines 2261–2364](https://github.com/pydna-group/pydna/blob/v5.5.16/src/pydna/assembly2.py#L2261-L2364); [`fusionpcr.py`](https://github.com/pydna-group/pydna/blob/v5.5.16/src/pydna/fusionpcr.py); [Gibson notebook](https://github.com/pydna-group/pydna/blob/v5.5.16/docs/notebooks/Gibson.ipynb); Pereira et al. (2015), pp. 3–4.

18. **Simulate restriction–ligation and Golden Gate product sets.** `restriction_ligation_assembly(fragments, enzymes, allow_blunt=True, circular_only=False)` digests inputs, considers compatible products (including selected partial-digest products), and returns possible assemblies; `golden_gate_assembly` is a current public wrapper/alias with Golden Gate provenance. **Status:** documented API; restriction-ligation has a tutorial, and Golden Gate appears in the history notebook. **Restrictions:** the README still labels Golden Gate “in progress”; current `golden_gate_assembly` is sequence-level restriction–ligation enumeration, not a protocol-specific overhang optimizer, enzyme-cycle/yield model, or library-design algorithm. It filters partial-digestion cases and prevents some same-enzyme existing/generated-end combinations. **Evidence:** [README, lines 16–33](https://github.com/pydna-group/pydna/blob/v5.5.16/README.md#L16-L33); [`restriction_ligation_assembly` and `golden_gate_assembly`, lines 2365–2535](https://github.com/pydna-group/pydna/blob/v5.5.16/src/pydna/assembly2.py#L2365-L2535); [history notebook](https://github.com/pydna-group/pydna/blob/v5.5.16/docs/notebooks/history.ipynb).

19. **Simulate Gateway BP/LR assemblies, including multisite filtering.** `gateway_assembly(fragments, reaction='BP'|'LR', greedy=False, circular_only=False, multi_site_only=False)` recognizes built-in attB/P/L/R site families, enumerates products and can filter to multisite products. **Status:** documented API and history-notebook example. **Restrictions:** only BP and LR are accepted; greedy consensus matching can generate false positives and is off by default; `multi_site_only` filters one-site intermediate products rather than designing att sites. **Evidence:** [`gateway_assembly`, lines 2603–2727](https://github.com/pydna-group/pydna/blob/v5.5.16/src/pydna/assembly2.py#L2603-L2727); [`gateway.py`](https://github.com/pydna-group/pydna/blob/v5.5.16/src/pydna/gateway.py); [history notebook](https://github.com/pydna-group/pydna/blob/v5.5.16/docs/notebooks/history.ipynb).

20. **Simulate homologous-recombination integration, excision and inversion.** `homologous_recombination_integration(genome, inserts, limit=40)` can integrate one or multiple joined inserts; `homologous_recombination_excision_or_inversion` returns rearrangement products between repeats. **Status:** documented API and tutorial/history examples; homologous recombination is also a central paper capability. **Restrictions:** integration requires a linear genome and a non-empty list of `Dseqrecord` inserts; exact homology and a minimum length are used; this predicts sequence products, not recombination frequency. **Evidence:** [`assembly2.py`, lines 2728–2922](https://github.com/pydna-group/pydna/blob/v5.5.16/src/pydna/assembly2.py#L2728-L2922); [hackathon tutorial examples](https://github.com/pydna-group/pydna/blob/v5.5.16/docs/notebooks/hackathon_copenhagen_2025.ipynb); Pereira et al. (2015), pp. 3–7.

21. **Simulate Cre–lox and user-defined site-specific recombination.** `cre_lox_integration` and `cre_lox_excision_or_inversion` recognize loxP/lox66/lox71-related sites; `pydna.recombinase.Recombinase` plus `recombinase_integration`, `recombinase_excision_or_inversion`, and `recombinase_assembly` support user-defined site pairs and collections of inserts/fragments. **Status:** documented API and history-notebook examples. **Restrictions:** custom site strings encode uppercase flanks around a contiguous lowercase shared core, and both sites must have the same core; results are recognition-site/sequence outcomes, including rare reversal possibilities, not kinetic selectivity. **Evidence:** [`assembly2.py`, lines 2923–3140](https://github.com/pydna-group/pydna/blob/v5.5.16/src/pydna/assembly2.py#L2923-L3140); [`recombinase.py`](https://github.com/pydna-group/pydna/blob/v5.5.16/src/pydna/recombinase.py); [history notebook, custom recombinase section](https://github.com/pydna-group/pydna/blob/v5.5.16/docs/notebooks/history.ipynb).

22. **Model SpCas9 cleavage and CRISPR-assisted integration.** `pydna.crispr.cas9(protospacer)` supplies a Biopython-restriction-like SpCas9 cutter for a 20-nt protospacer adjacent to NGG; `protospacer(guide_construct)` extracts candidate protospacer sequences next to the recognized scaffold; `crispr_integration` combines homologous-recombination candidates with guide-cut checks and returns repaired products. **Status:** documented API with CRISPR and history notebooks. **Restrictions:** this is fixed SpCas9/NGG sequence simulation, not guide design or scoring; the caller supplies guide primers, there is no off-target search against a genome, and integration rejects or warns on cuts outside/inside the repaired region according to its deterministic checks. `protospacer` extracts sequences from an already supplied guide construct. **Evidence:** [`crispr.py`, lines 22–207](https://github.com/pydna-group/pydna/blob/v5.5.16/src/pydna/crispr.py#L22-L207); [`crispr_integration`, lines 3141–3239](https://github.com/pydna-group/pydna/blob/v5.5.16/src/pydna/assembly2.py#L3141-L3239); [CRISPR notebook](https://github.com/pydna-group/pydna/blob/v5.5.16/docs/notebooks/CRISPR.ipynb).

23. **Assemble PCR products while tolerating substitutions.** `pydna.assembly2.PCRAssembly`/`pcr_assembly` enumerate products from primer/template overlaps and can annotate primer-binding sites. **Status:** documented API, distinct from ordinary `pcr`; no dedicated getting-started section. **Restrictions:** mismatch support is for substitutions, not insertions/deletions; the minimum usable overlap grows with the mismatch count. **Evidence:** [`PCRAssembly`](https://github.com/pydna-group/pydna/blob/v5.5.16/src/pydna/assembly2.py#L1940-L2031); [`pcr_assembly`, lines 3240 onward](https://github.com/pydna-group/pydna/blob/v5.5.16/src/pydna/assembly2.py#L3240).

24. **Generate all possible duplex products of two oligonucleotides.** `pydna.oligonucleotide_hybridization.oligonucleotide_hybridization` enumerates double-stranded records for every allowed relative placement/overhang of two `Primer`s with a minimum annealing region. **Status:** generated documented API and used internally by SnapGene-history replay; no first-party tutorial devoted to it. **Restrictions:** two oligos only; an alignment with mismatches raises rather than scoring imperfect hybridization; it is structural hybridization, not folding/thermodynamic prediction. **Evidence:** [`oligonucleotide_hybridization.py`, lines 14–119](https://github.com/pydna-group/pydna/blob/v5.5.16/src/pydna/oligonucleotide_hybridization.py#L14-L119).

25. **Track, serialize, replay and validate cloning provenance for one product or a collection.** Current simulated operations attach typed OpenCloning `Source` objects to `Dseqrecord.source`; `Dseqrecord.history()` prints a tree, while `CloningStrategy.from_dseqrecords([...])` gathers terminal products, input sequences, primers and steps into JSON, `to_dseqrecords` rebuilds them, and validation/normalization can replay and check the strategy. ### Phase 1 synthesis

Pydna is principally a programmable, sequence-exact cloning simulator and provenance system. For library work, its strongest native collection capabilities are: parsing/holding many sequences or primers; high-speed primer-set and diagnostic-primer screening; enumerating alternative PCR/ligation/assembly/recombination products; generating random DNA/RNA/ORF/protein sequences; comparing/deduplicating products; and serializing multiple terminal constructs with their shared cloning history. General biological variant-space enumeration and optimization are not core functions: the most explicit library-design gallery examples delegate that layer to teemi/custom Python and use pydna to simulate or verify each construction.

19. **Codon-diagnostic organism scope.** The record repeatedly describes yeast `sce` tables but does not state that `rarecodons(organism="eco")` is also supported, while CAI weights and the populated start/stop/N-end data are limited to `sce` (the `eco` mappings for the latter are empty). **Evidence:** [`codon.py` organism tables](https://github.com/pydna-group/pydna/blob/v5.5.16/src/pydna/codon.py); [`Seq.cai`, `rarecodons`, and `express`](https://github.com/pydna-group/pydna/blob/v5.5.16/src/pydna/seq.py#L142-L205). **Why material:** the supported organism depends on which diagnostic a protein-library user calls, and the record's singular wording hides that boundary.

## C. BALANCE

The record gives pydna's strengths substantial space—especially reaction simulation, provenance, primer screening, topology, features, visualization, and maintenance—so it is not a simple capability takedown. It is nevertheless tilted toward documenting library-design absences more deeply than native collection workflows and operational limits: the collection-capable `CloningStrategy` is explicitly denied/export-only, random/protein/deduplication and trace-verification APIs are buried or absent, and many assembly modes are praised by name without their decisive constraints. Overall it is impressively broad but not fully fair; the understatements and unqualified “all/only” claims materially distort the positive picture.
