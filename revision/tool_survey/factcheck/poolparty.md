## Phase 1 inventory (frozen before reading the survey record)

**Freeze note.** This inventory was completed and saved before the Phase 2 record was opened. It is the fixed comparison yardstick and was not revised after Phase 2 began. Audit date: 2026-08-14.

### Sources and scope

Primary sources used were the current local `main` checkout at `poolparty-statecounter/poolparty/`, its source-tree documentation and tests, the rendered-paper source corresponding to `26.05.18_bmc_submission/latex/main.pdf` (`latex/main.tex`), the project's PyPI page, and the project's public GitHub repository. The package calls these collections `Pool` objects and describes the library program as a lazy directed acyclic graph (DAG): operations construct immutable downstream pools, and actual strings are generated only on request. Evidence: `docs/pool.rst:4-19`; `src/poolparty/pool.py:24-80`; paper source `latex/main.tex:90,94-108`.

The labels below distinguish:

- **Documented API**: a dedicated operation/user-guide page or API-reference entry exists in the repository documentation.
- **Documented tutorial/example**: functionality is demonstrated in an official tutorial or paper example, but the example is not a separate operation.
- **Public code, incompletely indexed**: exported or public class/method code exists, but it is missing from the supposedly complete top-level API inventory (`docs/api.rst`) or lacks a dedicated user-guide entry. This is core code, not a plugin or third-party extension.

| Capability | Interface and documentation status | Restrictions / exact behavior | Primary evidence |
|---|---|---|---|
| Lazy, immutable design DAGs | `Pool`, `DnaPool`, `ProteinPool`, `Operation`; operations return new pools and support branching. **Documented API.** | Strings are not generated until preview/generation/export. Pool creation requires an active `Party`; importing the package creates a default Party, while `pp.init()` resets it and `with pp.Party()` gives a scoped context. | `docs/pool.rst:4-47`; `src/poolparty/__init__.py:268-269`; `src/poolparty/party.py:62-97,128-226`; paper `latex/main.tex:90,94-112`. |
| Pool inspection | `pool.name`, `.num_states`, `.seq_length`, `.regions`, `.parents`, `.operation`, `.iter_order`; `.named(name)`; Party lookup methods by ID/name. **Documented API**, with Party lookup details mainly class-docstring/source. | `num_states` counts state slots, not guaranteed unique strings: random draws can duplicate, `repeat` intentionally duplicates, and filtering leaves null slots. Pool names must be unique inside a Party. | `docs/pool.rst:51-126`; `src/poolparty/pool.py:82-163`; `docs/operations/modes.rst:210-234`; `src/poolparty/state_ops/repeat.py:55-97`; `src/poolparty/party.py:228-289`. |
| Sequential mode | `mode="sequential"` on supported operations. **Documented API.** | Deterministic enumeration; `num_states` below the natural size truncates and above it cycles. | Random mode | `mode="random"`, optional `num_states`, and generation `seed`. **Documented API.** | With no explicit count it is a fresh/stateless draw and does not multiply the pool's state count; with `num_states=N`, N reproducible designs become stateful. | Fixed mode | Fixed operations such as `rc`, `join`, case transforms. **Documented API.** | Exactly one transformation per input; no user-selectable mode/count. `join` is fixed as an operation but can still form a Cartesian product across independent parent-pool state spaces. | `docs/operations/modes.rst:112-133,236-266`; `docs/operations/library_size.rst:20-58,162-179`. |
| State-space arithmetic | Chained operations, `join`, `stack`, `sync`. **Documented API.** | Ordinary independent choices multiply; `stack` adds/disjoint-unions; fixed transforms do not change count; synchronization makes equal-sized pools iterate lockstep. Counts are state counts, not necessarily unique molecular sequences. | `docs/operations/library_size.rst:17-58,98-176`. |
| Iteration priority | `iter_order` on pools and most operations. **Documented throughout operation references.** | Alters which dimension changes fastest when Cartesian state dimensions are combined; it does not change members. | `src/poolparty/pool.py:82-92`; `docs/operations/join.rst`; `docs/operations/from_seqs.rst`. |
| Copy/branch controls | `pool.copy()` shares upstream pools; `pool.deepcopy()` recursively duplicates the upstream DAG. **Documented API.** | Must be used in an active Party; neither generates sequences. | `docs/pool.rst:487-503`; `src/poolparty/pool.py:200-247`. |
| Custom operation extension | Subclass `poolparty.Operation`; alternatively public exported `fixed_operation(parent_pools, seq_from_seqs_fn, seq_length_from_pool_lengths_fn, ...)` creates an arbitrary deterministic transform. - **Deep mutational scanning:** official tutorial/paper composes wild-type replication, exhaustive single- and pairwise amino-acid substitutions, 10,000 random higher-order codon mutants, stacking, design cards, translation/visual inspection, totaling 547,230 coding sequences. PoolParty generates the sequence/covariates; it does not run or optimize the AI model. Evidence: paper `latex/main.tex:199-221,229-231`.

### Boundaries and restrictions stated by the project

- The authors explicitly say PoolParty **is not** a sequence optimizer: it does not optimize codon usage, satisfy per-sequence synthesis constraints, or design sequences guided by machine-learning models. It also does not plan physical library construction or design mutagenic primers. Evidence: paper `latex/main.tex:225-239`.
- Constrained barcodes and rejection filters are narrower exceptions: they generate/test against specific GC, distance, homopolymer, complexity, DUST, or restriction-site criteria, but they do not provide general multi-objective repair/optimization (`docs/operations/get_barcodes.rst:1-12`; `src/poolparty/pool_mixins/filter_mixin.py:1-281`).
- The primary source factories create DNA pools; protein pools arise through translation, and reverse translation accepts a ProteinPool/raw protein string. There is no public protein-list source or direct amino-acid-level mutation API (`src/poolparty/fixed_ops/from_seq.py:12-21`; `src/poolparty/base_ops/from_seqs.py:15-28`; `src/poolparty/orf_ops/translate.py:99-128`; `src/poolparty/orf_ops/reverse_translate.py:77-119`).
- Exhaustive enumeration is deliberately bounded at one million states **per sequential operation** (`src/poolparty/operation.py:28-55`). Large designs are expected to use random sampling, compose smaller enumerations, slice/sample, or materialize.
- `filter` is rejection-with-null propagation, not state-space compaction, until output with `discard_null_seqs=True` or a materialization step (`docs/operations/filter.rst:12-21`; `src/poolparty/base_ops/materialize.py:157-239`).
- Package/API maturity is alpha, and current `main` includes explicitly unreleased behavior that should be distinguished from the 0.1.1 distribution (`pyproject.toml:25-27`; `CHANGELOG.md:8-32`).
