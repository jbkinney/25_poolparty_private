## 1. One-paragraph orientation (why the split rows land where they do)

DNA Chisel is a declarative single-sequence constraint solver: `DnaOptimizationProblem(sequence=…, constraints=[…], objectives=[…])` in, one optimized sequence out. Its internal machinery is genuinely combinatorial and genuinely lazy — `MutationSpace.all_variants(sequence)` is a documented public generator doing `itertools.product` over per-slot nucleotide choices, `space_size` gives the cardinality without materializing, `pick_random_mutations` / `apply_random_mutations(n, seq)` sample the space, and `EnforceChanges(minimum=3)` / `EnforceChanges(minimum_percent=70)` is a real "force ≥N changes" knob with GenBank shorthand. What does not exist is a **library**: no class holds a set of designed sequences, `load_record` is `Bio.SeqIO.read` (not `parse`) so even the loader refuses multi-record files, the CLI is one file in / one file out, and multi-sequence work is an explicit user `for` loop. The v2 split therefore separates cleanly: the mutagenesis *primitives* earn partial credit, and the *pool* — heterogeneous components in one labelled library specification — is where the "no" actually lives.

**Decision rule applied consistently** (borrowed from the `library_algebra` definition in ROWS_v2): if a single in-tool call performs the operation, it can score `partial`/`yes`; if the operation itself only happens because the user wrote an external loop or script, it is `no`. This is what separates `sampled_random_mutagenesis` / `higher_order_combinatorial` (`partial` — one call does the sampling / the multi-site combination) from `exhaustive_single_scans` and `library_algebra` (`no` — the sweep, and the combining, are the user's loop).

## 3. Evidence, row by row

### Block A — library specification

**`library_first_class_object` — no.**
No class in the API represents a set of designed sequences. `DnaOptimizationProblem(sequence=…)` takes a single sequence; `docs/ref/core_classes.rst` lists only `DnaOptimizationProblem`, `CircularDnaOptimizationProblem`, `Specification`, `SpecEvaluation`, `Location`, `MutationSpace`/`MutationChoice` and the pattern classes — there is no library/pool/variant module in the `dnachisel/` tree. Enforced at both ends: `load_record` uses `Bio.SeqIO.read` (not `parse`), so the loader accepts exactly one record and raises on a multi-record FASTA/GenBank; `to_record()`/`write_record()` emit one record; `cli.py` is `dnachisel <source> <target>` — one file in, one file out. Multi-sequence work is an explicit user `for` loop (`examples/common_scenarios/ecoli_genes_optimization.py`, `genome-wide-optimization.py`: one problem per CDS, results appended to a user-held Python list). The one multi-sequence API is a *reporting* utility, `constraints_breaches_dataframe(constraints, sequences)`, which validates sequences the user already holds — it takes `[(name, seq), …]` / dict / records and returns a pandas DataFrame, so a *set of sequences* can be passed in for QC, but nothing in the tool ever constructs or owns that set. Pre-empting the obvious objection: DNA Chisel's own `README.rst` § "Related projects" advertises the third-party `dnachisel-dtailor-mode` for "generation of large collection of sequences covering the objectives fitness landscape" (it exposes `DesignSpace`/`FullFactorial`/`Optimization`/`DnaDesignProblem`/`SequenceDesigner` over SQLite) — but it is not EGF, 3 stars, all four PyPI releases dated 2020-01-14, last repo push 2020-01-15.
*Source:* GitHub `master` tree; `docs/ref/core_classes.rst`; `dnachisel/biotools/genbank_operations.py`; `dnachisel/cli.py`; `dnachisel/reports/constraints_reports/constraints_breaches_dataframe.py`; `README.rst`; PyPI `dnachisel-dtailor-mode` JSON.

**`composable_operations` — partial.** *(rename of `dag_chaining`; value carried)*
The new wording ("compose/chain/nest arbitrarily vs a fixed pipeline") is, if anything, kinder to DNA Chisel, and it deserves the credit: the pipeline is **not** fixed. A problem is an arbitrary user-supplied list of constraints and objectives — the abstract's own claim is "freely define and combine optimization specifications" — specifications nest via `SpecificationSet` ("Generic class for writing Specs which are actually made of more specs… the initialization actually creates a dictionary of standard Specifications in the DNAOptimizationProblem", registered through `SpecificationSet.register_specifications`; `AllowPrimer` is such a set, expanding to `UniquifyAllKmers` + `EnforceMeltingTemperature` + three `AvoidPattern(RepeatedKmerPattern(k, n))` + optional `AvoidHeterodimerization`), and users can define new `Specification` subclasses with custom `evaluate`/`localized` and register them with the GenBank parser (shipped example: `gen9_9mer_score_minimization.py`). **Why not "yes":** what composes are *constraints and objectives evaluated on one sequence*, not design steps that produce sequences. There is no pipeline, graph or DAG object anywhere in the tree; chaining problems so the output of one feeds the next is hand-written user Python (`primers_collection.py` accumulates accepted primers in a list and re-constrains each new problem against them). Nesting is one level deep via `SpecificationSet`, not arbitrary-depth composition of generators.
*Source:* paper §Abstract, §Usage; `dnachisel/Specification/SpecificationSet.py`; `builtin_specifications/AllowPrimer.py`; `examples/common_scenarios/primers_collection.py`, `gen9_9mer_score_minimization.py`.

**`lazy_generation` — partial.** *(rename of `lazy_evaluation`; value carried)*
`dnachisel/MutationSpace/MutationSpace.py` defines `def all_variants(self, sequence)`, docstring *"Iterate through all sequence variants in this mutation space."*, implemented as `for variants in itertools.product(*variants_slots): … yield new_sequence.decode()` — a true generator lazily enumerating the constrained combinatorial mutation space, i.e. sequences produced on demand and never fully materialized. Alongside it: `space_size` ("Return the number of possible mutations", a product of per-choice cardinalities computed without materializing anything, log/exp-guarded against overflow), `pick_random_mutations(n, sequence)` / `apply_random_mutations(n, sequence)`, and `MutationSpace.from_optimization_problem(problem, new_constraints=None)` (so `EnforceTranslation` yields the space of all synonymous CDS variants). This is public API, not internal: `docs/ref/core_classes.rst` contains `.. automodule:: dnachisel.MutationSpace :members:` and the rendered `ref/core_classes.html` documents `all_variants`, `apply_random_mutations`, `choices_span`, `constrain_sequence`, `from_optimization_problem`, `localized`, `pick_random_mutations`, `space_size`, `string_representation`. **Why not "yes":** `all_variants` yields bare unlabelled sequence strings with no identity or metadata, over one problem's single sequence; it is a solver helper for exhaustive local search; and no example, docs prose or the paper presents it as a way to emit a library. So there is a documented lazy generator over a combinatorial design space, but no lazy materialization of a *library*.
*Source:* `dnachisel/MutationSpace/MutationSpace.py`; `docs/ref/core_classes.rst`; https://edinburgh-genome-foundry.github.io/DnaChisel/ref/core_classes.html.

**`library_algebra` — no.** *(new; split from `library_as_object`)*
There is nothing to do algebra on. No object represents a library, so there is no stack, concat, sample, repeat, or set operation over libraries in the API — the docs core-classes page and the `dnachisel/` tree contain no such module or method. Combining designed sequences is unambiguously an **external** operation: in `ecoli_genes_optimization.py` / `genome-wide-optimization.py` the user appends `problem.to_record(...)` to a plain Python list and calls Biopython to write a multi-record FASTA; in `primers_collection.py` the user maintains the accumulating `primers` list themselves and passes it back in as `AvoidHeterodimerization(other_primers)`. Per the ROWS_v2 definition ("if the user must concatenate outputs with an external script, this is no"), this is `no`. The nearest in-tool set-level features are (a) `constraints_breaches_dataframe(constraints, sequences)`, which *consumes* a user-held set for QC but neither builds nor transforms a library, and (b) `EnforceRegionsCompatibility(locations, compatibility_condition, condition_label)`, an all-pairs constraint over hand-listed sub-locations of a *single* sequence — cross-member-like, but not library algebra. Sampling of a library also does not exist; `pick_random_mutations` samples a mutation space, not a library.
*Source:* `docs/ref/core_classes.rst`; `examples/common_scenarios/{ecoli_genes_optimization,genome-wide-optimization,primers_collection}.py`; `builtin_specifications/EnforceRegionsCompatibility.py`; `dnachisel/reports/constraints_reports/constraints_breaches_dataframe.py`.

**`exhaustive_single_scans` — no.** *(new; split from `mixed_mutagenesis_one_pool`)*
There is no mutagenesis-scan abstraction: nothing sweeps positions, and the words variant/mutagenesis/scan/saturation appear nowhere in the built-in specification list, the GenBank annotation vocabulary, or the `builtin_specifications/` listing. Two specific absences make this a clean `no` rather than a `partial`. (i) **No position sweep in-tool.** `MutationSpace.all_variants()` enumerates the *joint* product over all mutable slots of one problem, not the set of single-position events; to obtain "every substitution at every position" the user must write an outer loop over positions, building a narrow-location problem each time — the sweep itself is the external script, which is exactly the condition ROWS_v2 defines as `no`. (ii) **No deletions at all.** DNA Chisel is length-preserving: edits are nucleotide substitutions (`sequence_edits_as_array`, `_replace_sequence`, per-position `MutationChoice` sets), `EnforceChoice` requires "List of same-length ATGC sequences", and even `EnforcePatternOccurence` (`@insert()`) substitutes a pattern into an existing span rather than lengthening the sequence. So no deletion or indel single-event scan is expressible at all. Stated openly so no referee can claim suppression: for a location narrowed to one position, `all_variants` *does* exhaustively enumerate the three substitutions, so the enumeration primitive is present — it is the per-position regime, the deletion arm, and the labelled output that are absent.
*Source:* `dnachisel/MutationSpace/MutationSpace.py`; `builtin_specifications/EnforceChoice.py` (docstring read verbatim this round); `builtin_specifications/EnforcePatternOccurence.py`; `docs/ref/builtin_specifications.rst`; `docs/genbank/genbank_api.rst`.

**`sampled_random_mutagenesis` — partial.** *(new; split from `mixed_mutagenesis_one_pool` — an upgrade on the split)*
The sampling primitives are real, public and documented, and the final memo says explicitly that they "must not be denied". `MutationSpace.pick_random_mutations(n_mutations, sequence)` and `apply_random_mutations(n_mutations, sequence)` draw `n` random mutations from the constrained space and return the mutated sequence — a single in-tool call that performs random mutagenesis at a user-set count; both are on the rendered public API page via `.. automodule:: dnachisel.MutationSpace :members:`. `DnaOptimizationProblem.mutations_per_iteration` exposes the same knob to the solver's stochastic search ("A region's sequence is optimized via either a stochastic search (using random mutations of the sequence) or an exhaustive search…", paper §Implementation). A genuine **rate-based** form also exists: `EnforceChanges(minimum_percent=70)` / `EnforceChanges(minimum=3)`, documented under "Forcing changes" with GenBank shorthands `@change`, `@change(minimum=50%)`, `~change` (`changes.md` v3.0.0: "AvoidChanges and EnforceChanges can now be tunable"). De-novo random generation exists too: `random_dna_sequence(length, gc_share, probas, seed)` and the top-level `random_compatible_dna_sequence(sequence_length, constraints, probas=None, seed=None, max_random_iters=5000)` — "Produce a random sequence complying to some specifications". **Why not "yes":** each call returns *one* unlabelled sequence. There is no sampled variant *set*, no requested-N-variants parameter, no per-variant record, no mutation-rate-per-library concept; assembling a sampled library is a user loop, and the samples carry no identity or provenance. Randomness is at least reproducible — `docs/notes.rst` guarantees determinism from `numpy.random.seed()` set before any DnaChisel call, backed by `tests/test_determinism/`.
*Source:* `dnachisel/MutationSpace/MutationSpace.py`; `builtin_specifications/EnforceChanges.py`; `dnachisel/utils/utils.py`; `dnachisel/biotools/random_sequences.py` (read verbatim this round); `docs/genbank/genbank_api.rst`; `docs/notes.rst`; `changes.md`; paper §Implementation.

**`higher_order_combinatorial` — partial.** *(new; split from `mixed_mutagenesis_one_pool` — an upgrade on the split)*
Higher-order multi-site combination is what the mutation space *is*. `MutationSpace` holds a list of `MutationChoice` slots spanning the mutable region, and `all_variants` is `itertools.product(*variants_slots)` over them — every combination of choices at every mutable position simultaneously, i.e. pairwise and arbitrarily high order by construction, not a special mode. `space_size` returns the cardinality of that joint space (log/exp-guarded precisely because it explodes combinatorially). `apply_random_mutations(n_mutations, sequence)` applies `n` simultaneous mutations for any `n`, `EnforceChanges(minimum=3)` demands at least 3 simultaneous changes, and `MutationSpace.from_optimization_problem(problem)` builds the joint space from any constraint set (e.g. all synonymous variants of a CDS = a full higher-order codon-combination space). `string_representation(separator="|")` and `plot(ax)` render that combinatorial space directly. **Why not "yes":** the combinations are solver states and generator output, not library members — the solver collapses the space to one returned sequence, and `all_variants` yields unlabelled strings with no order label, no per-variant record, and no way to say "give me all doubles" (there is no interaction-order parameter; you get the full product or a random draw, not a specified order stratum).
*Source:* `dnachisel/MutationSpace/MutationSpace.py`; `builtin_specifications/EnforceChanges.py`; `docs/ref/core_classes.rst`.

**`heterogeneous_components_one_library` — no.** *(new; split from `mixed_mutagenesis_one_pool` — this is where the old "no" actually lives)*
This is the real gap, and the final memo states it in exactly these terms: "The missing thing is the **pool**, not the primitives." There is no way to emit multiple regimes or structurally different component types into one labelled output: no library object, no component or regime concept, no WT/control replicates, no per-variant records, no regime labels. The solver collapses the mutation space to a single output sequence, and `all_variants` yields unlabelled strings from a *single* regime over a *single* sequence. Expressing "exhaustive singles + sampled doubles + WT controls + a barcode series, in one specification, with provenance" is not possible at any level of the API — not in `DnaOptimizationProblem` (one sequence), not in the GenBank annotation interface (specs on one record), and not in the CLI (one file in, one file out). Even the input side forbids it: `load_record` = `Bio.SeqIO.read`.
*Source:* `final/dnachisel.md` §5 (`mixed_mutagenesis_one_pool`); `dnachisel/MutationSpace/MutationSpace.py`; `dnachisel/biotools/genbank_operations.py`; `dnachisel/cli.py`.

**`combinatorial_motif_place` — no.** *(carried)*
`EnforcePatternOccurence` (`@insert()`) sets a required occurrence *count* of a pattern in a region: the docs state it "ensures that exactly one occurence of the pattern is present in the given region, but it can also be used to create more occurences", with new occurrences "preferentially placed towards the center"; the paper adds that "an `insert(CGTCTC)` constraint will attempt to place the pattern 'CGTCTC' at different locations of the sequence". There is no product API over motifs × positions × orientations × permutations, and the alternative placements the solver considers are never **emitted as distinct library members** — the problem returns one sequence with one chosen placement. (Deliberately softened, per the final memo: `all_variants` *can* enumerate a space, so the defensible claim is about emission as library members, not about enumeration.) All other motif handling is *avoidance*: `MotifPssmPattern` exists only as a `SequencePattern` for `AvoidPattern`-style constraints, and `sequence_without_tf_binding_sites.py` is pure avoidance of E. coli TFBS.
*Source:* `docs/genbank/genbank_api.rst`; paper §Usage; `builtin_specifications/EnforcePatternOccurence.py`; `docs/ref/core_classes.rst`.

**`barcode_generation` — partial.** *(carried, including the definitional fork)*
No barcode/UMI/demultiplexing abstraction exists — "barcode" appears nowhere in the built-in specification list, the biotools reference, the docs TOC or the `builtin_specifications/` listing — and there is **no mechanism to attach generated tags to library members**. But three of the four things this row normally means are shipped and documented. (a) *Generate N short sequences de novo*: `random_compatible_dna_sequence(sequence_length, constraints, probas=None, seed=None, max_random_iters=5000)`, a top-level export — "Produce a random sequence complying to some specifications". (b) *Minimum pairwise distance*: `EnforceRegionsCompatibility(locations, compatibility_condition, condition_label)` is an all-pairs constraint (`evaluate` runs `itertools.combinations(self.locations, 2)`, scoring `-len(incompatible_pairs)`) with an arbitrary user predicate, and the shipped, unit-tested `examples/builtin_specifications_examples/example_EnforceRegionsCompatibility.py` uses exactly `sequences_differences(seq1, seq2) >= 2` over `locations=[(0,4),(50,54),(100,104),(150,154)]` with `condition_label="2bp difference"` — an explicit minimum-Hamming-distance constraint over a set of four 4-nt tags. `sequences_differences` is a top-level export; `EnforceRegionsCompatibility` is in `docs/ref/builtin_specifications.rst`; `tests/builtin_specifications/test_EnforceRegionsCompatibility.py` exists. (c) *Composition filters*: `primers_collection.py` applies `AvoidPattern("3x3mer")`, `AvoidPattern("4xG")`, `EnforceGCContent(target=0.6)`. Only (d), binding tags to library members, is genuinely absent. Barcode-set design is therefore expressible but must be hand-assembled, and the product is a bare list of strings with no member association, no demultiplexing model, and no distance guarantee across an entire designed set (the constraint is over hand-listed sub-locations of one sequence).
*Definitional fork, stated openly (unchanged in v2):* under "primitives from which a barcode set can be built" the value is `partial`, recorded here; under "a first-class barcode generator producing a demultiplex-ready set bound to library members" it is `no`. Both survey rounds agree on every underlying fact and differ only on the row definition, so `partial` — the reading that gives the competing tool full credit — is recorded, with the narrow reading named rather than suppressed. Not `unknown`: nothing about the tool is unknown.
*Source:* `dnachisel/utils/utils.py`; `builtin_specifications/EnforceRegionsCompatibility.py`; `examples/builtin_specifications_examples/example_EnforceRegionsCompatibility.py`; `examples/common_scenarios/primers_collection.py`; `docs/ref/builtin_specifications.rst`.

**`per_sequence_provenance` — partial.** *(carried)*
For the single output sequence the provenance is genuinely rich and machine-readable. `problem.to_record(..., with_constraints=True, with_objectives=True, with_sequence_edits=True)` writes GenBank features for every specification applied plus one feature per nucleotide edit labelled `before=>after` (rendered red). `write_optimization_report` emits a bundle: `Report.pdf`, `plots.pdf`, `final_sequence.gb`, `final_sequence_with_edits.gb`, `constraints_before_and_after.csv` (constraint, start, end, before, after, edits, % edited), `objectives_before_and_after.csv` (objective, boost, start, end, before, after, edits, % edited) — one row per specification with before/after PASS-FAIL or score, an edit count and a % edited figure for that specification's span — an **md5 hash of the source file plus an embedded copy of the source file** (written as `[file_hash]_[original_basename]`), `logs.txt` from the problem logger, and before/after sequenticons. The paper calls this "comprehensive optimization reports for traceability and troubleshooting". **Why not "yes":** this is provenance of *how one sequence was edited*, not structured metadata about a library member's construction lineage; there is no per-member record because there is no library, and nothing records which design operation produced a given member of a set. `partial` holds under the library-member reading of the row.
*Source:* `dnachisel/reports/optimization_reports.py`; `DnaOptimizationProblem/mixins/RecordRepresentationMixin.py`; paper §Implementation.

**`automatic_naming` — no.** *(carried)*
`to_record(..., record_id=None)` does `record = sequence_to_biopython_record(self.sequence)` and then only `if record_id is not None: record.id = record_id`. Since `sequence_to_biopython_record(sequence, id="<unknown id>", name="<unknown name>", features=())`, **the default output id is the literal string `"<unknown id>"`** — it is not inherited from the input record. Naming is entirely the user's job (in the genome-wide example the user passes `protein_id`). Nothing generates names encoding what was designed. The nearest thing to auto-identification is visual, not nominal: reports embed `sequenticon(seq, output_format="html_image", size=24)` for the before and after sequences — an auto-generated identicon image, not a name or accession.
*Source:* `DnaOptimizationProblem/mixins/RecordRepresentationMixin.py`; `dnachisel/biotools/genbank_operations.py`; `dnachisel/reports/optimization_reports.py`.

**`design_visualization` — partial.** *(carried)*
Visualization is real and substantial, but per-sequence. `write_optimization_report` renders the sequence with annotated constraints, objectives and edits as PDF plots (paper Fig. 1C; `max_features_in_plots` option) via `dna_features_viewer` through a `SpecAnnotationsTranslator`; `plot_optimization_changes` renders the before/after edit diff using GeneBlocks `DiffBlocks.from_sequences(before, after).plot(...)`; `write_no_solution_report` renders a whole-sequence figure with the failing zone shaded plus a cropped local-breaches figure with passing constraints in green, along with `local_constraints_breaches.gb` and `plots.pdf`; `breaches_records_to_pdf` renders constraint breaches across many records (the one genuinely multi-sequence view, and it is QC of user-supplied sequences); and `MutationSpace.plot(ax, color="red", y_offset=-2)` / `MutationSpace.string_representation(separator="|")` visualize the allowed-variant space itself. **Why not "yes":** no design-graph / pipeline view and no library-level view of a designed set.
*Source:* `dnachisel/reports/optimization_reports.py`; `dnachisel/MutationSpace/MutationSpace.py`; `dnachisel/reports/constraints_reports/`; paper Fig. 1C.

### Block B — assay coverage

**`assay_dms` — no.**
Checked against the complete built-in specification list, `docs/examples.rst` and the full `examples/` tree: no per-position saturation, no codon-substitution enumeration for variant libraries, no variant table output, no DMS terminology anywhere. Third parties (e.g. Tycko et al. 2020) use DNA Chisel to codon-optimize oligos *after* designing a DMS library elsewhere — post-processing of someone else's library, not library design.
*Source:* `docs/ref/builtin_specifications.rst`; `docs/examples.rst`; `examples/` tree; prior analysis.

**`assay_mpra` — no.**
No regulatory/MPRA library design. Motif functionality is *avoidance* only: `MotifPssmPattern` exists purely as a `SequencePattern` for `AvoidPattern`-style constraints (alongside `EnzymeSitePattern`, `HomopolymerPattern`, `RepeatedKmerPattern`), and `sequence_without_tf_binding_sites.py` downloads E. coli TFBS data in order to forbid all matches. No promoter or enhancer tiling, no combinatorial motif installation, no oligo-pool output anywhere in the tree.
*Source:* `docs/ref/core_classes.rst`; `examples/common_scenarios/sequence_without_tf_binding_sites.py`.

**`assay_insilico` — no.**
Nothing in the paper, docs, README, source tree or examples concerns probing predictive or generative genomic AI models. Every objective is a biochemical or manufacturing score: CAI, codon-usage matching, RCA harmonization, GC content, melting temperature, hairpins, homology, restriction sites, and the user-defined Gen9 9-mer synthesis score.
*Source:* paper (full text); `docs/ref/builtin_specifications.rst`; `examples/` tree.

### Block C — genomics integration

**`genome_coordinates` — no.**
`Location(start, end, strand)` is purely sequence-relative — docs: "Location(5, 10) represents sequence[5, 6, 7, 8, 9]". `Location.from_data` accepts only a tuple/list, a Biopython `FeatureLocation`, or another `Location`, and `Location.from_biopython_location` reads only `.start`, `.end`, `.strand`. No assembly awareness, no `chrom:start-end` input, no liftback of designed sequence to genome coordinates. A genome can be *loaded* as a Biopython record and features extracted by the user (`feature.location.extract(genome_record)` in the genome-wide example) — that happens on the user side with Biopython, outside DNA Chisel.
*Source:* `dnachisel/Location.py`; `docs/ref/core_classes.rst`; `examples/common_scenarios/genome-wide-optimization.py`.

**`transcript_models` — no.**
Input is FASTA/GenBank/SnapGene: `load_record` dispatches to `Bio.SeqIO.read` for genbank/fasta and `snapgene_file_to_seqrecord` for `.dna`; `write_record` exports genbank or fasta. No GFF/GTF support anywhere in docs or source, and no transcript/isoform concept. The GenBank parser (`from_record`) reads only `misc_feature` labels beginning with `@` or `~` — specification declarations, not gene models. And `SeqIO.read` (not `parse`) means a multi-transcript file cannot even be loaded.
*Source:* `dnachisel/biotools/genbank_operations.py`; `docs/genbank/genbank_api.rst`.

**`exon_intron_split_codons` — no.**
`EnforceTranslation.set_location` validates that "Location length in Codon Specifications should be a 3x" and iterates codons contiguously via `codon_index_to_location(i)`. More damningly, `Location.from_biopython_location(location)` reads only `.start`, `.end`, `.strand`, so a Biopython `CompoundLocation` **silently collapses to its outer span** rather than raising — a spliced CDS would be treated as one contiguous region *including its introns*, producing silently wrong codon assignments instead of an error. No exon-array handling, no logic for codons spanning an intron boundary.
*Source:* `dnachisel/Location.py` (verbatim); `builtin_specifications/EnforceTranslation.py`.

**`vcf_vep_output` — no.**
Outputs verified in source: `write_record` (genbank or fasta); the optimization report bundle (`Report.pdf`, `plots.pdf`, `final_sequence.gb`, `final_sequence_with_edits.gb`, `constraints_before_and_after.csv`, `objectives_before_and_after.csv`, `logs.txt`, source-file copy); `constraints_breaches_dataframe` returning a pandas DataFrame exportable to Excel; and `breaches_records_to_pdf`. No VCF writer and no VEP-compatible output anywhere.
*Source:* `dnachisel/biotools/genbank_operations.py`; `dnachisel/reports/optimization_reports.py`; `dnachisel/reports/constraints_reports/`.

**`consequence_annotation` — no.**
`sequences_differences`, `sequences_differences_segments` and `annotate_differences` locate where two sequences differ, and `sequence_edits_as_features` labels each edit `before=>after` in red — but nothing classifies molecular consequence (stop-gained, missense, frameshift, in-frame indel, splice). Coding consequence is *constrained away* by `EnforceTranslation` and `AvoidStopCodons` rather than annotated after the fact.
*Source:* `dnachisel/biotools/`; `DnaOptimizationProblem/mixins/RecordRepresentationMixin.py`.

### Block D — adjacent / complementary

**`primer_design` — partial.** *(carried)*
`AllowPrimer` — "Enforce various specifications for enabling primers at the location… useful for making sure that you will be able to conduct a PCR or sanger sequencing with a primer annealing at a particular location" — is a `SpecificationSet` expanding to `UniquifyAllKmers(k=max_homology_length)` + `EnforceMeltingTemperature(tmin, tmax)` + `AvoidPattern(RepeatedKmerPattern(k, n))` for `((2,5),(3,4),(4,3))` + optional `AvoidHeterodimerization(other_primers, tmax=max_heterodim_tm)`. `AvoidHeterodimerization` and `EnforceMeltingTemperature` are separately available, and `primers_collection.py` documents building 20 mutually non-heterodimerizing 20-mers at ~60% GC, each new primer constrained against all previously accepted ones. **Limits:** these design/validate primer *annealing sites and sequences* de novo — no mutagenic-primer design (no NNK/degenerate mutagenesis primers), no assembly-oligo tiling, no protocol-aware oligo splitting for a variant library. Since the row is worded "mutagenic primer / oligo design for wet-lab protocols", the mutagenic arm is absent; `partial` is credited for the real, documented primer-sequence design machinery. **Practical limitation:** `primer3-py` is *not* a runtime dependency — PyPI `requires_dist` lists it only under `extra == "tests"` — so `AvoidHeterodimerization.evaluate` raises `ImportError("Using avoid_heterodimerization requires primer3 installed")` on a default `pip install dnachisel`, and the documented `primers_collection.py` example will not run out of the box. Neither `AvoidHeterodimerization` nor `EnforceRegionsCompatibility` can be declared as GenBank annotations.
*Source:* `builtin_specifications/AllowPrimer.py`, `AvoidHeterodimerization.py`; `examples/common_scenarios/primers_collection.py`; PyPI `dnachisel` JSON `requires_dist`; `docs/genbank/genbank_api.rst`.

**`codon_optimization` — yes.**
Core feature, confirmed at every level. `CodonOptimize` wrapper plus `MaximizeCAI`, `MatchTargetCodonUsage`, `HarmonizeRCA` and `AvoidRareCodons` in `dnachisel/builtin_specifications/codon_optimization/`, all exported from `__init__`, all listed in `docs/ref/builtin_specifications.rst`, in the README example and in paper Fig. 1A ("Gene NUM1 of Saccharomyces cerevisiae will be codon optimized for Escherichia coli"), with `EnforceTranslation` protecting the protein. Current DnaChisel depends on EGF's `python_codon_tables` (a listed runtime requirement) and accepts a species by name (`e_coli`, `h_sapiens`, `s_cerevisiae`, …) **or by NCBI TaxID** (`species=1423`), in which case frequencies are downloaded from Kazusa. `EnforceTranslation` gained alternative genetic codes (`genetic_table=`) and non-ATG start-codon policies (`start_codon=keep|ATG`) in v3.0.0, after the paper.
*Source:* `builtin_specifications/codon_optimization/`; `docs/ref/builtin_specifications.rst`; `README.rst`; paper Fig. 1A; PyPI `requires_dist`; `changes.md`.

**`synthesis_constraints` — yes.**
Unambiguously the tool's core purpose, and the row is scoped to individual sequences, which is exactly DNA Chisel's unit of work. README (verbatim): sequences can be optimized to "meet the constraints of a commercial DNA provider, avoid homologies between sequences, tune GC content". Specifications: `AvoidPattern` (restriction sites, homopolymers such as `6xA`, repeated k-mers such as `3x2mer`, IUPAC patterns, regexes), `AvoidHairpins` (per IDT guidelines), `EnforceGCContent` (global and windowed), `EnforceTerminalGCContent`, `UniquifyAllKmers`, `AvoidMatches` (Bowtie) / `AvoidBlastMatches` (BLAST), `SequenceLengthBounds`, plus the user-defined Gen9 9-mer synthesis-score example. Batch QC exists via `constraints_breaches_dataframe(constraints, sequences)`, which accepts `[(name, seq), …]`, a dict, or Biopython records and exports to Excel with `breaches_records_to_pdf`. Enforcement itself is per-sequence.
*Source:* `README.rst`; `docs/ref/builtin_specifications.rst`; `dnachisel/reports/constraints_reports/constraints_breaches_dataframe.py`.

**`degenerate_iupac_codons` — partial.** *(new row; resolved by targeted raw-source re-check this round)*
Degenerate/IUPAC handling is genuinely first-class as a *specification*, and it genuinely *expands*. `EnforceSequence` — docstring read verbatim this round: *"Enforces a (possibly degenerate) sequence at some location. Shorthand for annotations: 'sequence'."*, with the parameter documented as "possibly degenerated, for instance ATTCGCGTYTTKWNAA" — carries `enforced_by_nucleotide_restrictions = True` and implements `restrict_nucleotides()` by returning, per position, the allowed nucleotide set `IUPAC_NOTATION[self.sequence[i - lstart]]` (reverse-complemented per base on the minus strand). That set *is* the `MutationSpace`, so each IUPAC letter is expanded into concrete alternatives that `space_size` can count and `all_variants` can enumerate — degenerate-string → concrete-variant expansion, in-tool, with a GenBank shorthand (`@sequence(…)`). `evaluate` checks membership via `nuc not in IUPAC_NOTATION[self.sequence[i]]`. Supporting IUPAC infrastructure is exported from `dnachisel.biotools`: `IUPAC_NOTATION`, `NUCLEOTIDE_TO_REGEXPR`, `OTHER_BASES`, `dna_pattern_to_regexpr` (so `AvoidPattern`/`DnaNotationPattern` accept IUPAC patterns), plus `get_backtranslation_table` (degenerate codon mappings) and `reverse_translate`. **Why not "yes":** the row is *codon*-oriented and DNA Chisel's degeneracy is nucleotide-oriented. There is no degenerate-codon library design (no NNK/NNS/NNB mutagenesis-codon primitive, nothing named or documented as a degenerate codon library), and no **compression** — no facility that takes a set of desired variants/residues and emits the minimal degenerate codon or degenerate oligo covering them. Crucially, a degenerate `EnforceSequence` is *resolved down to one concrete sequence* by the solver; DNA Chisel never emits a degenerate oligo for ordering. `EnforceChoice` is the explicit-alternatives route and is not degenerate at all — its docstring requires a "List of same-length ATGC sequences, e.g. ['ATT','ATC','ATA']".
*Source:* `dnachisel/builtin_specifications/EnforceSequence.py` (raw source read 2026-08-10); `dnachisel/builtin_specifications/EnforceChoice.py` (raw source read 2026-08-10); `dnachisel/biotools/__init__.py` exports (read 2026-08-10); `docs/genbank/genbank_api.rst`; `docs/ref/builtin_specifications.rst`.

**`negative_control_generation` — no.** *(new row; resolved by targeted raw-source re-check this round)*
Nothing in DNA Chisel is a control-generation feature. `dnachisel/biotools/random_sequences.py`, read verbatim this round, defines exactly two functions — `random_dna_sequence(length, gc_share=None, probas=None, seed=None)` and `random_protein_sequence(length, seed=None)` — and **no shuffle, scramble, or dinucleotide-preserving shuffle exists anywhere in the module or in the `dnachisel.biotools` export list**. `reverse_complement` and `complement` are exported, but as sequence utilities used internally (e.g. `EnforceSequence.restrict_nucleotides` on the minus strand), not as a control-generation feature; there is no reverse-complement-control specification, no paired control emission, and no "control" terminology in the docs TOC, the built-in specification list, or the GenBank annotation vocabulary. The de-novo generators `random_dna_sequence` / `random_compatible_dna_sequence(length, constraints, …)` could of course be *used* by a user to make random controls, but that is an unlabelled single sequence produced by a general-purpose helper, with no pairing to a designed sequence and no control semantics — and since there is no library, a control cannot be a member of anything. Recorded as `no` rather than `partial` because the row requires this "as a first-class feature".
*Source:* `dnachisel/biotools/random_sequences.py` (raw source read 2026-08-10); `dnachisel/biotools/__init__.py` exports (read 2026-08-10); `dnachisel/utils/utils.py`; `docs/ref/biotools.rst`; `docs/ref/builtin_specifications.rst`.

**`ml_model_in_loop` — no.**
No predictive model drives design, and none ships. Every built-in objective is a biochemical or manufacturing score — CAI, codon-usage matching, RCA harmonization, GC content, terminal GC, melting temperature, hairpins, k-mer uniqueness, Bowtie/BLAST homology, restriction sites. The runtime dependency list contains no ML framework (numpy, biopython, proglog, docopt, flametree, python_codon_tables), and no example, docs page or paper section involves a trained predictor. Two things stated openly so a referee cannot claim we hid them, neither of which makes this row `partial`: (i) `MotifPssmPattern` scores sequences against a position-specific scoring matrix, and `sequence_without_tf_binding_sites.py` downloads real E. coli TFBS matrices — but a PSSM here is a *pattern matcher used for avoidance*, not a predictor whose output is optimized toward; (ii) DNA Chisel is explicitly extensible — a user can subclass `Specification` with a custom `evaluate(problem) -> SpecEvaluation` and the stochastic/exhaustive solver will optimize it, and the shipped `gen9_9mer_score_minimization.py` does exactly this with an external lookup-table synthesis score, so an ML predictor *could* be wrapped in ~20 lines. That is a generic extension point available in almost any extensible tool, not a model-in-the-loop capability, and crediting it would erase the row's discriminating power against tools built for this (ledidi, tangermeme). If the matrix intends the row as "can a predictive model be plugged into the optimization loop by the user", the value flips to `partial`; that reading is named here rather than suppressed.
*Source:* `docs/ref/builtin_specifications.rst`; `docs/ref/core_classes.rst` (pattern classes); `examples/common_scenarios/{gen9_9mer_score_minimization,sequence_without_tf_binding_sites}.py`; PyPI `dnachisel` JSON `requires_dist`; paper (full text).

**`readout_analysis` — no.**
DNA Chisel never touches sequencing data. There is no FASTQ/BAM/read input anywhere (`load_record` handles genbank/fasta/SnapGene only), no read counting, no demultiplexing, no per-variant abundance or enrichment analysis, no alignment of reads to designed members, and no such module in the `dnachisel/` tree (`DnaOptimizationProblem/`, `MutationSpace/`, `SequencePattern/`, `Specification/`, `biotools/`, `builtin_specifications/`, `reports/`, `utils/`, `Location.py`, `cli.py`). The analysis-shaped features are design-time QC of sequences the user supplies — `constraints_breaches_dataframe(constraints, sequences)` → DataFrame/Excel and `breaches_records_to_pdf` — plus the per-sequence optimization report. Since there is no built library, there is no readout to analyse.
*Source:* GitHub `master` tree; `dnachisel/biotools/genbank_operations.py`; `dnachisel/reports/constraints_reports/`; `docs` TOC.

## 4. How the new and split rows were resolved

- **Renames carried unchanged.** `dag_chaining` → `composable_operations` (partial) and `lazy_evaluation` → `lazy_generation` (partial). Neither new wording changes the answer; both evidence fields were re-read against the new question and a "why not yes" clause added. `composable_operations` is the one where the new wording arguably helps DNA Chisel — "vs a fixed pipeline" is a bar DNA Chisel clears, since a problem is an arbitrary user-composed spec list — so the reason for stopping at partial is now stated explicitly (what composes are constraints on one sequence, not sequence-producing steps).
- **`library_as_object` (no) split.** `library_first_class_object` = no and `library_algebra` = no. DNA Chisel was one of the tools scored a flat `no` on the old row rather than partial, so the split does not change anything, but both halves are now argued separately: no object holds a set; and combining/sampling/repeating whole libraries is provably external (user Python lists + Biopython in the shipped genome-wide and primer-collection examples).
- **`mixed_mutagenesis_one_pool` (no) split — the split is informative here, and two children move up.** The final memo's own verdict was "the missing thing is the pool, not the primitives", so scoring all four children `no` would understate the tool and be refutable in one sentence by an author-referee. Resolution: `sampled_random_mutagenesis` = **partial** (`pick_random_mutations`/`apply_random_mutations(n, seq)` are documented public API that sample the constrained space in one call; `EnforceChanges(minimum_percent=70)` is a real rate knob with GenBank shorthand); `higher_order_combinatorial` = **partial** (the mutation space is `itertools.product` over all mutable slots, so multi-site combination is intrinsic, and `apply_random_mutations(n, …)` / `EnforceChanges(minimum=3)` request n simultaneous changes); `exhaustive_single_scans` = **no** (no position sweep in-tool — the sweep is a user loop over narrow-location problems — and no deletions at all, since DNA Chisel is length-preserving and `EnforceChoice` requires "same-length ATGC sequences"); `heterogeneous_components_one_library` = **no**, which is where the old row's verdict genuinely lives (no pool, no regime labels, no WT/control members, no per-variant records).
- **Consistency rule used for the partial/no boundary on the split rows,** stated so it can be applied identically to the other 11 tools: `partial` if one in-tool call performs the operation on the mutation space; `no` if the operation only happens because the user wrote the loop. This is the same rule ROWS_v2 states for `library_algebra`, and it is what distinguishes `sampled_random_mutagenesis`/`higher_order_combinatorial` from `exhaustive_single_scans`.
- **`hgvs_input` dropped**, not output.
- **Four new Block D rows.** The memo did not address these head-on, so four raw source files were re-read this round (`EnforceSequence.py`, `EnforceChoice.py`, `biotools/__init__.py`, `biotools/random_sequences.py`). Result: `degenerate_iupac_codons` = partial (real IUPAC specification and real per-position expansion into the mutation space via `restrict_nucleotides` + `IUPAC_NOTATION`, but nucleotide-level not codon-level, no NNK/degenerate-codon library primitive, no compression, and the degenerate spec is resolved to one concrete sequence rather than emitted as a degenerate oligo); `negative_control_generation` = no (no shuffle/scramble anywhere; `reverse_complement`/`complement` are internal utilities; random generators are not control features); `ml_model_in_loop` = no (no model ships, no ML dependency, PSSM is used for avoidance; the custom-`Specification` hook is generic extensibility and crediting it would erase the row's discriminating power — the alternative reading is named in the evidence); `readout_analysis` = no (no sequencing-data path of any kind).
- **Three new Block E rows.** `installable_today` and `last_activity` unbundle the old `maintained` = yes, which mixed "you can install it" with "it is being worked on". Both are `yes` with the real answer in the evidence: pip-installable today at v3.2.16 under MIT, with the primer3/Bowtie/BLAST caveats named; last release and last `master` commit both 2025-05-10, ~15 months stale, non-master push 2025-11-05 — "maintained, not currently in active development". `documented_examples` is `yes` with a count: 8 docs examples, ~24 repo scripts, full API + GenBank reference, plus a documented determinism contract.
- **`barcode_generation` keeps its definitional fork verbatim** from the final memo (partial under "primitives sufficient to build a barcode set", no under "demux-ready generator bound to library members"). Recorded as partial — the reading that gives the competing tool full credit — with the narrow reading named. Nothing is recorded as `unknown`.

## 5. Confidence flags (for human review)

Liberally flagged. Ordered most to least likely to be challenged.

1. **`ml_model_in_loop` = no** — the judgement call most open to challenge. DNA Chisel's `Specification` interface is a documented extension point and the shipped `gen9_9mer_score_minimization.py` plugs an external scoring function into the solver loop; a referee can fairly say "any predictor drops in here". Scored `no` because no model ships and no ML dependency exists, and because crediting generic extensibility would erase the row. Flip to `partial` if the matrix intends "user can plug a predictor in".
2. **`exhaustive_single_scans` = no** — the split-row call most open to challenge, and the one that is asymmetric with its two `partial` siblings. `all_variants` over a narrow location does exhaustively enumerate substitutions there; the "no" rests on the absence of a position sweep and of deletions. If the matrix reads this row as "can the tool exhaustively enumerate single substitutions at a chosen position", it is `partial`.
3. **`sampled_random_mutagenesis` = partial** and **`higher_order_combinatorial` = partial** — both are upgrades relative to the v1 parent row's `no`, both rest on the same `MutationSpace` public-API argument the review used to move `lazy_evaluation` to partial. If the matrix requires that a *set* of sampled or higher-order variants be emitted, both become `no`. Needs a consistency check against how the other 11 tools' split rows were scored.
4. **`degenerate_iupac_codons` = partial** — hinges on whether the row means degenerate *codon* design (NNK-style, or compressing residue sets into degenerate codons — DNA Chisel has neither) or degenerate *sequence* specification with expansion (DNA Chisel clearly has this). Read verbatim from source this round, so the facts are solid; the value is a definitional call.
5. **`composable_operations` = partial** — carried from `dag_chaining`, and generous-but-bounded on purpose. The new wording's "vs a fixed pipeline" framing arguably supports `yes`, since a DnaChisel problem is an arbitrary user-composed spec list and specs nest via `SpecificationSet`. Kept at partial because nothing composes *sequence-producing steps*. A referee could push either way.
6. **`lazy_generation` = partial** — the deliberate concession from the review round; a flat `no` is refutable in one sentence because `all_variants` is a documented public generator. Retained. Under a strict "lazy materialization of a library" reading it is `no`.
7. **`barcode_generation` = partial** — the openly stated definitional fork. Facts agreed by all three rounds; value depends on the row's definition.
8. **`per_sequence_provenance` = partial** and **`design_visualization` = partial** — both hinge on reading "per sequence" / "design" as "the one output sequence". Under a strict library-member reading both are effectively `no`.
9. **`negative_control_generation` = no** — confident on the facts (no shuffle/scramble function exists; verified in `random_sequences.py` and the `biotools` export list), less confident that a referee will accept `no` given `random_dna_sequence`, `random_compatible_dna_sequence`, `reverse_complement` and `complement` all exist and could be composed into controls by a user. Turns on "as a first-class feature".
10. **`primer_design` = partial** — carried; the row's wording is "mutagenic primer / oligo design" and the mutagenic arm is absent, but `AllowPrimer`/`AvoidHeterodimerization`/`primers_collection.py` are real enough that a flat `no` would be attackable.
11. **`installable_today` = yes / `last_activity` = yes** — the values are `yes` per the Block E convention, but neither was verified by execution (no installation performed, per instruction), and the CUBA web app's interactive behaviour was not exercised. The `primer3-py`-absent-by-default finding means a strict "does the documented example run out of the box?" reading of installability is "not entirely".
12. **`documented_examples` = yes** — the count (8 docs headings, ~24 repo scripts, 12 scripts covering ~9 specs in `builtin_specifications_examples/`) is the figure most likely to need a recount if the matrix wants a strict single number; also Supplementary S1A–S1E remains unobtainable.
13. **`library_first_class_object` = no / `library_algebra` = no / `heterogeneous_components_one_library` = no** — highest confidence in the whole record (absence checked against the docs TOC, the complete built-in-spec list, the complete GenBank annotation vocabulary, and the actual `dnachisel/` and `builtin_specifications/` listings). Flagged only to note that `constraints_breaches_dataframe(constraints, sequences)` accepting a set of sequences is the one fact a referee could reach for; it consumes a user-held set for QC and neither builds nor transforms a library.
