# pydna citation-integrity audit

Record audited: `25_poolparty_private/revision/tool_survey/final/pydna.md`

Repository baseline: [`pydna-group/pydna`](https://github.com/pydna-group/pydna) `master` commit `4e02f81dfd39629c68d2a93dfbb434bfe7d56120` (2026-08-01). I checked the complete repository tree, the hosted Sphinx index (820 parsed objects), the paper PDF extracted with PyMuPDF, PyPI/GitHub metadata, and the live URLs. Only evidence that was not verified is reported below.

## NOT FOUND IN ANY SOURCE

1. **Status: NOT FOUND IN ANY SOURCE — record lines 101–104, 602, and 736.** The absolute claims that there is “no ... collection class anywhere in the documented API” and that “no collection type appears” among the 820 documented objects are contradicted by the cited Sphinx object index. The same 820-object index contains `pydna.recombinase.RecombinaseCollection` and its four public methods, as well as `pydna.opencloning_models.OpenDNACollectionsSource`. `RecombinaseCollection` is a real class at `src/pydna/recombinase.py:391–426`. This finding concerns the literal cited API inventory; it does not assess whether either class is a sequence-library abstraction.

2. **Status: NOT FOUND IN ANY SOURCE — record lines 131–135 and 603.** “`CloningStrategy` is export-only” and the purported exhaustive method list are contradicted by both `src/pydna/opencloning_models.py:1304–1404` and the cited 820-object index. In addition to the listed export methods, the documented class has `get_ids_of_sequences_that_are_inputs()`, `get_ids_of_sequences_that_are_not_inputs()`, `to_dseqrecords()`, `normalize()`, and `validate()`. `to_dseqrecords()` reconstructs `Dseqrecord` objects and their source trees from a serialized strategy; `validate()` calls it and then calls `validate_history()`, replaying the embedded operations against their original inputs. This does not establish parameterization over new inputs, but it makes the cited “export-only” API description false.

3. **Status: NOT FOUND IN ANY SOURCE — record lines 494–495.** The quotation attributed to `utils.cai()` — “Calculates codon adaptation index for a sequence relative to an organism” — occurs nowhere in the current repository, hosted documentation index, or paper. The actual docstring at `src/pydna/utils.py:225–226` is only `"""docstring."""`. The implementation does calculate CAI, but the purported documentation quotation is invented.

4. **Status: NOT FOUND IN ANY SOURCE — record lines 495–496.** The quotation attributed to `utils.rarecodons()` — “Identifies rare codons within a coding sequence” — likewise occurs nowhere in the current repository, hosted documentation index, or paper. The actual docstring at `src/pydna/utils.py:235–236` is only `"""docstring."""`. The implementation does return rare-codon slices, but the quoted documentation does not exist.

## Other non-verified evidence

1. **Status: minor-discrepancy — record line 4.** The quoted full name capitalizes the final word as “Python.” The paper title and the repository citation both say “using python” with lowercase `python`. This is capitalization-only, but the text in quotation marks is not verbatim.

2. **Status: minor-discrepancy — record lines 87–90.** The assembly-backend inventory uses the apparent function names `homologous_recombination_.../inversion` and `cre_lox_.../inversion`. No separate `homologous_recombination_inversion` or `cre_lox_inversion` functions exist. The implemented names are `homologous_recombination_excision_or_inversion()` (`assembly2.py:2876`) and `cre_lox_excision_or_inversion()` (`assembly2.py:2987`), plus deprecated excision-only wrappers. The same inventory also omits current top-level backends such as `crispr_integration()`, `recombinase_integration()`, and `recombinase_excision_or_inversion()`.

3. **Status: minor-discrepancy — record lines 181–187 and 606.** The unqualified statements that `Assembly` enumerates “all” linear/circular/insertion paths and “all valid orders and orientations” overstate the cited implementation. `Assembly(..., use_fragment_order=True)` defaults to considering only linear assemblies that start with the first fragment and end with the last (`assembly2.py:1224–1226,1264–1271,1451–1474`). Public assembly methods default to `max_assemblies=50`, and cycle enumeration is guarded at 10,000 paths. Broader enumeration is available with different settings and within the guards, but “all” is not the unconditional behavior cited.

4. **Status: minor-discrepancy — record lines 268–270.** The claim that a PCR product inherits a feature label “when a feature fully spans the amplicon” does not match `src/pydna/amplify.py:364–375`. The auto-name code selects only a feature whose location starts at 0 and ends at `len(self.template)`, meaning a feature spanning the entire template, not merely one spanning a partial amplicon.

5. **Status: minor-discrepancy — record lines 290–291.** `pydna.gel.gel()` does not render “via PIL/matplotlib.” Its implementation imports NumPy and PIL, uses SciPy for interpolation, and contains no matplotlib import or call (`src/pydna/gel.py:11–102`). Matplotlib is used by `Contig.figure_mpl()`, the preceding and separate visualization mechanism.

6. **Status: number-wrong — record lines 430–436.** The claimed “single repo-wide code-search hit” for `hgvs` is wrong. A case-insensitive search of the exact cited commit finds **31 occurrences in two tracked files**: one in `tests/pUC_LAC4_correct_rotation.gb` and 30 in `docs/notebooks/gibson_eg.gb`. They are incidental sequence substrings rather than an HGVS parser, and the separate claim of zero `hgvs` terms in `searchindex.js` is verified; only the repository-wide count is wrong.

7. **Status: misquoted — record lines 445–449.** `seqrecord.isorf()` is glossed in quotation marks as “is this an ORF?” That phrase does not occur in the source or hosted docs. Its actual docstring begins “Detect if sequence is an open reading frame (orf) in the 5'-3' direction” (`src/pydna/seqrecord.py:145–160`). The record presents a paraphrase as a quotation.

8. **Status: misquoted — record lines 453–456.** The `primer_design()` quotation is not verbatim. The actual docstring is: “This function designs a forward primer and a reverse primer for PCR amplification of a given template sequence.” (`src/pydna/design.py:83–84`). The record changes this to “Designs forward and reverse primers for PCR amplification of a template sequence.”

9. **Status: misquoted — record lines 499, 621, and 759–760.** `utils.express` is repeatedly quoted as “Not yet implemented.” Its actual source text is `**NOT IMPLEMENTED YET**` (`src/pydna/utils.py:248–252`). The substance is supported because the function raises `NotImplementedError`, but the quoted word order is not verbatim.

10. **Status: minor-discrepancy — record lines 494–500 and 621.** The claim that the `utils.py` functions are “surfaced as” the corresponding `Seq` methods is inaccurate for `express`. `utils.express()` is the unimplemented function above, whereas `Seq.express()` is a separate, implemented method at `src/pydna/seq.py:172–202` that returns a populated `PrettyTable`; it does not call `utils.express()`. The summary-table shorthand `express "Not yet implemented"` can therefore misattribute the status to the implemented public `Seq.express()` method.

11. **Status: number-wrong — record lines 569–578 and 624.** “Every source file ... carries `SPDX-License-Identifier: BSD-3-Clause`” and “SPDX headers in every file” are false. Of the 40 tracked top-level `src/pydna/*.py` files, 39 carry BSD-3-Clause, while `src/pydna/threading_timer_decorator_exit.py:3` carries `SPDX-License-Identifier: MIT` and includes the MIT license. The file is live code imported by `src/pydna/assembly.py:61`.

12. **Status: number-wrong — record lines 592–594 and 775–778.** “67 open issues” is the GitHub repository API aggregate `open_issues_count`, which includes pull requests. The [live repository](https://github.com/pydna-group/pydna) currently splits the same aggregate into **61 open issues and 6 open pull requests**. Thus 67 is verified as issues-plus-PRs, not as an issue count.

13. **Status: wrong-location — record lines 653–656.** The heading “From the 2015 paper (files still shipped in `docs/cookbook/`)” is accurate for the YEp24PGK_XK and pGUP1 assets but not for the lactose-pathway bullet beneath it. The current `docs/cookbook/` tree contains no set of nineteen lactose scripts and no `pYPK0_PDC1tp_KlLAC4_PGI1tp_KlLAC12_TPI1tp.py`. The paper places those scripts in **Additional file 2**, which remains available with the paper ([CaltechAUTHORS record](https://authors.library.caltech.edu/records/k4rpm-ef941/latest)).

14. **Status: minor-discrepancy — record lines 765–766.** The paper's Google Code source URL is classified as a dead link, but `https://code.google.com/p/pydna/` redirects to the live archival page `https://code.google.com/archive/p/pydna` (HTTP 200). It is obsolete as an active project host, but it is not dead. The appspot console and Dropbox/nbviewer URL were independently confirmed dead.

15. **Status: minor-discrepancy — record lines 592–594 and 775–786.** The GitHub `pushed_at` field is mutable and no longer matches the recorded `2026-08-10T08:46:14Z`; the current [repository API](https://api.github.com/repos/pydna-group/pydna) reports `2026-08-11T14:09:17Z`. More importantly, the record's own snapshot cites a 2026-08-10 push and then calls 2026-08-01 “Last activity: 10 days before this survey.” If a repository push counts as activity, the cited date is one day before the 2026-08-11 survey, not ten. The commit date itself is verified.
