## 2. What the tool actually is

Four independent Django web forms, one HTTP POST each, each returning an entire oligo library in FASTA (embedded in an HTML results page by default; plain text on download):

1. **MPRA Motifs** — substitute up to 4 motifs into background scaffolds in all subsets × all permutations × all admissible position tuples, with spacing/edge constraints and an interval of substitution.
2. **MPRA SNPs** — substitute SNPs (and indels ≤10 nt) into coordinate-annotated scaffolds; emits variants, a `| REFERENCE` WT entry, and optional SNP combinations.
3. **Transmutation** — scramble / reverse / complement / N random point mutations, "therefore serving to generate negative controls for the MPRA SNP and Motif design tools" (Supp. §2.3).
4. **PWM Seq-Gen** — convert PWMs to k-mers, either by probabilistic simulation or by exhaustive enumeration above a probability threshold; "The output of PWM Seq-Gen can be inputted into MPRAs Motifs tool" (live docs).

Motifs and SNPs additionally assemble a modular oligo (barcode / background / 2 restriction sites / 2 adapters) whose component order is set by a jQuery-UI drag-and-drop list.

**Structural fact that drives half the matrix:** there is no object, no importable library API (the repo's modules are undocumented Django internals), no CLI, and no package. The user-facing representation of a designed library is FASTA embedded in an HTML results page or downloaded as a plain-text file.

**Live deployment:** the Motifs and SNPs forms submit a JS-generated `ordering` field that is not a static `<input>` in the served HTML (Transmutation and PWM Seq-Gen have no such field and no such JavaScript). A POST that omits `ordering` reaches the generator and returns **HTTP 500** rather than a validation error. This input-robustness defect makes the "REST API" undocumented-field-sensitive.

## 4. Additional capabilities NOT covered by the current row list

Candidates for new matrix rows, or at minimum footnotes so a referee cannot say we ignored what MPRAnator does well.

1. **PWM → sequence generation, in two modes.** Probabilistic realisations of a PWM, or exhaustive enumeration of all k-mers exceeding a user probability threshold (Supp. §2.4). Nothing in Blocks A–E captures "motif sampling/enumeration from a PWM". **Both modes verified working live 2026-08-10.** Live bounds: threshold 0–1 (default 0.1) and 1–1000 simulations (default 1).
2. **Per-k-mer PWM probability reported in the output header** *(ADDED on review)* — `> MA0056.1 MZF1_1-4 | Prob : 0.10965375000000001`, verified live in exhaustive-threshold mode; Supp. §2.4: the header "contains information regarding the probability of each k-mer occurring". A quantitative per-sequence score attached to a designed sequence.
3. **IUPAC / degenerate-base awareness throughout the tool** *(ADDED on review — entirely absent from the extraction)*. `myfunctions.regex_mapper` expands R/Y/S/W/K/M/B/D/H/V/N into regex character classes (`'R': '[A|G]'`, `'N': '[A|T|G|C]'`, …), so **restriction-site collision matching is degenerate-code aware** (motif placement itself is plain string substitution and does no matching — `findMatch`/`regex_mapper` are reached only from the duplicate-restriction-site check); `myfunctions.mapperDict` defines legal substitutions for every IUPAC code (`"M": 'GT'`, `"W": 'GC'`, …) so `part3.mutateString` mutates degenerate positions consistently and **explicitly skips `N` positions** (`while sequenceS[posChosen] == "N" or posChosen in positionsChosenL`), refusing an all-N input ("Please do not enter a string only containing N"); `myfunctions.complement` carries a complement map for all 15 DNA ambiguity codes, though it maps `S`↔`W` rather than each to itself. Live docs state it plainly: "The input will accept all nucleic acid IUPAC letters." The coverage is not in fact complete: `U` is in neither `mapperDict` nor the complement map, and a live Transmutation submission of `AUGC` was rejected with "Invalid letters!" on 2026-08-14.
4. **Negative-control / scramble generation as a first-class feature.** Scramble, reverse, complement, and N random point mutations (Transmutation), with the choices recorded in the header. Each submission yields one random realisation per input sequence — the scramble is a mononucleotide shuffle, the operations are applied in the fixed order scramble → reverse → complement → point mutation, and there is no seed and no replicate-count control. A `negative_control_generation` row would be a fair addition — this is genuinely a capability PoolParty should be compared on.
5. **Modular oligo assembly with user-orderable sub-components** (2 adapters, 2 restriction sites, barcode, background) via drag-and-drop. Ordering vocabulary from the shipped API scripts: `Barcode, Background, restriction site 1, restriction site 2, adapter site 1, adapter site 2`. Distinct from `combinatorial_motif_place`.
6. **Restriction-site collision reporting in the assembled oligo** (`DUPLICATE_RESTRICTION_SITES`) — a cloning-compatibility check rather than a synthesis check; partially credited under `synthesis_constraints`.
7. **Indel handling with length normalisation** — insertions/deletions up to 10 nt from the VCF input, with automatic A-padding or edge-trimming to keep all oligos equal length, and the operation recorded in the header. Verified live in both directions.
8. **Barcode replicates / sequence multiplicity** — N distinct-barcode copies of every designed sequence in one pass. Supp. §2.1: "the user can select the multiplicity of each sequence to optimize the experiment."
9. **Reference/WT sequences emitted alongside variants** in the SNP module (`| REFERENCE` header), without the user asking for it. Verified live.
10. **Library-level duplicate removal in PWM Seq-Gen** *(ADDED on review)* — live form field `dupMotifs`; docs: "Remove duplicates: Allows users to either keep only unique Sequence Motifs or include Duplicates as well"; Supp. §2.4: "If duplicates are present the user can select to remove duplicates in the output." Relevant if the matrix gains a dedup/uniqueness row.
11. **Input QC checks** *(ADDED on review)* — `mycustom.FastaFile.areDuplicatesPresent()` and `lengthsSame()`. The latter is user-visible and a real design constraint (the Motifs module requires all scaffolds be the same length); verified live: unequal-length input → "Sizes of the sequences should be the same".
12. **BED coordinate-centering helper script** — converts arbitrary intervals into equal-sized windows centered on the original, X nt each side (offered on the homepage). *Currently undownloadable: the download endpoint returns HTTP 500.*
13. **SNP module doubles as a plain assembly tool.** Supp. §2.2: "the MPRAnator SNP design tool can accept a set of FASTA sequences without a list of associated SNPs and perform their incorporation into the user-designed constructs. This is particularly useful if the regulatory role of existing sequences is being investigated."
14. **Hard library-size caps** — a *limitation*, but worth a row if the matrix ever gains one on scalability. See §6 for the values and the repo-vs-live caveat.

## 5. Scoring conventions this record relies on (must be applied uniformly across all tools)

- **C1 — `maintained` threshold** (identical to the convention written into `final/codongenie.md`): `yes` = a human commit or a release within ~2 years of the survey date; `partial` = 2–5 years dormant but public, unarchived and still installable/runnable; `no` = >5 years dormant, archived, or unavailable. MPRAnator (single commit 2015-12-27, ~10.6 y) = **no**. The codongenie review flagged the identical convention problem and resolved it the same way; this is now settled cross-tool.
- **C2 — "ships in the package" vs "user-facing".** A capability present in code but unreachable from the tool's own UI/API scores `partial`, not `yes`. Not load-bearing for MPRAnator (everything scored here is user-reachable in principle), but stated for cross-tool consistency.
- **C3 — generous reading on borderline scope cells.** Where a tool performs a genuine, user-visible sub-step of a row's capability but not the full capability, score `partial` with an explicit scope note rather than `no`. Affects `library_as_object`, `dag_chaining`, `per_sequence_provenance`, `design_visualization`. Under a strict reading all four would be `no`; extractor and reviewer independently agreed `partial` is the referee-safe posture, and it must be applied to the other web-only tools in the survey identically.
- **C4 — declared-but-unshipped license.** Where a paper names a license but the repository ships no LICENSE file, score `license = partial` and record both facts. This is the honest reading: `yes` asserts a license file that does not exist; `no` denies the authors' own public declaration.
- **C5 — capability value vs. live outage.** A capability that is designed, documented and implemented keeps its value even if the deployed service currently errors; the outage is recorded in `availability_status`. This is why `barcode_generation` stays `yes` despite every barcode-enabled request returning HTTP 500 today.

## 6. Stated and material limitations

**Repo-derived caps** (`iliasApp/forms.py`, 2015 — label them as repo values, **not** as the live tool's limits): `motifs⁴ × sequences ≤ 100` ("Only a maximum of %s motifs^4*sequences allowed"); ≤1000 input sequences (Motifs) / ≤50000 (SNPs); ≤20000 nt per sequence; `numOfBarCodesPerSequence` 1–5; barcode length ≥10. The 2015 result view then truncates silently below those caps, to the first 20 background records and the first 800 nt of each (`views.py`: `sequenceO[:20]`, `i.sequence[:800]`), and the same form permits a substitution interval of 0, which `oligo.py` uses as a modulus divisor. **The live deployment does not enforce these identically** — the live forms accept `numOfBarCodesPerSequence` 0–100 and `barCodeLength` 10–25 (Motifs), and 4 motifs × 1 sequence (=256, over the repo cap) passes validation and reaches the generator. **Never quote "≤5 barcodes per sequence" as MPRAnator's limit** — the tool's own worked use case asks for 6.

**Structural / documented limitations:**
- ≤4 motifs per design, ≤2 restriction sites, ≤2 adapters. Indels: the Supplementary says "up to 10nt", but the code generates only `abs(len(REF) − len(ALT)) < 10` and the form separately rejects any ALT longer than 10 characters — verified live 2026-08-14, a 9-nt insertion is emitted and a 10-nt one is not.
- Motif orientation is a single global scaffold-level `reverseComplement` toggle, not per-motif orientation enumeration.
- The Motifs module requires **all input scaffolds to be the same length** ("Sizes of the sequences should be the same").
- Chromosome validation in `SnpFile` is hard-coded **human-only** (1–22, X, Y).
- The SNP parser wants ≥5 whitespace-separated columns with a bare chromosome token and no `#` header line; it never checks the supplied REF against the background, and any background sequence with no in-range variant is dropped from the output entirely (verified live 2026-08-14).
- No reference genome is ever read — the user must supply the actual sequence.
- The barcode "Levenshtein distance" is implemented as a **Hamming-style** position-wise identity count.
- Everything is materialised eagerly into one in-memory string, which is why the caps exist at all.
- The public repository is a **development snapshot that predates the published tool** — no PWM Seq-Gen code. The deployed source is not public.
