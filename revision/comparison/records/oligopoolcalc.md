**The load-bearing structural fact (verified, unrebuttable):** across all 22 modules there is **no row-union / sub-library concatenation operator**. `merge` "Concatenate[s] contiguous **columns** into a single column" (api.md L427). `join` requires that "`ID` sets must match exactly across both inputs (order can differ)" (api.md L563) and "`join` never creates or drops rows; mismatched IDs are an error" (api.md L567; docs.md L729 restates it). **No shipped operation can therefore union two independently designed tables into a single pool of rows** — the only row-count changes available are `compress` (collapses variants into fewer degenerate oligos) and `expand` (enumerates them back), both acting within one library. This is the cleanest contrast with PoolParty and cannot be rebutted by pointing at an example script.

## 3. The file the original extraction missed

`examples/library-compressor/mutant_generator.py` — 8,431 B, module docstring header `Author: Ayaan Hossain`, docstring: *"Mutant Generator for Degenerate Mode Demonstration … Includes: Single nucleotide mutants (educational - shows poor compression case) / Codon variants at a specific position (shows good compression) / Combinatorial variants at multiple positions (best compression demo)."*

Read in full. It contains:

- `CODONS = [''.join(c) for c in itertools.product(DNA_BASES, repeat=3)]` — all 64 codons.
- `generate_single_mutants(sequence, include_wildtype=True)` — all 3L single-nucleotide mutants, **auto-minting ref-position-alt variant IDs**: `variant_id = f'{ref_base}{pos + 1}{alt_base}'` → `A5T` (no source calls this HGVS, and it is not HGVS syntax, which requires a coordinate-type prefix and `>`, e.g. `c.5A>T`). Yields `(variant_id, mutant_seq, pos+1, ref_base, alt_base)`.
- `generate_codon_variants(sequence, codon_position, include_wildtype=True)` — all 64 codons at one codon position, IDs `f'{wt_codon}_{codon}'` → `ATG_AAA`.
- `generate_multi_position_variants(sequence, positions, include_wildtype=True)` — all `4**len(positions)` combinatorial variants, IDs `'_'.join(f'p{p+1}{b}' ...)` → `p1A_p5C`.
- All three are Python **generators** (`yield`, typed `Generator[...]`).
- `generate_variant_dataframe(sequence, strategy='codon', codon_position=0, positions=None, ...)` wraps them into a `DataFrame` with columns `ID`, `Sequence`. **`strategy` is a single string — `'single'`, `'codon'`, or `'multi'` — so exactly one strategy per call; there is no way to express a mixed specification.**

**Why the values still stand:** this is a worked example shipped alongside the compression demo, not part of the `oligopool` package API (`op.*` exposes no such function; the 22 modules in api.md contain nothing of the kind). But four of the original evidence strings were worded as blanket absences that this file falsifies, and all four have been rewritten below.

## 4. Capability-by-capability (FINAL values)

*Rule used for `yes` vs `partial` in Block B (state this in the table caption):* **`yes` = demonstrated end-to-end on published libraries of that assay type, with shipped tooling for it; `partial` = documented recipe only, with the assay-specific variant content supplied by the user.*

### Block A — library specification

**`library_as_object` = partial.**
*Evidence:* The library is a plain **pandas DataFrame / CSV**, not a dedicated library class. docs.md "Core Concepts → The DataFrame Flow": *"**Input**: CSV path or pandas DataFrame with an `ID` column … **Chainable**: Output of one module feeds into the next."* Design/transform modules have the signature `(input_data, ..., output_file) -> (DataFrame, stats)` (five stats-only modules — `background`, `lenstat`, `inspect`, `index`, `pack` — return `stats` alone, and `background`/`inspect` do not take an `input_data`/`output_file` pair under those names; docs.md L140–L156); there is no library class anywhere in `oligopool/**/*.py`. Every module operates on the *whole table at once*, so the user never loops over sequences — that part is genuinely first-class. But there is no object carrying design semantics: the "library" is the accumulated set of columns, and `final` reduces it to `ID`, `CompleteOligo`, `OligoLength` (api.md L613: *"output contains `ID`, `CompleteOligo`, `OligoLength` only"*), after which docs.md L764 warns verbatim: *"Save your annotated design DataFrame/CSV before `final` if you plan to `index`, `pack`, and count later."* Table-as-library, not library-as-object.
*Source:* docs.md "The DataFrame Flow", L764; api.md L613; all 22 module signatures in api.md.
*Note:* judgement call. `yes` ("a DataFrame *is* the whole library; no user looping") and `no` ("there is no library abstraction, just a table") are both arguable. `partial` is the defensible middle and is the generous reading.

**`dag_chaining` = yes.**
*Evidence:* Two mechanisms, both shipped.
(a) **CLI YAML pipelines with an explicit DAG.** docs.md §"Parallel Pipeline Execution" (L1630 ff.), verbatim: *"**Serial format**: a list of command names (`- primer`, `- barcode`, ...), which runs in listed order. **Parallel/DAG format**: a list of step objects with `name`, `command`, and optional `after`, which defines dependencies explicitly. **Mixed format (supported)**: you can mix strings and step objects in one list; if any dict-style step appears, DAG parsing is used…"* Execution model, verbatim: *"Steps with no `after` dependencies form level 1 (eligible to run concurrently). Each subsequent level waits for dependencies, and independent steps are grouped automatically for concurrent execution. `--dry-run` shows execution levels and parallelism."*
(b) **A runnable DESIGN-mode DAG example**, `examples/cli-yaml-pipeline/mpra_design_parallel.yaml` — steps `primer` → (`barcode_a` ∥ `barcode_b`, both `after: [primer]`) → `rejoin` (`command: join`, `after: [barcode_a, barcode_b]`) → `spacer` → `final`. Its own header comment: *"This example is intentionally 'mostly serial' with one parallel fan-out: two independent barcode branches are designed from the same backbone, then recombined with `join` into a single design table for downstream steps."* (Cite **this** file, not the analysis DAG, so a referee cannot say only the analysis case was found. `analysis_multi.yaml` also exists.)
*The caveat that must be kept verbatim in the response:* the DAG is an **execution/scheduling graph over design steps applied to one flat table**, not a **content-composition graph over library sub-populations**. Verified structurally: `join` requires "`ID` sets must match exactly across both inputs" and "never creates or drops rows; mismatched IDs are an error" (api.md L563, L567). The authors concede the design-side limit themselves: docs.md L1634 *"design workflows are often dependency-dense and mostly sequential"*, and the docs call design branch-join **"Rare"**.
*Source:* docs.md L1630–L1700, L729; api.md L563, L567; `examples/cli-yaml-pipeline/mpra_design_parallel.yaml`.

**`lazy_evaluation` = no.**
*Evidence:* Every module materializes its result — design/transform modules return `(DataFrame, stats)`, counting modules `(counts_df, stats)`, and the five stats-only modules (`background`, `lenstat`, `inspect`, `index`, `pack`) return a `stats` dict (docs.md L140–L156); the public API exposes no deferred or lazy evaluation anywhere. Grep for `lazy|generator|yield|iterator|on-demand` across README.md/docs.md/api.md/agent-skills.md returns no feature hits (the only literal `yield` hits — api.md L955, api.md L1257, agent-skills.md L247 — are ordinary-language "yield different barcodes" prose). Internal helpers under `oligopool/base/` do use Python generators, and `oligopool/__init__.py` lazily *imports* public names via `__getattr__`, but neither is a user-facing evaluation model. The one enumerating module, `expand`, is explicitly eager with a safety cap — docs.md L973–L974, verbatim: *"Expansion can be exponential (N positions = 4^N for all-N sequence)"* / *"Use `expansion_limit` as a safety cap for highly degenerate sequences."*
*Completeness note (state before a referee does):* the shipped example `examples/library-compressor/mutant_generator.py` **is** generator-based (`yield`, typed `Generator[...]`), but it is example code that feeds a DataFrame into the package, not the package's evaluation model.
*Source:* api.md (all module Returns lines); docs.md L973–L974; documentation-wide grep; `mutant_generator.py`.

**`mixed_mutagenesis_one_pool` = no.** **(Evidence rewritten.)**
*Evidence:* The `oligopool` **package** has **no mutagenesis module** — no `op.*` module derives variants from a mutation specification; variant content is a required user input. docs.md Quick Start: *"# Start with your variants"*; docs.md §Workflows L1304: *"Start with your variants in a CSV (must have an `ID` column)"*; the tutorial notebook is explicit: *"let us first generate a random library of 59-73 mers (**designing exact ribozymes is beyond the scope here**)."* agent-skills.md L371: *"Cost-efficient saturation mutagenesis | generate all substitutions → `compress` → order `synthesis_df` (6-20x fewer oligos)"* — "generate all substitutions" is the user's step.
**The repo does ship a worked-example helper** — `examples/library-compressor/mutant_generator.py` — that enumerates single-nucleotide mutants, all-64-codon saturation at one position, and 4^N multi-position combinatorial variants. It is example code, not `op.*` API, and **`generate_variant_dataframe(strategy=...)` accepts one strategy string per call (`'single'` | `'codon'` | `'multi'`)**, so no mixed-mutagenesis specification is expressible even there. Combined with the absence of any row-union operator (`merge` concatenates columns; `join` "never creates or drops rows"), two differently-mutagenized sets cannot be combined into one pool by any shipped operation.
*Source:* api.md module list; docs.md Quick Start, L1304; agent-skills.md L371; `examples/OligopoolCalculatorInAction.ipynb`; `examples/library-compressor/mutant_generator.py`; api.md L427, L563, L567.

**`combinatorial_motif_place` = no.**
*Evidence:* `motif` inserts **one** motif into **one** named column per call. api.md `motif`: one `motif_sequence_constraint` → one `motif_column`; `motif_type` ∈ {`0`/`'variable'` = a distinct sequence per row satisfying an IUPAC constraint, `1`/`'constant'` = a single anchor shared by all rows}. **No position, orientation, or motif-set enumeration parameter exists.** Multiple motifs require multiple chained `motif` calls at fixed column positions; there is no cross-product over motif sets. Paper §"Restriction Sites, Motifs, and Spacers": motifs are *"defined using the IUPAC degenerate nucleotide code"* and the pathfinder *"identifies an oligonucleotide-specific sequence solution that satisfies design rule #1"* — one solution per oligo, not a combinatorial expansion. `revcomp` reverse-complements a **contiguous column range for the whole table** and reverses column order — global, not per-variant orientation enumeration. The nearest thing to combinatorial content generation is `expand` (all concrete sequences from an IUPAC-degenerate string), but api.md states it is *"Primarily used as a verification tool to confirm `compress` output"* and docs.md L975 adds *"Does NOT recover original variant IDs."*
*Source:* api.md `motif`, `revcomp`, `expand`; paper §"Restriction Sites, Motifs, and Spacers"; docs.md L970–L977.

**`barcode_generation` = yes.**
*Evidence:* Flagship feature. Full verified signature (api.md L76–L120):
`op.barcode(input_data, oligo_length_limit, barcode_length, minimum_hamming_distance, maximum_repeat_length, barcode_column, output_file=None, barcode_type=0, left_context_column=None, right_context_column=None, patch_mode=False, cross_barcode_columns=None, minimum_cross_distance=None, excluded_motifs=None, background_directory=None, random_seed=None, verbose=True)`.
Constraints: minimum pairwise **Hamming distance**; `maximum_repeat_length` (`int`, ≥4) = *"Maximum shared repeat length between barcode and context/oligos"*; `excluded_motifs` accepting *"a list, CSV/FASTA path, DataFrame with `Exmotif` column, comma-string, or multiple sources (list of sources or `{name: source}` dict)"*; context/edge-effect awareness (*"At least one of `left_context_column` or `right_context_column` must be specified"*); `background_directory` k-mer screening (*"screened against ALL specified DBs; junction-aware when context columns are provided"*); cross-set orthogonality (`cross_barcode_columns` + `minimum_cross_distance`, *"each new barcode must be ≥`minimum_cross_distance` away from every barcode in the union"*); `patch_mode` for incremental fill; `random_seed`. **Two distinct algorithms** via `barcode_type`: *"`0`/`'terminus'`=fast terminus-optimized (targets distinctive 5'/3' ends), `1`/`'spectrum'`=thorough spectrum-optimized (targets k-mer saturation)."* The barcode is written as a column at its correct position in the oligo, i.e. genuinely attached, not merely enumerated. Paper: *"over four million highly unique and compact barcodes in 1.2 h."*
***One honest, verified gap — keep it:*** **there is no GC-content parameter for barcodes.** No GC and no sequence-constraint argument appears anywhere on `op.barcode`, and the paper's four stated barcode design criteria (PDF ¶"Barcodes") are: ≥1 barcode per variant; minimum pairwise Hamming distance for distinguishability; minimal length ("*not any longer, as oligonucleotide lengths are currently limited by synthesis processivity*"); and *"all barcode sequences must not contain homopolymer tracts that are challenging to sequence while also excluding a set of researcher-defined sequences, such as restriction sites."* **GC is never mentioned.** *Precise phrasing:* GC is **not constrainable for barcodes** — not "absent from the tool" — because GC content **is** computed and reported for primers (`primer_guanine_cytosine_content`, verified on **6 lines** of `oligopool/primer.py` — L542, L1070, L1176, L1245, L1321, L1347, 7 occurrences in all because L1245 carries it twice; api.md L1665 documents `guanine_cytosine_content` as a stats key term). For primers GC is also controllable indirectly through `primer_sequence_constraint` (docs.md L471: *"GC clamp-like starts such as `'SS' + 'N'*18`"*).
*Source:* api.md L76–L125; `oligopool/primer.py`; paper ¶"Barcodes"; docs.md L471.

**`per_sequence_provenance` = partial.** **(Evidence strengthened.)**
*Evidence:* Two real per-sequence mechanisms, one real gap.
*What exists:* (i) Each designed element lives in its own named column, so a row structurally records which barcode/primer/motif/spacer composes that oligo. (ii) `verify` emits genuine **per-row, per-COLUMN attribution** (api.md L1369–L1405, verbatim): `LengthConflictDetails.column_lengths` = *"Per-column contribution (gap-stripped lengths) for attribution"*; `ExmotifConflictDetails` is a *"list of emergence entries (one dict per emergent motif)"* with `motif`, `occurrences`, `library_baseline` (*"Library-wide baseline for this motif (minimum count across all oligos)"*), `excess_occurrences`, `positions` (*"0-based start offsets in `CompleteOligo`"*) and `columns` (*"Column attribution for each position (same length/order as `positions`)"*) — i.e. each occurrence is mapped back to the element column containing its start offset (`core_verify.py` assigns `columns` from each match's start position, so a junction-spanning motif is attributed to the column it starts in, not to a pair of columns); `BackgroundConflictDetails` carries the same `matched_kmers`/`positions`/`columns` triple. (iii) `compress` returns `mapping_df` (`ID`, `Sequence`, `DegenerateID`) and `expand(mapping_file=...)` *"restores original variant IDs in output"* (api.md L811, L862) — real per-sequence provenance across the compression step.
*What does not exist:* any record of **how a variant was derived** (no mutation or design history), because the package never derives variants. And the per-run `stats` dict is aggregate — docs.md **L176**, verbatim: *"`stats` is **aggregate**: programmatic pass/fail decisions and summary reporting."*
*Source:* api.md L1369–L1405, L811, L862; docs.md L176.

**`automatic_naming` = no.** **(Evidence rewritten; value unchanged.)**
*Evidence:* **Scoped to library-member (variant) naming, where it is airtight.** The `ID` column is a **required user input** on every table-based design module (docs.md L1304: *"Start with your variants in a CSV (must have an `ID` column)"*; the non-tabular modules take other inputs — `background` a sequence list/FASTA/`Sequence` table, `pack` FastQ files, `inspect` an artifact path, and `vectorDB`/`Scry` are classes), and **no module renames, enumerates, or invents variant IDs**. Output *file* names get auto-suffixes (`.oligopool.<module>.csv`).
*Two things this cell deliberately does NOT claim (both were wrong in the original memo and are easy to disprove):*
1. **Output column names are NOT all user-specified.** Five modules auto-create columns: `split` → `Split1`, `Split2`, … (api.md L676, count varies per oligo; even-numbered splits are auto-reverse-complemented); `pad` → `5primeSpacer`, `ForwardPrimer`, `<split_column>`, `ReversePrimer`, `3primeSpacer` (api.md L743); `final` → `CompleteOligo`, `OligoLength` (api.md L613); `expand` → `ExpandedSeq`, `OligoLength` (api.md L868); `compress` → `DegenerateID`, `DegenerateSeq`, `Degeneracy` (api.md L811–L812).
2. **`compress` does mint identifiers for rows the user never named.** Its `synthesis_df` is a table of **new rows** (`DegenerateID`, `DegenerateSeq`, `Degeneracy`, `OligoLength`) identified solely by auto-minted `DegenerateID`s. These name **degenerate groups**, not designed library members, so the value holds. Separately, the example helper `mutant_generator.py` auto-mints ref-position-alt variant IDs (`A5T`) — again example code, not `op.*`.
*Source:* docs.md L1304; api.md L613, L676, L743, L811–L812, L868; `mutant_generator.py`.

### Block B — assay coverage

**`synthesis_constraints` = yes.** **(Evidence rewritten — fabricated quote deleted, mechanism corrected.)**
*Evidence:* Enforced per sequence, at design time and again at QC time.
*Length:* `oligo_length_limit` is a **required** parameter on every generative design module (`barcode`, `primer`, `motif`, `spacer`) and on `join` and `pad`; `background`, `merge`, `revcomp` and `final` do not take it. `lenstat` reports length statistics and free space remaining (non-destructive); over-length constructs are resolved **constructively** by `split` (Tm- and Hamming-constrained overlaps for Gibson/homology assembly) → `pad` (Type IIS pads that are excised scarlessly before assembly; the enzyme removes the pads, and the `split` overlaps drive the actual joining — docs.md L878), not merely flagged.
*Forbidden sequences — correct mechanism:* **homopolymers and restriction sites are banned via `excluded_motifs`**, which accepts a list, CSV/FASTA path, DataFrame with an `Exmotif` column, comma-string, or multiple named sources. Documented usage, verbatim: docs.md L360 `op.barcode(..., excluded_motifs={'cutsites': 'cutsites.csv', 'homo': ['AAAA', 'TTTT']})`; docs.md L2223 `'homopolymers': ['AAAAA', 'CCCCC', 'GGGGG', 'TTTTT']`. Motifs must be strict ATGC (no IUPAC). Paper: barcodes *"must not contain homopolymer tracts that are challenging to sequence while also excluding a set of researcher-defined sequences, such as restriction sites."*
*Repetitiveness — a different mechanism:* `maximum_repeat_length` caps the **maximum shared repeat length** between the designed element and the input oligos / flanking context, with k-mer size = `maximum_repeat_length + 1` (api.md L397, L409). docs.md L468, verbatim: *"`maximum_repeat_length` controls non-repetitiveness against `input_data` only; screening against a background requires `background_directory`."* It constrains homopolymers only incidentally, and only by coincidence of corpus membership: `core_barcode.is_nonrepetitive` rejects a candidate's (k+1)-mer solely when that same k-mer is present in the input/context/background corpus, so a homopolymer run is not intrinsically capped.
*Off-target:* `background_directory` k-mer screening against host genome/plasmid/phiX DBs, applied junction-aware when context columns are given, layerable across multiple DBs, and re-checked in `verify`.
*Thermodynamics:* Tm windows and hairpin/homodimer/heterodimer/cross-dimer rejection for primers and overlaps.
*Dedicated pre-synthesis QC:* `verify` emits per-row `HasIntegrityConflict`, `HasLengthConflict`, `HasExmotifConflict`, `HasBackgroundConflict`, `HasAnyConflicts` plus four JSON detail columns with per-position, per-column attribution (schema quoted under `per_sequence_provenance`). **Motif emergence is checked as excess over a library-wide baseline** — `ExmotifConflictDetails.library_baseline` = *"Library-wide baseline for this motif (minimum count across all oligos)"* and `excess_occurrences` = `occurrences - library_baseline` — i.e. a row is flagged when its count for a motif exceeds the library-wide *minimum* (api.md L1439: *"A motif has emergence when its count exceeds the library-wide minimum (baseline)"*), so a motif present equally in every oligo is baseline rather than a conflict. Note this is an excess-over-baseline test, not specifically a junction test: the excess may also sit wholly inside one column. Most competing tools do not do this. Cost is addressed separately via `compress`.
*Source:* api.md L100, L184, L264, L338, L397, L409, L1369–L1405, `split`/`pad`/`lenstat`; docs.md L360, L468, L2223; paper ¶"Barcodes", ¶"Primers".

## 6. Notable capabilities NOT covered by the row list

Real strengths the matrix would otherwise miss. Several may deserve new rows; otherwise flag them explicitly as out of scope.

1. **The NGS analysis / demultiplexing half (Analysis Mode).** `index`, `pack`, `acount` (association counting), `xcount` (combinatorial multi-barcode counting), the **Scry** barcode classifier, efficient read packing; ~500 M reads/hour on 8 cores. The paper additionally claims index-hopped reads *"are identified during mapping and removed during counting"* and *"reporting of mismatch distributions"*, but **neither term appears anywhere in the current documentation** — today's `xcount` reports observed barcode combinations, retains reads when at least one barcode maps, and fills missing positions with `'-'`, while `acount` separately reports `BarcodeCount` and the stricter `AssociationCount`; neither output classifies hopped reads or carries a mismatch distribution. **No other tool in this survey closes the design→measurement loop.**
2. **Degenerate-oligo compression (`compress`/`expand`).** Lossless IUPAC compression of a concrete variant library into far fewer synthesis oligos (6–20× documented), with `mapping_df` (`ID`, `Sequence`, `DegenerateID`) mapping sequenced survivors back to original variant IDs. A **synthesis-cost** capability no other surveyed tool has.
3. **Background off-target screening** against a host genome/plasmid (`background` / `vectorDB` k-mer DB), applied junction-aware to barcodes, primers, motifs and spacers, layerable across multiple DBs, and re-checked in `verify`.
4. **Length-overflow resolution by construction:** `split` (Tm- and Hamming-constrained overlaps) and `pad` (Type IIS pads excised scarlessly before assembly — the enzyme removes the pads; the `split` overlaps do the joining).
5. **Patch Mode** (`patch_mode=True` on `barcode`/`primer`/etc.) — incrementally extend an already-ordered library, filling only missing elements, without redesigning or perturbing existing barcodes/primers. Directly relevant to multi-round library projects.
6. **Cross-set barcode orthogonality** (`cross_barcode_columns`, `minimum_cross_distance`) and **tandem/multi-barcode architectures** (CombiGEM-style), designed *and* counted combinatorially.
7. **Per-sub-pool primer design** (`oligo_set`) with cross-set dimer screening and per-set Tm matching — multiplexed sub-libraries independently amplifiable from one synthesis pool.
8. **Declarative architecture spec** (`examples/design-assembly-parser`): element list + element-spec dictionary, with `get_primer_order()` resolving the paired-primer design order by a one-pass `deque` insertion heuristic (not a general topological sort), and `split_spec`/`padding_spec` in the same call. The nearest analogue to PoolParty's declarative style — but a worked example, not a shipped API.
9. **CLI + YAML config with DAG scheduling**, `--dry-run`, YAML merge-key parameter sharing, and documented CLI > config > defaults precedence.
10. **Scale.** 4 M barcodes in 1.2 h; universal primer binding sites for 1 M 200-mers in 15 min; ~35 min for a 1 M-variant oligopool — all on an 8-core desktop. If the referee cares about scale, this is the benchmark to beat or concede.
11. **LLM-agent-ready documentation** (`docs/agent-skills.md`).
12. **Reproducibility as a first-class documented feature.** docs.md §"Reproducibility" (L279–L289), verbatim: *"All stochastic design modules support `random_seed` for reproducible results … Same seed + same inputs = same outputs. Great for debugging and publications."* `random_seed` is echoed back in the stats dict for `barcode`/`primer`/`motif`/`spacer`/`split`/`pad`/`compress`. **PoolParty presumably claims reproducibility too — do not present this as a differentiator.**
13. **Machine-readable output contract.** CLI `--stats-json` (stats dict as JSON to stdout) and `--stats-file path.json`, plus `--quiet` (docs.md L1477–L1479); api.md ships a formal **Stats Dict Schema** (`status`, `basis`, `step`, `step_name`, `vars`, `warns`, `module`, `input_rows`, `output_rows`) with a documented `basis` vocabulary (`solved`/`complete`/`unsolved`/`infeasible`/`verified`/`conflicts`/`corrupted`) and snake_case `vars` naming conventions (api.md L1665: *"expanded lowercase key terms … e.g. `melting_temperature`, `guanine_cytosine_content`, `minimum_free_energy`"*).
14. **User-extensible counting via the `callback` hook** (Python-only) in `acount`/`xcount`: `callback(r1, r2, ID, count, coreid)` where `r1` is read 1, `r2` is read 2 or `None`, `ID` is the identified barcode ID tuple, `count` the read frequency in the current pack — *"Returns: bool - True to accept, False to reject"* (api.md L1154–L1162; docs.md L2483). A genuine extension point at analysis time.
15. **Failed-read diagnostics.** `failed_reads_file` samples discarded reads by failure category — docs.md L2613, verbatim: *"Use `failed_reads_file` to sample discarded reads by failure category (anchor missing, barcode absent, barcode ambiguous, callback rejected, etc.)"* — with JSON-serialized `DiagnosticDetails` columns.
16. **Built-in phiX spike-in filtering.** `oligopool/base/phiX.py` ships the phiX k-mer spectrum; `core_count.py` imports it and exposes the `phix_match` failure category (*"PhiX contamination detected; first k-mer (k=30) match"*, api.md L1113, L1235) and the `phix_reads` counter (api.md L1666).
17. **Built-in Type IIS enzyme knowledge base.** api.md §"Type IIS Enzymes" (L1724–L1730) lists **34** enzymes — `AcuI, AlwI, BbsI, BccI, BceAI, BciVI, BcoDI, BmrI, BpuEI, BsaI, BseRI, BsmAI, BsmBI, BsmFI, BsmI, BspCNI, BspQI, BsrDI, BsrI, BtgZI, BtsCI, BtsI, BtsIMutI, EarI, EciI, Esp3I, FauI, HgaI, HphI, HpyAV, MlyI, MnlI, SapI, SfaNI` — with recognition motif **and** 3′ cut-offset models (e.g. BsaI `GGTCTC` + N×5), selected so pad excision is scarless; plus a common-restriction-site appendix. `pad` validates that the recognition site is absent from all split fragments in either orientation and *"fails early if conflicts are found"* (api.md L746).
18. **The `index` anchor model** — `barcode_prefix_column`/`barcode_suffix_column` with `barcode_prefix_gap`/`barcode_suffix_gap` (*"Bases between prefix anchor and barcode in read"*), plus a parallel set for associates (`associate_prefix_column`/`associate_suffix_column`/`associate_prefix_gap`/…). At least one of prefix/suffix is required. This is the explicit **design↔analysis contract** that lets barcodes be located at variable read offsets. (api.md L906–L956.)
19. **Two distinct barcode-design algorithms** selectable via `barcode_type`: `0`/`'terminus'` (fast, distinctive 5′/3′ ends) vs `1`/`'spectrum'` (thorough, k-mer saturation).
20. **`verify`'s per-row, per-COLUMN attribution** — `LengthConflictDetails.column_lengths` (per-element bp contribution) and `ExmotifConflictDetails` mapping every emergent-motif occurrence to the element column containing its start offset. Finer-grained than the `per_sequence_provenance` row credits.
21. **GC content is reported (not constrained) for primers** — `primer_guanine_cytosine_content`, on 6 lines of `oligopool/primer.py` stats. Phrase the barcode GC gap as "not constrainable", never "absent".
22. **The absence of any row-union / sub-library concatenation operator** (see §2). Not a strength — the **cleanest, most defensible contrast with PoolParty**, and the recommended load-bearing sentence for the referee response.

## 7. Stated limitations / scope boundaries (authors' own words, verified verbatim)

- **Variant content is the user's responsibility.** docs.md L1304: *"Start with your variants in a CSV (must have an `ID` column)"*; notebook: *"designing exact ribozymes is beyond the scope here."*
- **Excluded motifs are global.** docs.md L366: *"Excluded motifs are applied globally to all variants (no per-variant exclusion)."*
- **Design pipelines are mostly sequential.** docs.md L1634: *"Parallel execution helps most when steps are naturally independent. In practice, that is usually analysis workflows (`index`, `pack`, `xcount`, `acount`), while design workflows are often dependency-dense and mostly sequential."* Parallel design branches are described as **"Rare"**.
- **`compress` is a terminal branch.** docs.md L2395: *"treat `compress` output (`synthesis_df`) as a terminal branch in design mode. You usually don't chain it into `barcode`, `primer`, or `spacer`, because barcodes are intentionally maximally different and that works against IUPAC compression."* Restated at L2497.
- **`expand` blows up exponentially** and needs `expansion_limit` (docs.md L973–L974); *"Does NOT recover original variant IDs; use `mapping_df` from `compress` for that"* (L975).
- **Motif matching in `verify` is literal substring matching.** docs.md L1262: *"Motif matching is literal substring matching; IUPAC bases are not expanded as wildcards."*
- **`verify` silently skips degenerate columns.** api.md L1438: *"IUPAC/degenerate columns are skipped silently during DNA column detection"* — so Degenerate Mode output does not receive the same sequence-level QC as concrete designs.
- **`compress` has real applicability limits.** api.md L798, L817–L818: input *"Must contain only A/T/G/C (no degenerate codes)"*; *"Sequences of different lengths are compressed independently"*; *"If sequences are too diverse to compress, returns 1:1 mapping"*. `rollout_simulations` / `rollout_horizon` trade runtime for compression quality.
- **`final` drops annotations.** api.md L613: output contains `ID`, `CompleteOligo`, `OligoLength` only; docs.md L764 tells users to save the annotated DataFrame beforehand.
- **`pad` is per-fragment.** api.md L749: *"Run `pad` separately for each fragment (e.g., `Split1`, `Split2`, ...); you cannot pad all columns in one call."*
- **Cross-set barcode mode is global, not per-row** (api.md `barcode` Notes).
- **Excluded motifs must be strict ATGC** — no IUPAC codes, no dashes (api.md `barcode` / `primer`).
- **No native Windows support** — Linux, macOS, and WSL; Docker is the documented native-Windows path (README).
- **Structural, verified (not stated by the authors):** no row-union operator; no GC constraint for barcodes; no protein/reading-frame model; no genomic coordinate, GTF/GFF, HGVS, VCF, or consequence vocabulary anywhere; no plotting of any kind.
