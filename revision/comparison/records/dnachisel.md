## 2. What the tool actually is

Abstract: *"DNA Chisel is an easy-to-use, easy-to-extend sequence optimization framework allowing to freely define and combine optimization specifications via Python scripts or Genbank annotations."*

Usage section: *"An optimization problem is defined in DNA Chisel by a list of global or local specifications against which a starting linear or circular sequence will be optimized. A specification can be either a hard constraint, which must be satisfied in the final sequence, or an optimization objective, whose score must be maximized."*

Implementation section (solver): *"(i) resolution of all hard constraints, ignoring optimization objectives, and (ii) objectives maximization with respect to the constraints… A region's sequence is optimized via either a stochastic search (using random mutations of the sequence) or an exhaustive search through all possible sequence variants, depending on the number of variants."*

**The unit of work is one sequence in, one optimized sequence out.** This is enforced at both ends of the pipeline, not merely by convention:

- **Input:** `load_record(filepath, linear=True, name="unnamed", file_format="auto")` dispatches to `Bio.SeqIO.read` — **not** `parse` — so DNA Chisel's own loader accepts exactly one record and raises on a multi-record FASTA/GenBank.
- **Output:** `DnaOptimizationProblem.to_record(...)` returns one Biopython record; `write_record(record, target, file_format="genbank")` writes one record.
- **CLI:** `dnachisel <source> <target> [--circular] [--mute] [--with_sequence_edits]` — one file in, one file out; the module docstring concedes "this CLI will be developed on a per-request basis".

The word "variants" in the paper refers to candidate solutions explored *inside* the solver, not to library members emitted to the user. There is no library, pool, or variant-collection class anywhere in the API: `dnachisel/` contains only `DnaOptimizationProblem/`, `MutationSpace/`, `SequencePattern/`, `Specification/`, `biotools/`, `builtin_specifications/`, `reports/`, `utils/`, `Location.py`, `cli.py`, plus `__init__.py`, `version.py` and a `README.md`.

**Important nuance corrected this round:** the extraction framed DNA Chisel as "repair-and-optimize rather than generate". That framing is wrong. `dnachisel.random_compatible_dna_sequence(sequence_length, constraints, probas=None, seed=None, max_random_iters=5000, logger="bar", **kwargs)` is a **top-level export** whose docstring reads *"Produce a random sequence complying to some specifications"* — de-novo constraint-satisfying generation. The README's own headline example likewise starts from `random_dna_sequence(10000)`. DNA Chisel does generate; what it does not do is generate a *set*.

## 5. Capability-by-capability record

### Block A — library specification

**`library_as_object` — no.**
No class in the API represents a set of designed sequences. `DnaOptimizationProblem(sequence=…)` takes a single sequence; `docs/ref/core_classes.rst` lists only `DnaOptimizationProblem`, `CircularDnaOptimizationProblem`, `Specification`, `SpecEvaluation`, `Location`, `MutationSpace`/`MutationChoice` and pattern classes — no library/pool/variant module exists in the `dnachisel/` tree. The constraint is enforced at both ends: `load_record` uses `Bio.SeqIO.read` (not `parse`), so the loader accepts exactly one record and raises on multi-record FASTA/GenBank, and `cli.py` is `dnachisel <source> <target>` — one file in, one file out. Multi-sequence work is an explicit user `for` loop (`examples/common_scenarios/genome-wide-optimization.py`: one `DnaOptimizationProblem` per CDS, results appended to a list and written as a multi-record FASTA by the user; `ecoli_genes_optimization.py` loops over genes only to accumulate constraints into a single whole-record problem, and writes one record). Several specifications *consume* a set of sequences as reference material (`AvoidMatches(sequences=…)`, `AvoidBlastMatches(sequences=…)`, `AvoidHeterodimerization(other_primers_sequences)`, `MotifPssmPattern.from_sequences`), but the only API that takes a collection of sequences as its object of work is a *reporting* utility, `constraints_breaches_dataframe(constraints, sequences)`, which validates sequences the user already has.
*Source:* GitHub `master` tree; `docs/ref/core_classes.rst`; `dnachisel/biotools/genbank_operations.py`; `dnachisel/cli.py`.

**`dag_chaining` — partial.**
Specifications compose freely and nest one level via `SpecificationSet` ("Generic class for writing Specs which are actually made of more specs… the initialization actually creates a dictionary of standard Specifications in the DNAOptimizationProblem"), registered through `SpecificationSet.register_specifications`; `AllowPrimer` is such a set, expanding to `UniquifyAllKmers` + `EnforceMeltingTemperature` + three `AvoidPattern(RepeatedKmerPattern(k, n))` + optional `AvoidHeterodimerization`. But this composes *constraints on one sequence*, not design steps that produce sequences. There is no pipeline or DAG object anywhere in the tree; chaining problems (output of one feeding the next) is done by hand in user Python, as in `primers_collection.py`. "Partial" is the generous reading — a flat "no" would also be defensible, and erring generous toward a competitor is the safe direction for a referee response.
*Source:* `dnachisel/Specification/SpecificationSet.py`; `builtin_specifications/AllowPrimer.py`; `examples/common_scenarios/primers_collection.py`.

**`lazy_evaluation` — partial.** *(changed from "no")*
`dnachisel/MutationSpace/MutationSpace.py` defines `def all_variants(self, sequence)` with the docstring *"Iterate through all sequence variants in this mutation space."*, implemented as `for variants in itertools.product(*variants_slots): … yield new_sequence.decode()` — a true generator lazily enumerating the constrained combinatorial mutation space. Alongside it: `space_size` ("Return the number of possible mutations", computed without materializing anything as `exp(min(100, Σ log(choice counts)))` — so it saturates at e¹⁰⁰ for very large spaces, and returns 0 rather than 1 when there are no multichoices), `pick_random_mutations(n_mutations, sequence)` / `apply_random_mutations(n_mutations, sequence)`, and `MutationSpace.from_optimization_problem(problem, new_constraints=None)` (so e.g. `EnforceTranslation` yields the space of all synonymous CDS variants). Separately, `DnaNotationPattern.all_variants()` eagerly returns a Python list containing every concrete ATGC sequence encoded by one user-supplied IUPAC pattern. These are public, not internal: `docs/ref/core_classes.rst` contains `.. automodule:: dnachisel.MutationSpace :members:` and the rendered page `ref/core_classes.html` documents `all_variants`, `apply_random_mutations`, `choices_span`, `constrain_sequence`, `from_optimization_problem`, `localized`, `pick_random_mutations`, `space_size`, `string_representation`, while the same page documents `DnaNotationPattern.all_variants`. **Bounded, however:** both paths return bare unlabelled sequence strings with no identity or metadata, for one problem or one pattern; `MutationSpace.all_variants` is a solver helper for exhaustive local search; and no example, docs prose, or the paper ever presents either as a way to emit a managed library. So there is a documented lazy generator over a combinatorial design space and an eager degenerate-pattern expander, but no lazy materialization of a *library*.
*Source:* `dnachisel/MutationSpace/MutationSpace.py`; `dnachisel/SequencePattern/DnaNotationPattern.py`; `docs/ref/core_classes.rst`; https://edinburgh-genome-foundry.github.io/DnaChisel/ref/core_classes.html.

**`mixed_mutagenesis_one_pool` — no.** *(value kept; evidence fully rewritten — the extraction's reasoning was wrong)*
The missing thing is the **pool**, not the primitives. The primitives exist and must not be denied: exhaustive enumeration via `MutationSpace.all_variants()`; random sampling via `MutationSpace.pick_random_mutations` / `apply_random_mutations(n_mutations, sequence)` plus `DnaOptimizationProblem.mutations_per_iteration`; and an explicit "force at least N nucleotide changes" primitive in `EnforceChanges(minimum=3)` / `EnforceChanges(minimum_percent=70)`, documented under "Forcing changes" in `docs/genbank/genbank_api.rst` with GenBank shorthands `@change`, `@change(minimum=50%)` and `~change` (`changes.md` v3.0.0: "AvoidChanges and EnforceChanges can now tunable" [sic]); the mirror-image primitive `AvoidChanges(max_edits=3)` / `AvoidChanges(max_edits_percent=…)` caps rather than forbids edits in a region. What does not exist is any way to emit **multiple mutagenesis regimes into one labelled output**: no library object, no WT/control replicates, no per-variant records, no regime labels. The solver collapses the mutation space to a single output sequence, and `all_variants` yields unlabelled strings from a single regime over a single sequence. Mixing e.g. exhaustive singles + sampled doubles + WT controls into one pool with provenance is not expressible.
*Source:* `dnachisel/MutationSpace/MutationSpace.py`; `builtin_specifications/EnforceChanges.py`; `docs/genbank/genbank_api.rst`; `changes.md`.

**`combinatorial_motif_place` — no.**
`EnforcePatternOccurence` (`@insert()`) sets a required occurrence *count* of a pattern in a region: docs state it "ensures that exactly one occurence of the pattern is present in the given region, but it can also be used to create more occurences", and that new occurences will be "preferentially placed towards the center of the selected region"; the paper adds that "an `insert(CGTCTC)` constraint will attempt to place the pattern 'CGTCTC' at different locations of the sequence". There is no product API over motifs × positions × orientations × permutations. The alternative placements the solver considers are never **emitted as distinct library members** — the problem returns one sequence with one chosen placement. (Deliberately softened from the extraction's "search states, not enumerated": `MutationSpace.all_variants()` *can* enumerate the space, so the defensible claim is about emission as library members, not about enumeration.) Most other motif handling in the tool is *avoidance* — `sequence_without_tf_binding_sites.py` is pure avoidance — but not all of it: `EnforcePatternOccurence` accepts any `SequencePattern`, including a `MotifPssmPattern` (buildable with `from_sequences` / `from_file`), so a PSSM motif can be positively enforced to a requested occurrence count; the paper's SI Note 1 says the same, listing a PSSM among the patterns usable by "specifications such as AvoidPattern and EnforcePattern".
*Source:* `docs/genbank/genbank_api.rst`; paper §Usage; `builtin_specifications/EnforcePatternOccurence.py`; `docs/ref/core_classes.rst` (pattern classes).

**`barcode_generation` — partial.** *(changed from "no"; definitional fork flagged below)*
No barcode/UMI/demultiplexing abstraction exists — the string "barcode" appears nowhere in the built-in specification list, the biotools reference, the docs TOC or the `builtin_specifications/` listing — and there is **no mechanism to attach generated tags to library members**. But three of the four things a barcode row normally means are shipped and documented. (a) *Generate a constraint-satisfying short sequence de novo*: `dnachisel.random_compatible_dna_sequence(sequence_length, constraints, probas=None, seed=None, max_random_iters=5000, logger="bar", **kwargs)`, a top-level export — "Produce a random sequence complying to some specifications" — which returns exactly one sequence per call, so a set of N tags requires a user loop. (b) *Minimum pairwise distance*: `EnforceRegionsCompatibility(locations, compatibility_condition, condition_label)` is an all-pairs constraint (`evaluate` runs `itertools.combinations(self.locations, 2)`, scoring `-len(incompatible_pairs)`) with an arbitrary user predicate, and the shipped, unit-tested example `examples/builtin_specifications_examples/example_EnforceRegionsCompatibility.py` uses exactly `sequences_differences(seq1, seq2) >= 2` over `locations=[(0,4),(50,54),(100,104),(150,154)]` with `condition_label="2bp difference"` — i.e. an explicit minimum-Hamming-distance constraint over a set of four 4-nt tags. `sequences_differences` is a top-level `dnachisel` export; `EnforceRegionsCompatibility` is listed in `docs/ref/builtin_specifications.rst`; `tests/builtin_specifications/test_EnforceRegionsCompatibility.py` exists. (c) *Composition filters*: the `primers_collection.py` recipe applies `AvoidPattern("3x3mer")`, `AvoidPattern("4xG")` and `EnforceGCContent(target=0.6)` — the usual repeat, homopolymer and GC filters. Only (d), binding tags to library members, is genuinely absent. **Barcode-set design is therefore expressible but must be hand-assembled, and the product is a bare list of strings with no member association, no demultiplexing model and no distance guarantee across an entire designed set (the constraint is over hand-listed sub-locations of one sequence).**
*Definitional fork, stated openly:* if the matrix defines this row as "primitives from which a barcode set can be built", the correct value is `partial` and is recorded here. If the matrix defines it narrowly as "a first-class barcode generator producing a demultiplex-ready set bound to library members", the correct value is `no`. The extraction said `no` and the reviewer said `partial`; both rounds agree on every underlying fact and differ only on the row's definition, so this is recorded as `partial` (the reading that gives the competing tool full credit) with the narrow reading named explicitly rather than suppressed. It is **not** recorded as `unknown`, because nothing about the tool is unknown.
*Source:* `dnachisel/utils/utils.py`; `builtin_specifications/EnforceRegionsCompatibility.py`; `examples/builtin_specifications_examples/example_EnforceRegionsCompatibility.py`; `examples/common_scenarios/primers_collection.py`; `docs/ref/builtin_specifications.rst`.

**`per_sequence_provenance` — partial.**
For the single output sequence the provenance is genuinely rich and machine-readable — richer than the extraction credited. `problem.to_record(..., with_constraints=True, with_objectives=True, with_sequence_edits=True)` writes GenBank features for every objective and for every constraint carrying a single `location` (specifications that hold a `locations` list instead, such as `EnforceRegionsCompatibility`, are skipped), and one feature per contiguous run of edited nucleotides labelled `before=>after` (rendered red; `sequence_edits_as_features` merges adjacent edits into one segment via `sequences_differences_segments`). `write_optimization_report` emits a bundle containing `Report.pdf`, `final_sequence.gb`, `final_sequence_with_edits.gb`, `constraints_before_and_after.csv` (columns: constraint, start, end, before, after, edits, % edited) and `objectives_before_and_after.csv` (columns: objective, boost, start, end, before, after, edits, % edited) — i.e. one row per specification carrying before/after PASS-FAIL or score plus an edit count and a % edited figure for that specification's span — plus before/after sequenticons inside `Report.pdf`, and, only when the problem was created from a file (`file_path`), an embedded copy of that file named `[first 8 hex digits of its md5]_[original_basename]`. `logs.txt` is **not** part of this bundle; it is written by `write_no_solution_report`. The paper describes this as "comprehensive optimization reports for traceability and troubleshooting". **But** this is provenance of *how one sequence was edited*, not structured metadata about a library member's construction lineage; there is no per-member record because there is no library. `partial` holds under the library-member reading of the row.
*Source:* `dnachisel/reports/optimization_reports.py`; `DnaOptimizationProblem/mixins/RecordRepresentationMixin.py`; paper §Implementation.

**`automatic_naming` — no.** *(evidence corrected — the extraction was factually wrong)*
`to_record(..., record_id=None)` does `record = sequence_to_biopython_record(self.sequence)` and then only `if record_id is not None: record.id = record_id`. Since `sequence_to_biopython_record(sequence, id="<unknown id>", name="<unknown name>", features=())`, **the default output id is the literal string `"<unknown id>"`** — it is *not* inherited from the input record, as the extraction claimed. Naming is entirely the user's job (in the genome-wide example the user passes `protein_id`). Nothing generates names encoding what was designed. The nearest thing to auto-identification is visual, not nominal: reports embed `sequenticon(seq, output_format="html_image", size=24)` for the before and after sequences — an auto-generated identicon image, not a name or an accession. The corrected fact strengthens the "no".
*Source:* `DnaOptimizationProblem/mixins/RecordRepresentationMixin.py`; `dnachisel/biotools/genbank_operations.py`; `dnachisel/reports/optimization_reports.py`.

**`design_visualization` — partial.**
Visualization is real and better than the extraction credited, but it is per-sequence. `write_optimization_report` produces `Report.pdf`: before/after summary tables for every constraint and objective, before/after sequenticons, and — only when `geneblocks` is installed, which the `[reports]` extra does not do — the before/after edit-diff figure that `plot_optimization_changes` renders with GeneBlocks `DiffBlocks.from_sequences(before, after).plot(translator_class=SpecAnnotationsTranslator, ...)`; its `max_features_in_plots` parameter is accepted but never read. The annotated whole-sequence plotting via `dna_features_viewer` through a `SpecAnnotationsTranslator` (paper Fig. 1C) belongs to `write_no_solution_report`, which renders both a whole-sequence figure with the failing zone shaded and a cropped local-breaches figure with passing constraints in green, plus `local_constraints_breaches.gb` and `plots.pdf`; `breaches_records_to_pdf` renders constraint breaches across many records; and `MutationSpace.plot(ax, color="red", y_offset=-2)` / `MutationSpace.string_representation(separator="|")` visualize the allowed-variant space itself. What is absent is a **design-graph / pipeline view** and a **library-level view** — the extraction's blanket "there is no view of the design" is loose given `MutationSpace.plot` and should not be used as written.
*Source:* `dnachisel/reports/optimization_reports.py`; `dnachisel/MutationSpace/MutationSpace.py`; paper Fig. 1C.

### Block B — assay coverage

**`assay_dms` — no.**
Checked against the complete built-in specification list, `docs/examples.rst` and the full `examples/` tree: no per-position saturation, no codon-substitution enumeration for variant libraries, no variant table output, no DMS terminology anywhere.
*Source:* `docs/ref/builtin_specifications.rst`; `docs/examples.rst`; `examples/` tree.

**`assay_mpra` — no.**
No regulatory/MPRA library design. Motif functionality is overwhelmingly *avoidance*: `MotifPssmPattern` is a `SequencePattern` (listed under pattern classes alongside `EnzymeSitePattern`, `HomopolymerPattern`, `RepeatedKmerPattern`) used for `AvoidPattern`-style constraints, and `sequence_without_tf_binding_sites.py` attempts to download E. coli TFBS data in order to forbid all matches. It is not avoidance *only* — `EnforcePatternOccurence` takes the same pattern objects, so a PSSM motif can be enforced to a target occurrence count — but that is a count within one sequence, not a designed set. No promoter or enhancer tiling, no combinatorial motif installation, no oligo-pool output anywhere in the tree.
*Source:* `docs/ref/core_classes.rst`; `examples/common_scenarios/sequence_without_tf_binding_sites.py`.

**`assay_insilico` — no.**
Nothing in the paper, docs, README, source tree or examples concerns probing predictive or generative genomic AI models. Every *shipped* objective is a biochemical, manufacturing or edit-distance score: CAI, codon-usage matching, RCA harmonization, GC content, melting temperature, hairpins, homology, restriction sites, the edit-count objectives `AvoidChanges` / `EnforceChanges`, and the user-defined Gen9 9-mer synthesis score. A user can wrap a predictive model in a custom `Specification.evaluate` (or pass an `evaluate` callable to `Specification`) and the standard objective loop will optimize its returned score — the paper offers "any new sequence specification that the Python language can express" — but no shipped specification, example or doc page does this.
*Source:* paper (full text); `docs/ref/builtin_specifications.rst`; `examples/` tree.

### Block C — genomics integration

**`genome_coordinates` — no.**
`Location(start, end, strand)` is purely sequence-relative — docs: "Location(5, 10) represents sequence[5, 6, 7, 8, 9]". `Location.from_data` accepts only a tuple/list, a Biopython `FeatureLocation`, or another `Location`, and `Location.from_biopython_location` reads only `.start`, `.end`, `.strand`. There is no assembly awareness, no `chrom:start-end` input, and no liftback of designed sequence to genome coordinates. A genome can be *loaded* as a Biopython record and features extracted by the user (`feature.location.extract(genome_record)` in the genome-wide example) — that extraction happens on the user side with Biopython, outside DNA Chisel.
*Source:* `dnachisel/Location.py`; `docs/ref/core_classes.rst`; `examples/common_scenarios/genome-wide-optimization.py`.

**`transcript_models` — no.**
Input is FASTA/GenBank/SnapGene: `load_record` dispatches to `Bio.SeqIO.read` for genbank/fasta and to `snapgene_file_to_seqrecord` for `.dna`; `write_record` exports genbank or fasta. There is no GFF/GTF support anywhere in docs or source, and no transcript/isoform concept. The GenBank parser (`from_record`) reads only `misc_feature` labels beginning with `@` or `~` — i.e. specification declarations, not gene models. Note also that `SeqIO.read` (not `parse`) means a single record only, so even a multi-transcript file cannot be loaded.
*Source:* `dnachisel/biotools/genbank_operations.py`; `docs/genbank/genbank_api.rst`.

**`exon_intron_split_codons` — no.** *(evidence strengthened)*
`EnforceTranslation.set_location` validates that "Location length in Codon Specifications should be a 3x" and iterates codons contiguously via `codon_index_to_location(i)`. Its constructor standardizes locations through `Location.from_data`, which accepts tuples/lists, a Biopython `FeatureLocation`, or a DNA Chisel `Location` but has no `CompoundLocation` branch. A supplied compound location therefore becomes `None`; `EnforceTranslation` treats it as omitted and `_copy_with_full_span_if_no_location` substitutes the whole sequence during problem initialization. `from_record` also ignores CDS features and parses only labelled `misc_feature` specifications. There is no exon-array handling and no logic for codons spanning an intron boundary.
*Source:* `dnachisel/Location.py`; `Specification/Specification.py`; `builtin_specifications/EnforceTranslation.py`; `DnaOptimizationProblem/mixins/RecordRepresentationMixin.py`.

**`hgvs_input` — no.**
No HGVS or other variant nomenclature parsing anywhere in the source tree, and no variant-parsing module. Checked against the GenBank annotation vocabulary documented in `docs/genbank/genbank_api.rst`: constraint forms `@no`, `@keep`, `@change`, `@insert`, `@sequence`, `@choice`, `@cds`, `@gc`, `@all_unique_kmers`, `@avoid_matches`, `@tm`; objective forms `~use_best_codon`, `~match_codon_usage`, `~harmonize_rca`, `~no`, `~change`; and the long class-name forms (`@AvoidPattern`, `@EnforceTranslation`, …). Nothing resembling `c.76A>T` / `p.Lys76Ter` notation.
*Source:* `docs/genbank/genbank_api.rst`; GitHub `master` tree.

**`vcf_vep_output` — no.**
Outputs verified in source: `write_record` (genbank or fasta); the report bundles (on success `Report.pdf`, `final_sequence.gb`, `final_sequence_with_edits.gb`, `constraints_before_and_after.csv`, `objectives_before_and_after.csv`; on failure `plots.pdf`, `local_constraints_breaches.gb`, `logs.txt`; either way a copy of the source file when one was supplied); and `constraints_breaches_dataframe` returning a pandas DataFrame exportable to Excel, plus `breaches_records_to_pdf`. There is no VCF writer and no VEP-compatible output anywhere.
*Source:* `dnachisel/biotools/genbank_operations.py`; `dnachisel/reports/optimization_reports.py`; `dnachisel/reports/constraints_reports/`.

**`consequence_annotation` — no.**
`sequences_differences`, `sequences_differences_segments` and `annotate_differences` locate where two sequences differ, and `sequence_edits_as_features` labels each edit `before=>after` in red — but nothing classifies molecular consequence (stop-gained, missense, frameshift, in-frame indel, splice). Coding consequence is *constrained away* by `EnforceTranslation` and `AvoidStopCodons` rather than annotated after the fact.
*Source:* `dnachisel/biotools/`; `DnaOptimizationProblem/mixins/RecordRepresentationMixin.py`.

### Block D — physical construction

**`primer_design` — partial.**
`AllowPrimer` — "Enforce various specifications for enabling primers at the location… useful for making sure that you will be able to conduct a PCR or sanger sequencing with a primer annealing at a particular location" — is a `SpecificationSet` expanding to `UniquifyAllKmers(k=max_homology_length)` + `EnforceMeltingTemperature(tmin, tmax)` + `AvoidPattern(RepeatedKmerPattern(k, n))` for `((2,5),(3,4),(4,3))` + optional `AvoidHeterodimerization(other_primers, tmax=max_heterodim_tm)`. `AvoidHeterodimerization` and `EnforceMeltingTemperature` are separately available, and `primers_collection.py` documents building 20 mutually non-heterodimerizing 20-mers at ~60% GC, each new primer constrained against all previously accepted ones. **Limits:** these design/validate primer *annealing sites and sequences* de novo — there is no mutagenic-primer design (no NNK/degenerate mutagenesis primers), no assembly-oligo tiling, no protocol-aware oligo splitting for a variant library. **Practical limitation:** `primer3-py` is *not* a runtime dependency — PyPI `requires_dist` lists it only under `extra == "tests"` — so `AvoidHeterodimerization.evaluate` raises `ImportError("Using avoid_heterodimerization requires primer3 installed (pip install primer3-py)")` on a default `pip install dnachisel`, and the documented `primers_collection.py` example will not run out of the box. Neither `AvoidHeterodimerization` nor `EnforceRegionsCompatibility` can be declared as GenBank annotations (docs: "Specifications not yet supported as Genbank annotations").
*Source:* `builtin_specifications/AllowPrimer.py`, `AvoidHeterodimerization.py`; `examples/common_scenarios/primers_collection.py`; PyPI `dnachisel` JSON `requires_dist`; `docs/genbank/genbank_api.rst`.

**`codon_optimization` — yes.**
Core feature, confirmed at every level. `CodonOptimize` wrapper plus `MaximizeCAI`, `MatchTargetCodonUsage`, `HarmonizeRCA` and `AvoidRareCodons` in `dnachisel/builtin_specifications/codon_optimization/`, all exported from `__init__`, all listed in `docs/ref/builtin_specifications.rst`, in the README example and in paper Fig. 1A ("Gene NUM1 of Saccharomyces cerevisiae will be codon optimized for Escherichia coli"), with `EnforceTranslation` protecting the protein. The top-level `reverse_translate(protein_sequence, randomize_codons=False, table="Standard")` also maps one user-supplied amino-acid sequence to one DNA sequence, choosing the first valid codon or a random synonymous codon; it does not enumerate a codon/amino-acid substitution library. **Provenance modernized (the extraction cited 2020 sources for 2025 software):** the paper cites Nakamura 2000 / the Codon Usage Database, but current DnaChisel depends on EGF's `python_codon_tables` (a listed runtime requirement on PyPI) and accepts a species by name (`e_coli`, `h_sapiens`, `s_cerevisiae`, …) **or by NCBI TaxID** (`species=1423`), in which case frequencies are downloaded from Kazusa. `EnforceTranslation` gained alternative genetic codes (`genetic_table=`) and non-ATG start-codon policies (`start_codon=keep|ATG`) in v3.0.0, released 2019-11-16 — a month *before* the paper was submitted (received 2019-12-18), not after it.
*Source:* `builtin_specifications/codon_optimization/`; `dnachisel/biotools/sequences_operations.py`; `docs/ref/builtin_specifications.rst`; `README.rst`; paper Fig. 1A; PyPI `requires_dist`; `changes.md`.

**`synthesis_constraints` — yes.**
Unambiguously the tool's core purpose. README: sequences can be optimized to "meet the constraints of a commercial DNA provider, avoid homologies between sequences, tune GC content" (verified verbatim). Specifications: `AvoidPattern` (restriction sites, homopolymers such as `6xA`, repeated k-mers such as `3x2mer`, IUPAC patterns, regexes), `AvoidHairpins` (per IDT guidelines), `EnforceGCContent` (global and windowed), `EnforceTerminalGCContent`, `UniquifyAllKmers` (whose docstring warns it "may not work as a problem constraint" where a subsequence appears more than twice, though it does work as an objective), `AvoidMatches` (Bowtie) / `AvoidBlastMatches` (BLAST), `SequenceLengthBounds` (a checker only — "it can't really be solved or optimized", there being no indel operation), plus the user-defined Gen9 9-mer synthesis score example. Batch QC exists via `constraints_breaches_dataframe(constraints, sequences)`, which was read in source and does accept `[(name, seq), …]`, a dict, or Biopython records; the returned DataFrame is exported to Excel by pandas' `to_excel`, and rendered as PDF plots by `records_from_breaches_dataframe` + `breaches_records_to_pdf`. Enforcement itself is per-sequence (one sequence at a time).
*Source:* `README.rst`; `docs/ref/builtin_specifications.rst`; `dnachisel/reports/constraints_reports/constraints_breaches_dataframe.py`.

## 7. Additional capabilities (candidate new matrix rows)

1. **Constraint/objective solving on an existing sequence** — repair-and-optimize under a declarative spec list, DNA Chisel's defining capability, orthogonal to every current row. *(But note item 2: it also generates.)*
2. **De-novo constraint-satisfying sequence generation** — `random_compatible_dna_sequence(sequence_length, constraints, probas, seed, max_random_iters)`, a top-level export; the README's headline example itself starts from `random_dna_sequence(10000)`. The extraction's "repair-and-optimize rather than generate" framing was wrong and is retracted here.
3. **Lazy enumeration of a constrained combinatorial mutation space** — `MutationSpace.all_variants()` (generator over `itertools.product`), `space_size` (cardinality without materialization, saturating at e¹⁰⁰), `pick_random_mutations` / `apply_random_mutations(n, seq)`, `from_optimization_problem(problem)`, `string_representation()`; all on the public API reference page via `.. automodule:: dnachisel.MutationSpace :members:`. `plot(ax)` also exists in source, but it has no docstring and is absent from the rendered page.
4. **Batch synthesis-constraint QC over a set of sequences** — `constraints_breaches_dataframe(constraints, sequences)` accepting `[(name, seq), …]` / dict / records, exporting Excel + `breaches_records_to_pdf`. A genuine multi-sequence feature and the fairest thing to credit DNA Chisel with in a library-oriented table.
5. **Set-level cross-member constraints with user predicates** — `EnforceRegionsCompatibility(locations, compatibility_condition, condition_label)`, all-pairs over hand-listed subregions; the closest analogue to PoolParty-style cross-member constraints.
6. **Extensibility by user-defined design primitives** — new `Specification` subclasses with custom `evaluate`/`localized`, optionally registered with the GenBank parser. Directly comparable to PoolParty's user-defined Operations.
7. **Annotation-driven (no-code) design specification** — problems declared as GenBank feature labels (`@keep`, `@no(BsaI_site)`, `@change(minimum=50%)`, `~use_best_codon`) editable in SnapGene/Benchling.
8. **Circular-sequence / cross-origin support** — `CircularDnaOptimizationProblem`.
9. **Homology / repeat-uniqueness control across a construct** — `UniquifyAllKmers`, `AvoidMatches` (Bowtie), `AvoidBlastMatches`.
10. **Oligo/primer cross-reactivity control** — `AvoidHeterodimerization`, `max_heterodim_tm` (subject to the primer3 install caveat).
11. **Explicit "force at least N (or X%) nucleotide changes" primitive** — `EnforceChanges(minimum=3)` / `EnforceChanges(minimum_percent=70)`, GenBank shorthands `@change`, `@change(minimum=50%)`, `~change`. The nearest thing DNA Chisel has to a mutagenesis knob.
12. **Documented reproducibility contract** — `docs/notes.rst`: "The randomness in DNA Chisel is entirely determined by the Numpy random generator"; set `numpy.random.seed(123)` *before* calling any part of DNA Chisel and results are deterministic; reproducibility failures despite the seed are treated as bugs. Backed by a `tests/test_determinism/` suite with fixture CSVs. **Relevant if PoolParty claims reproducibility as a differentiator — DNA Chisel has an explicit, documented one.**
13. **Rich machine-readable per-sequence provenance bundle** — per-specification before/after CSVs with edit counts and `% edited`, an embedded copy of the source file prefixed with the first 8 hex digits of its md5 (only when the problem was built from a file), sequenticons, and a GeneBlocks diff figure when `geneblocks` is installed. (`logs.txt` belongs to the no-solution report, not this bundle.)

## 8. Stated limitations / scope statements

- The problem is defined on "a starting linear or circular sequence" (singular) — the framework has no library-level scope. Reinforced by `load_record` = `SeqIO.read` (one record in) and the one-in/one-out CLI.
- The primer-collection example concedes in its own docstring that "DNA Chisel is not originally meant for creating collections of sequences … but it is still possible to create collections of inter-compatible sequences".
- The solver is heuristic (stochastic search, or exhaustive local search when the variant count is small); constraints may be unresolvable, in which case `write_no_solution_report` emits a troubleshooting figure of the problematic region plus `local_constraints_breaches.gb` rather than a solution.
- `EnforceTranslation` requires a contiguous, in-frame, length-divisible-by-3 location — no spliced CDS. A supplied `CompoundLocation` is unsupported, becomes `None`, and is initialized over the full sequence rather than its exon parts.
- The GenBank annotation interface does not support all specifications — docs list `AvoidHeterodimerization` and `EnforceRegionsCompatibility` as "not yet supported as Genbank annotations", and the parser's default registry `DEFAULT_SPECIFICATIONS_DICT` additionally omits `AvoidMatches`, `AvoidStopCodons`, `EnforceTerminalGCContent` and `SequenceLengthBounds`, so the documented `avoid_matches` annotation is not parseable by the stock parser.
- `EnforceSequence` and `EnforceChoice` both still carry the module-header warning "DO NOT USE YET: Work in progress, stabilizing" in v3.2.16, although both are registered in the GenBank parser and `EnforceSequence` is in the published built-in reference.
- Report plotting degrades with many features ("plots with thousands of features may take ages to plot").
- **Optional/undeclared dependencies:** Bowtie for `AvoidMatches`; local NCBI BLAST+ for `AvoidBlastMatches` (whose own docstring says "Only local BLAST is supported/tested as for now" and opens "WARNING: try using AvoidMatches instead, it is much better!!"); `snapgene_reader`, which is not declared in `pyproject.toml` at all, for `.dna` SnapGene input; the `[reports]` extra (matplotlib, pdf_reports, sequenticon, dna_features_viewer, pandas) for any report; `geneblocks`, listed only under `extra == "tests"`, for the report's edit-diff figure (the PDF prints an install note in its place); and **`primer3-py`, which is likewise listed only under `extra == "tests"` and is therefore absent from a default install — `AvoidHeterodimerization` raises `ImportError` and the documented `primers_collection.py` example will not run out of the box.**
- The default output record id is the literal `"<unknown id>"` unless the user supplies `record_id` — sequences are not self-identifying.
